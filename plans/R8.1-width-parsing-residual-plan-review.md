## 3. The named focus areas

### 3.1 Step-0 cross-check of the three unit conversions — clean

cm: `Value / 2.54 * 300` is exactly the architecture's
`widthCm / 2.54 * 300`. Inches: `Value * 300` is `widthInches * 300`.
Pixels: `Value` verbatim is "the entered value is the pixel width". Height:
`pixelWidth_unrounded * sceneHeightPt / sceneWidthPt` is the architecture's
`pixelWidth * sceneHeightPoints / sceneWidthPoints` as a formula; the
composition order is the one ambiguity, resolved in §3.2. Safety: the
positive-dimension and documented-limit requirements are satisfied and each
guard is pinned by a test. **The Step-0 cross-check verifies clean under
the ruling.**

### 3.2 Rounding composition ambiguity — explicitly resolved

The architecture's two-line text, read literally, derives `pixelHeight` from
the already-rounded `pixelWidth`; `ExportSize.ToPixels` derives the height
from the unrounded width and rounds each dimension once at the final
boundary. The two readings differ by at most 1 px, and only when the
unrounded width's fractional part straddles the height's rounding midpoint
(10 cm on a 2:1 scene: 1181×591 implemented vs 1181×590 literal under
to-even). **Resolution — owner ruling 2026-11-22: the implementation is
normative.** The rationale is recorded and defensible: (a) checklist A
requires rounding at exactly one documented boundary with no repeated
rounding through the pipeline — feeding a rounded width into the height
computation is a second rounding use, while the implementation rounds each
output exactly once; (b) the unrounded-width height preserves the scene
aspect ratio with maximum fidelity, not propagating the width's rounding
error into the height; (c) the existing suite pins the behaviour. The plan
is consistent with the ruling in its header, §4, §7 and §10 R1, and
correctly does **not** edit `02-ARCHITECTURE.md` (documentation-only
clarification, per the ruling). The residual — a future reader of the
architecture text alone can still misread the composition — is accepted by
the ruling and mitigated by the feed-contract record.

### 3.3 One-boundary discipline — confirmed with a broader net

The duplicate-parser check was re-run with tokens beyond the plan's
original grep: the unit-suffix `EndsWith` calls, `ExportUnit`, both limit
constants, and `Dpi`. Only `ExportSize.cs` matches. The plan's claim
survives a stronger test than it reports — the plan's P1 step should re-run
this broader pattern at execution time, not only the original four tokens.

### 3.4 Consistency with the owner ruling — enforced

Every load-bearing statement in the plan agrees with the ruling:
implementation normative; the reading recorded in the feed contract; no
parser change; no `02-ARCHITECTURE.md` edit; no ADR. The stop conditions
are restated and, with the ruling, expected unreachable. No section of the
plan proposes or implies a code change.

### 3.5 Test inventory — exact

The Raster test project contains exactly one test file. Re-counted: 4
`[Theory]` methods (5 + 5 + 6 + 4 = 20 cases) and 21 `[Fact]` methods = 25
methods, 41 executed cases, matching the plan's DoD-1 and the recorded
"Raster 41" gate counts. The plan's "no new tests, justified" position is
sound: the equality pin's producer does not exist until R8.7, and no new
validator ships, so the every-validator-positive-test rule is not
triggered.
