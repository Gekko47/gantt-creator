## 1. Verdict

The plan is contract-grounded, correctly sequenced, and honest about owed
gates. Its probe-first discipline, its validate-before-replace reading of
D1/D2, and its deterministic failure-matrix arms are all right. But an
adversarial pass finds **thirteen defects**, two of which are wrong as
written (a mischaracterized numeric conversion and a self-contradictory
integration task), and one of which (W4) would produce an **invalid PNG** if
the probe lands on the "wrong density present" arm and the implementer follows
the plan literally. The §12 owner checkpoints are mostly well-reasoned; one
(CP2) papers over a documentation residue it should have named.

---

## 2. Strengths (prioritized)

1. **The encoder decision tree is probe-decided inside pre-ruled boundaries**
   (plan §4.2). It honours F9's anti-assumption ruling, keeps the chunk patcher
   in-tree exactly as the review ruled, and reserves the custom-writer stop
   condition. This is the strongest part of the plan.
2. **Validate-before-replace is pinned to D1 with the D2 tension made
   explicit** (§4.4): validating the flushed temp from disk is strictly
   stronger than replace-then-validate and leaves no non-atomic window. The
   "re-read from the written file" reading is reconciled rather than glossed.
3. **The failure matrix uses only deterministic host-free arms** and —
   unusually self-aware — flags the classic Windows trap itself (risk 4: a
   directory's ReadOnly attribute does not block file creation), substituting
   illegal-chars, parent-is-a-file, and read-only-target-file arms.
4. **The independent test-side parser** (§8.2) satisfies R8.5 D1's "no image
   library trust" and pre-builds R8.8 D2's separate-decoder requirement.
5. **No new dependencies**: the hand-rolled CRC-32 with the standard check
   vector avoids the `System.IO.Hashing` package and the AGENTS.md dependency
   stop condition; ADR-0071 remains the complete dependency record.
6. **The owed gate is recorded, not hidden** (§10, risk 8): the live
   unwritable-path case is marked Required-and-owed until R8.8, per F8.
7. **Traceability**: every acceptance line in both work items maps to a named
   test arm (§8.3), including the two mandated positives (wrong-density
   comparator, mid-write target-untouched).

## 3. Findings

| ID | Severity | Finding and evidence | Required revision |
| --- | --- | --- | --- |
| W1 | **High — correctness** | §6 claims the 11811 conversion "is integer arithmetic over `ExportSize.Dpi` / `CmPerInch`". Both constants are `const double` ([`ExportSize.cs`](../src/GanttCreator.Raster/ExportSize.cs) lines 44 and 47); the conversion is double arithmetic — `300 × 100 / 2.54 = 11811.0236…` — rounded once at a single boundary. The pinned value 11811 is right; the arithmetic description is wrong and would mislead the implementer's checklist-A self-certification. | Reword: one guarded `Math.Round` over double constants, single rounding boundary, cast guarded by range check. |
| W2 | **High — internal consistency** | Task 1.5 says "Encode a real R8.4-path render (text-free scene, host-free)". The R8.4 representative scene **carries text** — the R8.4 STATUS record rules fixture typography onto the committed scene, and `GoldenRasterRepresentativeTests` is `Category=FontProbe` precisely because the scene carries text. A text-bearing encode needs the pinned Aptos faces and is not host-free; a text-free scene is not "the R8.4 path". The task is self-contradictory as written. | Split: a routine host-free encode pin over a text-free scene, plus an optional `Category=FontProbe` representative-scene encode pin for the reference machine. |
| W3 | **Medium — design** | `PngExportBytes` carries `DotsPerInchX/Y` (300) — a second density representation beside the pinned 11811 px/m, contradicting the plan's own "zero duplication of `ExportSize` facts" maintainability claim (§6). DPI is an input concept; the file's density is pHYs. | Carry `Bytes` + `Dimensions` only, or carry the actual `PixelsPerMetreX/Y` (11811) that the validator re-checks. Never both concepts. |
| W4 | **Medium — correctness** | §4.2's patch arm says "insert a spec-ordered `pHYs` after `IHDR`" for the "wrong **or missing** density" outcome. If the encoder emits a pHYs with wrong values, insertion produces a **duplicate pHYs — an invalid PNG**. The tree conflates replace-in-place with insert. | The patch arm must branch: replace the existing pHYs in place when present, insert after `IHDR` only when absent. Add a positive test for the wrong-present case. |
| W5 | **Medium — hidden assumption** | The read-only-target arm is committed to `UnwritablePath` (§4.5) without probe backing. Whether `File.Replace` fails on a read-only destination is a Windows fact the plan itself treats as probe-worthy for the sharing violation but asserts here. | Mark the arm probe-dependent (0.3 must pin the read-only-destination outcome before the test asserts a typed refusal). |
| W6 | **Medium — consistency** | §4.6 says "an optional **internal** seam" while §5 shows `PngWriteSeam` as a **public** parameter of `Write`. The repo's injection precedent is public ([`SceneRasterRenderer.Render`](../src/GanttCreator.Raster/SceneRasterRenderer.cs) takes the public `PinnedFontSource?` at line 74); an internal seam would drag in `InternalsVisibleTo`, which no Raster file currently uses. | Make the seam public, matching the `fontSource` precedent; delete the "internal" wording. |
| W7 | **Low — process** | CP2 recommends running `verify-office.ps1` at R8.6 close as "the cleanest evidence trail" but does not name the defect it is working around: R8.6's evidence-command block still lists `verify-office.ps1 # Required` ([`R8.6-atomic-write-validator.md`](../docs/work-items/R8.6-atomic-write-validator.md) line 105) — residue of the pre-Revision-C wording that Revision C's own edit did not touch. The next reader will re-litigate this. | Name the residue; recommend the evidence-command line be revised in R8.6's own doc-update task so the guide and the ruling agree. |
| W8 | **Low — completeness** | The validator's "non-empty IDAT" check is undefined over multiple `IDAT` chunks (large encodes chunk `IDAT`; the patcher's "before first IDAT" is stated, the validator's summation is not). | Define the check over the summed length of all `IDAT` chunks. |
| W9 | **Low — completeness** | Encode determinism (same bitmap → identical bytes) is neither pinned nor explicitly waived. Full-digest pins would be brittle across SkiaSharp bumps; metadata-level pins are the right granularity — but the plan never says so, leaving the choice implicit. | State the deliberate granularity choice and its reason, or add a same-process determinism fact. |
| W10 | **Low — completeness** | Checklist K names "encode" and "metadata" injection points; the plan covers them only implicitly (input-contract positives, malformed-encoder-output arm). | Map those two K-points explicitly in §8.3 so the self-certification is traceable. |
| W11 | **Low — design nit** | `PngWriteOutcome` with nullable `Refusal`/`ActionableMessage`/`TechnicalRecord` invites consumer null-checking. The repo's failure-record style (R7.5's `PowerPointTransferFailure`) keeps message and record non-null on the failure arm. | Either two records (success/failure) or documented non-null guarantees per arm. |
| W12 | **Low — scope honesty** | Phase 3 adds `verify.ps1` at R8.6 close; the R8.6 work item's evidence commands list `verify-quick.ps1` only. Harmless branch hygiene, but the plan presents it alongside owed gates without labelling it discretionary. | Label it discretionary (the branch is not final until R8.8). |
| W13 | **Low — edge case** | The existence branch (Move for new, Replace for existing) has a check-then-act race: the target can appear between check and Move. The generic `IOException` mapping already makes the wrong guess fail cleanly and typed, but the plan never states the race or its clean-failure handling. | One sentence in §4.4: the race is accepted; a wrong guess is a typed failure, never a partial write. |

**Not findings (checked and cleared):** the validator's CRC recompute is a
deliberate, defensible superset of the architecture's four checks — the row's
own "corrupt" matrix arm cannot be caught by signature/dims/density/non-empty
alone, and the work item's D2 wording ("non-empty-IDAT/**decode** check")
anticipates exactly this strength; the plan should record the superset
decision in one line so a future reader does not mistake it for drift. The
7-unit decomposition matches the Raster project's fine-grained house style
(11 small files already). The synchronous model, the no-new-dependency
discipline, and the two-commit sequencing all conform to the binding guides.

## 4. The three owner checkpoints — adversarial assessment

**CP1 (J-section certification) — endorse.** The recommendation (certify E +
K, record J not-applicable) is not merely a preference; it is what the
authoritative sources already require. Checklist J's own scope line is "when
COM interop is touched" ([`08-TEST-CHECKLIST.md`](../docs/08-TEST-CHECKLIST.md)
line 172) — R8.6 touches none — and AGENTS.md forbids claiming certification
for sections that do not apply. The defect is in the work item's DoD line
("sections E, K, J"), not in the plan; the plan correctly reports the conflict
instead of silently picking. The one improvement: recommend the DoD line
itself be revised in R8.6's doc-update task, closing the discrepancy at its
source rather than leaving a standing doc/code mismatch — which checklist I
would otherwise flag.

**CP2 (verify-office timing) — adjust.** Both options are defensible, but the
plan's "run it anyway" recommendation spends ~20 measured minutes of live-host
time on a diff that **cannot** affect the Office suites: the AddIn does not
yet reference Raster (that reference is R8.8's), so no Office test even loads
the new code. The letter-of-the-guide reading exists only because of the W7
residue. The sharper recommendation: record `Not run` with the two-part reason
(Raster-only diff, no Office surface; the row's live case is owed to R8.8 per
Revision C) **and** fix the evidence-command line in the same doc update —
or, if the owner prefers belt-and-braces, run it, but then say it is
belt-and-braces, not "Required".

**CP3 (ADR vs work-item record) — endorse, with the alternative named.** The
recommendation matches precedent exactly: R8.3's hatch-rendering decision
(explicit clipped lines over `Create2DLine`) is the closest analogue — a
permanent rendering-strategy choice recorded in the work item and STATUS with
no ADR — while ADR-0070/0071 accompanied **new dependencies**, and the patcher
adds none. The defensible counter-argument the plan should state plainly: the
patch couples every future exported PNG's byte layout to the pinned encoder's
output shape, a permanent maintenance coupling an ADR would make harder to
forget. Both readings are legitimate; the owner's ruling is the mechanism, and
the plan's default (work-item record, ADR-0072 reserved for the stop path) is
the precedent-consistent one.

## 5. Edge cases and security review

- **TOCTOU on the existence branch** — see W13; acceptable once stated.
- **Crash-orphaned temp files**: a process crash between create and `finally`
  strands a random-named temp in the target directory. In-scope cleanup is
  impossible (random names cannot be distinguished from user files); the plan
  is silent. Record it as a known, accepted residue owned by R9.7's
  crash-recovery matrix consolidation rather than leaving it unstated.
- **Temp-file naming** (`Path.GetRandomFileName` + exclusive create) is the
  correct pre-create/symlink defence; no finding.
- **Concurrent exports to one target**: each write is independently atomic;
  last-wins is acceptable; unstated but harmless.
- **Long/trailing-dot paths**: typed failure mapping catches; no finding.
- **No schedule content in records**: held throughout; the success record
  carries path + dimensions only, matching R8.8 D1.

## 6. Maintainability

Sound overall: one CRC authority, one chunk reader shared by patcher and
validator, no `ExportSize` duplication (after W3), XML-doc and analyzer
discipline restated. The one real smell is W3's dual density representation;
W4's replace/insert branch is the one place where a literal reading produces
invalid output — both are cheap to fix now and expensive to discover in a
golden-image diff later.

## 7. Recommendation

**Approve with adjustments.** Fold W1–W6 into the plan before
implementation (W1 and W2 are correctness-level; W4 is the one that would
ship an invalid PNG if the probe lands on the wrong-density-present arm).
Record W7–W13 as plan edits or accepted-residue notes. Re-confirm CP1 and
CP3 as recommended; adjust CP2 per §4. No reject-level finding exists: the
plan violates no product invariant, no source-of-truth ordering, and no
stop condition, and its sequencing (probe → R8.5 commit → R8.6 commit)
matches both the roadmap order and the Phase-8 review's own dependency
graph.
