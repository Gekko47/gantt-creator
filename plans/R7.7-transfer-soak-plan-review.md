**Verdict.** The plan is contract-faithful on scope, exclusions, the gate split, the
Phase-8 upgrade and the evidence assembly, and its two headline corrections (the
already-landed Step-0 fixture fix; the third negated-filter surface) are confirmed
correct against live source. It is **not shippable as written**: two high-severity
defects would surface on the plan's own first execution (F1, F2), one gate-coupling gap
would turn the plan's Phase-1 validation red (F3), and several assertions are
under-determined in ways that invite flaky or silently-degraded evidence (F4, F5). All
corrections are prescribed below and have been applied to the plan in the same session.

Severity scale: **High** = wrong or unrunnable evidence, or a safety/ownership hazard ·
**Medium** = a gate breaks or an assertion degrades silently · **Low** = noise, cost, or
maintainability · **Info** = confirmed-sound, recorded to close the question.

## Findings

### F1 — HIGH severity, HIGH likelihood. The soak body has no "no pre-existing PowerPoint" pre-condition, so a user session can capture the run

`PowerPointFixture.Initialize` creates the host through
[`new PowerPoint.Application()`](../tests/GanttCreator.Office.IntegrationTests/PowerPointFixture.cs:133)
— the PIA co-class construction, which **returns the running instance when PowerPoint is
already open** (the work item's own Step-0 text documents this COM behaviour for
`Activator.CreateInstance`, and `new Application()` is the same call). The fixture's
ownership model then correctly does the safe thing —
[`AdoptOwnedProcesses`](../tests/GanttCreator.Office.IntegrationTests/PowerPointFixture.cs:934)
finds no new PID, `_startedByUs` stays `false`, and `DisposeAsync` never quits the user's
host. But the *soak's transfers* are not fixture-owned: `PowerPointTargetResolver` resolves
the **active** deck, which on a user's running PowerPoint can be the user's deck. The soak
would then paste onto and delete from a user deck, or — when the fixture's
`Presentations.Add` window happens to be active — pass every assertion while measuring the
wrong host and leaving the user's PowerPoint running with fixture-created decks. Either way
the recorded evidence does not measure what the record claims, and the run is
nondeterministic in exactly the dimension the soak exists to control.

The repository already solved this: the R7.2 gate opens with
[`WaitForNoPowerPointAsync`](../tests/GanttCreator.Office.IntegrationTests/PowerPointTargetDecisionIntegrationTests.cs:397)
(poll with deadline, refuse otherwise) precisely because the absent/attach cases need a
proven zero-host start. The plan omitted it.

**Correction (applied).** The soak body opens with the same wait-for-zero-`POWERPNT`
poll and refuses to start with a message naming the blocker; the same poll runs between
Arm B iterations so each fresh start provably begins from no host (this also closes the
attach-to-a-dying-host race between dispose and re-initialize). The script header
documents the close-user-Office reference-machine discipline.

### F2 — HIGH severity, HIGH likelihood. The manifest assertions are unrunnable in the plan's own Phase-2 measured run (internal contradiction)

The plan's Phase 2.3 end-state asserts "the manifest contains every PowerPoint PID the
fixture started", and Phase 2.4 executes the measured run through the raw
`dotnet test --filter "Category=TransferSoak"` route. But
[`OfficeFixture.RecordOwnedProcessId`](../tests/GanttCreator.Office.IntegrationTests/OfficeFixture.cs:1312)
is a **no-op unless `GANTTCREATOR_OWNED_PIDS_PATH` is set**
([`OfficeFixture.cs`](../tests/GanttCreator.Office.IntegrationTests/OfficeFixture.cs:1316)),
and that env var is set by [`verify-office.ps1`](../scripts/verify-office.ps1:389), not by
a bare `dotnet test` invocation. The same holds for `GANTTCREATOR_FORCED_KILLS_PATH`
([`verify-office.ps1`](../scripts/verify-office.ps1:397)). As written, the first measured
run either fails the manifest assertion for a harness reason (a non-defect red) or — worse
— the assertion is quietly skipped and the acceptance line "the manifest contains every
PowerPoint PID the fixture started" is evidenced by nothing until Phase 3.

**Correction (applied).** The body records `manifestArmed=true|false` from the env var and
asserts manifest content only when armed; the script arms **both** env vars and fails
closed when a run reports unarmed (the exit-5 discipline — an unmeasured signal is not a
zero signal); Phase 2.4's measured run sets both env vars by hand so the pre-script route
still produces the full record.

### F3 — MEDIUM severity, HIGH likelihood. The filter-extension commit must also update `ci-parity.Tests.ps1`'s pinned strings, which the plan did not name

[`ci-parity.Tests.ps1`](../scripts/ci-parity.Tests.ps1:722) and
[`ci-parity.Tests.ps1`](../scripts/ci-parity.Tests.ps1:734) pin the **exact** current
filter strings `--filter 'Category!=OfficeIntegration'` in `test-non-office.ps1` and
`verify.ps1`. Extending the filters without updating these pins turns the Pester gate
(`verify-quick` step 7 and the CI "Script lint (Pester)" step) red on the plan's own
Phase-1 validation — and an implementer who does not know the pins are deliberate could
"fix" the red by reverting the filter, which is precisely the D4 regression the split
exists to prevent.

**Correction (applied).** Phase 1's file list now names
[`ci-parity.Tests.ps1`](../scripts/ci-parity.Tests.ps1) explicitly: update the two pins to
the extended strings in the same commit. The W8 anti-inline tripwire
([`ci-parity.Tests.ps1`](../scripts/ci-parity.Tests.ps1:128)) is unaffected — the plan
correctly never inlines a test command into `ci.yml`.

### F4 — MEDIUM severity, MEDIUM likelihood. No mechanical pin against the D4 double-tag defect

D4: "A soak body that also carries `OfficeIntegration` is a defect (it would enter the
780 s gate)." xUnit permits multiple `[Trait("Category", …)]` attributes, and the
categorization is per-test only — **verified: there is no assembly-wide category
application** ([`tests/Directory.Build.props`](../tests/Directory.Build.props:68) is a
comment convention, not a mechanism; no `[assembly:]` trait or discoverer exists in the
integration project). So the double-tag hazard is a human-error class the plan asserted
against but did not mechanically pin. The routing prompt
[`.github/prompts/office-integration-test.prompt.md`](../.github/prompts/office-integration-test.prompt.md:11)
actively teaches the wrong route for soak bodies ("The test is tagged
`[Trait("Category", "OfficeIntegration")]`").

**Correction (applied).** A static Pester pin (the comment-stripped
[`verify-office.Tests.ps1`](../scripts/verify-office.Tests.ps1:68) pattern) asserts the
soak file contains `[Trait("Category", "TransferSoak")]` and does not contain
`OfficeIntegration`; the prompt gains a routing note for soak bodies (Phase 6.4).

### F5 — MEDIUM severity, MEDIUM likelihood. `WorkingSet64` as a gated max−min trend is the weakest leak signal and a flakiness source

D1 requires *recording* both counters and a "flat within a recorded tolerance" trend. The
plan gated both. Windows working set is OS-trimmed and can swing by tens of MB on a UI
application like PowerPoint; a max−min bound over 15 samples is tripped by a single trim,
and a genuine monotonic leak can hide under trimming. A healthy run fails (flaky gate) or
the tolerance gets widened until it is meaningless — the exact failure mode the
repository's own gate history (the retired absolute forced-exit ceiling) documents.

**Correction (applied).** The **gate** is the handle-count trend; `WorkingSet64` is
recorded with a coarse measured tolerance and a robust statistic (first-third vs
last-third medians), and a working-set failure routes to profiling rather than an
automatic red. The work item's wording is satisfied — it names the counters to record and
a recorded tolerance, not which counter carries the verdict.

### F6 — LOW severity, MEDIUM likelihood. The mid-phase "routine count unchanged" check was under-specified and expensive

The plan asked for "the routine `dotnet test --filter "Category=OfficeIntegration"` count
unchanged" as a Phase-2 validation — a ~20-minute full live suite for a fact the
phase-exit gate (7.2) proves anyway.

**Correction (applied).** The cheap mid-phase proof is
`dotnet test --list-tests --filter "Category=OfficeIntegration"` naming no soak body; the
authoritative proof stays at phase exit.

### F7 — LOW severity, MEDIUM likelihood. Arm B's ten host churns are heavier than the work item's "some" and race a dying host

Each fresh iteration pays a PowerPoint start (~2–5 s) and a teardown that polls up to 10 s
before killing
([`PowerPointFixture.EnsureOwnedProcessesExitedAsync`](../tests/GanttCreator.Office.IntegrationTests/PowerPointFixture.cs:1021));
ten cycles inflate the measured deadline and — without F1's between-iteration zero-host
poll — the next `new Application()` can race the previous process's shutdown and attach
to the dying instance, silently degrading `_startedByUs` and the arm's ownership
assertions.

**Correction (applied).** The between-iterations zero-host poll (from F1) makes each
fresh start deterministic; the arm-mix open question now offers the owner a five-iteration
trim that carries the same lifecycle-churn evidence at half the wall time.

### F8 — LOW severity, LOW-MEDIUM likelihood. The plan did not state that `PowerPointFixture` teardowns write no forced-kill records

The forced-exit histogram reads `GANTTCREATOR_FORCED_KILLS_PATH`, written only by
`OfficeFixture` teardowns; `PowerPointFixture.DisposeAsync` kills its owned processes
without writing a record (its kills are the sweep's territory). The soak has exactly one
`OfficeFixture` teardown, so the script's histogram will show one record — an implementer
unaware of this could misread a small histogram as a broken handoff and "fix" it wrongly.

**Correction (applied).** The script phase states the histogram's scope explicitly.

### F9 — LOW severity, LOW likelihood. `Process.HandleCount` availability asserted, not verified

The plan's B.3 claims the wrapper without the repository's own verify-before-relying step.
`Process.HandleCount` is `[SupportedOSPlatform("windows")]` and present on modern .NET, but
the claim should be checked against the installed `net10.0-windows` SDK metadata with a
recorded fallback (a direct `GetProcessHandleCount` P/Invoke in the test project).

**Correction (applied).** Phase 0.4 verifies the API and records the fallback decision
before Phase 2 depends on it.

### F10 — LOW severity, LOW likelihood. The "existing user PowerPoint" wording needs its interpretation stated, not implied

The work item scope says "some against an existing user PowerPoint"; the plan arranges the
R7.6 body-1 simulation (fixture-owned host, on-disk deck, unsaved marker —
[`SendToPowerPointIntegrationTests.cs`](../tests/GanttCreator.Office.IntegrationTests/SendToPowerPointIntegrationTests.cs:44)).
That is the only non-destructive arrangement available to an automated gate and the R7.6
owner accepted it for identical wording — but an exit review could otherwise accuse the
evidence of quietly redefining the row.

**Correction (applied).** The interpretation is now stated in the arm description, with
the real-user-session check named as the owner's exploratory step.

## Confirmed-sound (Info) — questions this review closed with evidence

1. **Filter grammar.** `Category!=OfficeIntegration&Category!=TransferSoak` is valid
   VSTest filter syntax (`&` = AND; `!=` supported on trait properties). Per-category
   semantics verified: a `TransferSoak`-only body is excluded by both conditions'
   combination, a non-categorized test still runs, an `OfficeIntegration` test stays
   excluded.
2. **No assembly-wide category application.**
   [`tests/Directory.Build.props`](../tests/Directory.Build.props:68) documents the
   convention only; traits are per-test attributes. A `TransferSoak`-tagged test cannot
   implicitly carry `OfficeIntegration`. (The stale "every test is tagged" sentence in
   [`test-non-office.ps1`](../scripts/test-non-office.ps1:31) is corrected by the plan's
   Phase 1.)
3. **Mutation gate.** [`Get-ChangedCoreFiles`](../scripts/mutation-gate.ps1:348) selects
   only `src/GanttCreator.Core` diffs; an empty changed set skips Stryker and passes "on
   that fact" ([`mutation-gate.ps1`](../scripts/mutation-gate.ps1:593)). A test/docs-only
   row is judged correctly — the plan's claim is confirmed, not assumed.
4. **Coverage thresholds.** [`verify.ps1`](../scripts/verify.ps1:186) collects coverage
   under the negated filter and step 13 merges per-project cobertura files. The soak never
   contributed to that collection, so excluding it changes no threshold. Had the filter
   *not* been extended, the soak would have entered the coverage run and silently shifted
   the Office project's numbers — one more reason the Phase-1 extension is load-bearing.
5. **CI behaviour.** [`ci.yml`](../.github/workflows/ci.yml:5) excludes all Office tests
   by policy; there is **no CI matrix** — a single `windows-latest` job. The compatibility
   matrix subset is therefore reference-machine evidence by construction, matching the
   work item's "no CI-hosted soak" exclusion. The only CI surfaces R7.7 touches are the
   shared filter script and the Pester suites, both via the W8 delegation rules
   ([`ci.yml`](../.github/workflows/ci.yml:151)).
6. **Pester sibling pattern is CI-safe.** [`verify-office.Tests.ps1`](../scripts/verify-office.Tests.ps1:10)
   drives a stub `dotnet.cmd`, never a real test run — the soak sibling can copy this
   shape, so no Pester case will ever invoke a live Office gate in CI.
7. **The stale-seed supersession is correct.** The typed fixture, the adoption model and
   the manifest write are landed
   ([`PowerPointFixture.cs`](../tests/GanttCreator.Office.IntegrationTests/PowerPointFixture.cs:943));
   the work item's two stale ledger seeds are correctly marked superseded by the plan.
8. **Tier arithmetic.** 50 Tier A + 9 Phase-8 guides = 59 Tier A; 55 − 9 = 46 Tier B.
9. **Determinism and isolation posture.** `xunit.runner.json` disables assembly and
   collection parallelization; the fixtures' PID+start-tick identity checks make the
   counters immune to PID recycling; the pre-condition (F1) removes the last
   nondeterministic input (an accidental user host).

## Overengineering and simplification assessment

- **Proportionate:** the `SoakCounters`/trend-evaluator split (required by the
  validator-positive-test rule), the dedicated script over the `-IncludeSoak` switch (the
  work item's primary option, and the repo's one-gate-per-concern layout), the Pester
  sibling (repo convention for every gate script).
- **Trimmed by this review:** the mid-phase routine-suite re-run (F6); the option of five
  fresh iterations instead of ten (F7, owner's call); per-phase timing fields are
  diagnostics-only and may be reduced to per-iteration totals if the first run shows they
  buy nothing.
- **Not overengineering:** the 25-iteration single `[Fact]` — the trend across iterations
  1→25 is one measurement, and per-method teardown would destroy the long-lived-host
  series the trend depends on.
