# ADR-0020 — The application-state scope covers five settings, not six

- **Status**: Accepted
- **Date**: 2026-09-27
- **Context**: R4.2's application-state scope exists to save and restore the Excel settings a rendering command must not leave changed. The architecture contract (`AGENTS.md` and `docs/02-ARCHITECTURE.md` "C# and architecture conventions") named six: `ScreenUpdating`, `EnableEvents`, `DisplayAlerts`, the **calculation mode**, the status bar, and the selection. R4.2's Required Office gate then found that `Application.Calculation` cannot be used at all on the reference host. Every access raises `COMException 0x80020005 (DISP_E_TYPEMISMATCH)`, confirmed over two full gate runs on 2026-09-27, and on **both** access forms: the `Application` coclass and the `_Application` interface (the PIA declares the member only on the interface, so the interface is not a workaround). The member is correctly typed `XlCalculation`, read/write, with a virtual setter and three defined values, so this is a COM-marshalling defect on that Office build (`O365HomePremRetail` 16.0.20326.20158, x64) rather than a call-shape error. `Calculation` is one of **19** enum-typed members on `_Application` (`ReferenceStyle`, `WindowState`, `DefaultSaveFormat`, `AutomationSecurity`, `Cursor`, `CutCopyMode`, ...), so a late-bound `InvokeMember` workaround is a spike with a wider blast radius, not a local fix. Three options were put to the product owner; the owner chose (a) drop calculation mode and record the amendment.
- **Decision**:
  - **D1 — The scope covers five settings: `ScreenUpdating`, `EnableEvents`, `DisplayAlerts`, the status bar (`DisplayStatusBar` and `StatusBar`), and the selection.** The calculation mode, the `GanttCalculationMode` enum, the `SetCalculationMode` method, its two test seams, and the interop mapping helpers are removed rather than left as dead code that reads as a supported contract.
  - **D2 — The amendment is scoped to rendering, not to the product.** The rationale is that **R4.9's render step writes shapes and never cells** (R4.9 D1: read, validate, build the scene, then render R4.5-R4.7), so a calculation-mode change has no consumer in the first live slice. A future command that **writes cells** must reinstate it, and must do so with a probed path on each supported Office build, not by re-adding this code. The setting was dropped because nothing needed it, not because it is unimportant.
  - **D3 — The change is recorded, not silent.** `KNOWN-LIMITATIONS` L17 moves from `_unassigned_` to closed-by-this-ADR, and the R4.2 work item, the manifest, the entity-guide-adjacent architecture text, and STATUS all state that the contract is five settings and why.
  - **D4 — AMENDED 2026-10-01: the scope still covers five settings, but the Refresh path does not use all five.** `GanttRefreshOrchestrator` used to call `SuppressStatusBar()` and then `SetStatusBarText(...)`. `DisplayStatusBar` and `StatusBar` are two distinct Excel properties — visibility and text — so hiding the bar and then writing into it produced a message that was set and correctly restored but **never seen**. `DisplayStatusBar` is no longer suppressed by Refresh; the progress text is still written, and whether the user sees it is decided by their own Excel setting. A user who keeps the status bar hidden is not shown one for the duration of a refresh. `SuppressStatusBar` remains on `IApplicationStateScope` and is still implemented, captured and restored; this narrows **which members one caller invokes**, not what the scope supports, so the five-setting contract and its capture-on-change guarantee are unchanged. Pinned by `The_application_state_is_suppressed_and_restored_on_success`, which asserts both that the text is set and that visibility is not touched.
- **Consequences**: `docs/02-ARCHITECTURE.md` and `AGENTS.md` are amended to name five settings instead of six, so the always-loaded contract matches the code. The D1 capture-on-change, D2 restore-resilience, and D3 selection-last guarantees are unchanged and still tested at each of the five settings (checklist K). Two defects surfaced while making the change and are fixed here: the contract test that injected a failing restore had to stop asserting that the *failing* member was restored, because it is now precisely the member that stays unrestored, and that assertion is stronger for it; and the obsolete "undefined calculation mode is refused" test was removed rather than left passing vacuously. The host defect itself is unchanged and still true: a future row that needs calculation mode will hit the same `DISP_E_TYPEMISMATCH`, and L18-style evidence should be gathered before any reinstatement.
- **Alternatives considered**: (b) spike a late-bound `InvokeMember` read/write path (rejected for this row - unbounded across 19 enum members, delays R4.9, and has no consumer); (c) a weaker substitute such as `Application.Calculate` or a versioned key-press (rejected - it cannot *read* the current mode, so D1 capture-on-change is impossible for that property, which is a correctness regression, not a trade-off).
