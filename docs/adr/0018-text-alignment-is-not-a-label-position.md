# ADR-0018 — Text alignment is its own type, not a label position

- **Status**: Accepted
- **Date**: 2026-09-26
- **Context**: R3.11 step 2 (`PanelBuilder`) could not be written. Entity guide §4 requires header cells to be "centred unless the schema defines left alignment for `Description`", but no centred value existed: `SceneText.Alignment` and `SceneStyle.Alignment` were both typed `GanttLabelPosition`, whose members are placements (`Auto`, `Inside`, `TopLeft`, `PlotCentre`, …) and which has no `Centre`. One enum was answering two unrelated questions — *where does the label box sit* and *how does the text sit inside the box the scene already resolved* — and the reuse was not merely a naming wart. It had produced four distinct wrong values at four call sites: `FrameBandsBuilder` passed `Auto` for the chart title, year bands, and period bands (§2 says the title is "horizontally centred"); `LabelPlanner` passed the raw chosen `position` through as the alignment; `LabelPlanner` also read `SceneStyle.Alignment` as a *position* default for the delay cascade; and `DelineatorBuilder` alone used it as a genuine text alignment. ADR-0013 recorded the scene-snapshot format as changeable only before a committed golden baseline exists, and R3.12 creates that baseline. R4.4, the Phase 4 Office consumer, states the rule this change follows: "Alignment cannot be expressed for a scene alignment member → stop; extend the scene contract via the scope-change protocol, not a renderer workaround."
- **Decision**:
  - **D1 — A closed `GanttTextAlignment` enum with `Left`, `Centre`, `Right`.** Not open-ended: adding `Justify` would be a guide amendment plus an ADR, as with every other closed enum here. Values are numbered `0`–`2` so the snapshot stays compact, matching `PanelColumnAlignment`'s prior numbering.
  - **D2 — Retype `SceneText.Alignment` and `SceneStyle.Alignment`.** Both become `GanttTextAlignment` (non-null) and `GanttTextAlignment?` (nullable) respectively. The snapshot writes the numeric value, so the wire format is unchanged in shape; only the meaning of `0` moves from `None` to `Left`, which is why this must land before R3.12's golden baseline rather than after. `SceneSnapshot` now rejects an undefined value as "Invalid text alignment" instead of "Invalid label alignment".
  - **D3 — The label *position* default gets its own member.** `LabelRequest.StyleDefaultPosition` (default `GanttLabelPosition.Inside`) replaces reading a position out of `SceneStyle.Alignment`. This is the fix for the conflation at its source: a style may now carry a text alignment and a request may carry a position, and neither has to impersonate the other. `LabelRequest` takes the new member last with a default, so no existing positional call site breaks.

  - **D4 — §22 label text alignment is a product decision, not a reading of the guide.** §22 fixes label *box* geometry but never states how text sits inside that box. The product owner decided on 2026-09-26 that text hugs the shape — the §24 rule generalised: a label placed to the shape's `Left` is `Right`-aligned so it terminates against the edge, a label placed to the `Right` starts at that edge, and `Inside`/`Above`/`Below` — all centred placements per §22 — are `Centre`. `LabelPlanner.TextAlignmentFor` encodes exactly this. **This is the one member set in this ADR that is inferred rather than read from a section, and it is flagged as such in the code comment and pinned by test.** It is also the input R4.4's D3 mapping table needs.
  - **D5 — `PanelColumnAlignment` is removed, not kept as an alias.** The R3.11 step-1 input model introduced a panel-local `Left`/`Centre`/`Right` enum. Keeping it would leave two identical enums in `GanttCreator.Core.Scene`, and `PanelBuilder` would need a conversion that could drift from the scene's own vocabulary. `PanelColumn.Alignment` now takes `GanttTextAlignment` directly, so a measured column's alignment flows into the emitted `SceneText` with no conversion. This is a deliberate API change to a model landed in `d763e67`; no consumer exists yet, which is why it is cheaper now than later.
  - **D6 — Unreachable positions throw; they do not silently default.** `TextAlignmentFor` lists every `GanttLabelPosition` member and ends in `_ => throw new ArgumentOutOfRangeException`, matching the repository's exhaustive-switch convention (`BandSequence`, `SceneSnapshot`, `GanttDateDisplayFormat`). The trailing throw guards unnamed values from a malformed cast; `LabelRequest.ResolvedPosition` is already refused as `InvalidPosition` before planning, so it is unreachable. A silent `Left` fallback would have hidden a future position member's misalignment.
- **Consequences**: §2's centred title, §4's centred header, and §22's labels are each now expressible, and R3.11 step 2 can be written without a workaround. Two producers change behaviour, not just type: `FrameBandsBuilder`'s three band/title texts move from a meaningless `Auto` to `Centre`, and `LabelPlanner` now emits a real alignment. Both are newly pinned — the prior 804-test suite passed with these two defects present, which is itself the finding. R4.4's Step 0 and D3 must be read against the new member set; its mapping table is not yet pinned (R4.4 is Tier B, upgrading at Phase 3 exit), so authoring it against `GanttTextAlignment` is the intended order. The snapshot's `alignment` field keeps its name and numeric shape, so no reader or writer outside `SceneSnapshot` changes.
- **Alternatives considered**: add `Centre` to `GanttLabelPosition` (rejected — it entrenches the conflation by placing a text-alignment value beside `Inside` and `PlotCentre`, and every future caller would be free to make the same mistake); ship `Left`/`Right` only (rejected — a visible §4 violation, since the data-panel header must be centred); have `PanelBuilder` compute centre by offsetting the text bounds instead of declaring an alignment (rejected — the scene owns geometry and the renderer consumes it; an offset hack would put centring policy in a primitive nobody else can see); leave `SceneStyle.Alignment` typed `GanttLabelPosition` and only retype `SceneText` (rejected — it would leave the delay-cascade position default still riding on a text-alignment field, preserving the conflation at its only remaining site).
