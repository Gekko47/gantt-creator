# ADR-0017 — Shared scene ownership for deduplicated entities

- **Status**: Accepted
- **Date**: 2026-09-26
- **Context**: Entity guide §24 requires that same-date delineator lines "are drawn once per resolved line style when identical", and the R3.10 guide's D4 requires that the surviving line record **both** owning rows. ADR-0013 gave `SceneOwnerId` exactly two closed kinds — one `GanttRowId`, or the reserved chart owner — so a line contributed to by two rows had no truthful representation, and `SceneGroup` does not help because it also carries a single owner. R3.10 is the first Phase-3 row to need shared ownership. ADR-0013 also recorded that the scene-snapshot format may still change "before a committed golden scene baseline exists"; R3.12 creates that baseline, so this decision had to be made before R3.10 rather than deferred.
- **Decision**:
  - **D1 — A third closed kind, `SceneOwnerKind.Rows`.** It carries an ordered, de-duplicated set of `GanttRowId` values. Ownership is then truthful by construction: a shared line is deleted exactly when its last contributing row goes, and survives while any of them does. This amends ADR-0013's two-kind model; ADR-0013 remains otherwise in force.
  - **D2 — Canonical encoding, and one spelling only.** `Value` is the distinct row IDs sorted Ordinal and joined with `|` — the separator ADR-0007 D6 already uses for the catalogue hash, and a character a `GanttRowId` (`G-` plus 32 lowercase hex digits) can never contain. `ForRows` requires **at least two** distinct IDs and always sorts and de-duplicates its input, so two spellings of the same set cannot exist. A one-element set is a `Row` owner, not a `Rows` owner; representing both would put the same ownership in the snapshot two ways.
  - **D3 — Parsing is strict, not lenient.** `TryParse` accepts a `rows` value only when every part is a well-formed ID, there are at least two, and they are already strictly ascending. Non-canonical text is refused rather than normalised, because a lenient parse would let a hand-edited snapshot carry an ordering the builder can never produce, and the golden snapshot is compared byte-for-byte.
  - **D4 — Primitive IDs are membership-sensitive.** `ScenePrimitive.CreateId` already derives from `ownerId.Value`, so a shared line's ID contains the full sorted set: `idA|idB:delineator`. Membership changes therefore change the ID, and R4.7 reconciliation removes the stale shape and creates the current one instead of mutating an ID in place. A single-row line's ID is unchanged from ADR-0013.
  - **D5 — The chart owner is unaffected.** A `Chart` owner has no rows and stays the reserved single value; `Chart` and `Row` semantics are untouched.
- **Consequences**: The scene-snapshot format gains a third owner kind before any golden baseline exists, which is the cheapest moment to do it. `SceneSnapshot.ToOwner` must switch on the kind rather than comparing to `Row` — a ternary would silently serialise a shared owner as `chart`, so the kind mapping is exhaustive by construction. `OwnedRows` gives renderers and the future R9.4 repair logic one accessor for "which rows own this" instead of each re-deriving it. R3.14's equivalence test gains a stronger assertion: a shared primitive's ownership field is complete, not nominal.
- **Alternatives considered**: assign the shared line to the first row in deterministic order and record the rest elsewhere (rejected: the scene would assert something untrue, and R3.14 exists to catch exactly that class of gap; a `SceneWarning` is a user-facing, sorted, de-duplicated validation message and is the wrong carrier for machine state); collapse identical lines in the renderer (rejected: the scene-first rule and §23's "never infer per renderer" both forbid it); one primitive per row (rejected: it is the same renderer-side collapse, and it duplicates the visible line); a non-empty `Rows` kind (rejected: it duplicates the `Row` kind and breaks snapshot canonicality); a `|`-free delimiter (rejected as unnecessary — the ID alphabet excludes every plausible alternative, and `|` keeps one separator in the repository).
