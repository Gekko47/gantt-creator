## Design decisions (D1 needs a human nod; D2–D5 follow repo contracts)

- **D1 — Canonical type per command (recommendation; confirm at review).**
  Add activity → `As-Planned Activity`; Add milestone →
  `As-Planned Milestone`; Add delineator → `Delineator` (the only
  delineator type). Rationale: planned-first authoring matches the
  Phase 5 exit workflow; the user can change `Type` afterwards via the
  R2.9 dropdown. The entity guide defines no per-command type mapping —
  this decision fills that gap; the user's explicit R2.8 implementation request confirms it.
- **D2 — Insertion position: append to the table body end.** One
  `ListRows.Add`, deterministic, independent of selection (the selection
  service is R5.2; selection-relative insertion would make today's
  mutation non-deterministic). This is the contract the roadmap's
  "insertion position" acceptance names.
- **D3 — Default row content (all 14 columns, exact).** `Id` =
  injected-generator `GanttRowId` (never blank — identity is generated
  once, per R2.3); `Type` = canonical display name (D1); `StyleKey` =
  the catalogue `DefaultStyleKey` for that type; `LaneId`, `StackIndex`,
  `Description`, `Start`, `Finish`, `ParentId`, `LabelPosition`,
  `FillColour`, `StrokeColour`, `SortOrder` = blank (blank
  `LabelPosition` resolves to `Auto`; blank `Visible` means visible —
  verify both blank semantics against the entity guide "Required
  worksheet fields" at Step 0). The row is intentionally a scaffold:
  validation flags missing dates/lane until the user fills them —
  correct behaviour, not an error to mask.
- **D4 — Bulk single write.** The row is written as one 1×14 `Value2`
  assignment through a `Range` local (mirroring the reader's bulk read);
  no per-cell COM round-trips, no chained access.
- **D5 — Success is silent; refusals surface one message.** Identical to
  R2.2's D7: the new row is self-evident. Refusal messages are
  actionable and contain no schedule content.

## Implementation evidence — blank-row correction, fix commit `75df937`

- The confirmed defect was reproduced in live Excel: a newly initialized table reported `ListRows.Count == 0`, `DataBodyRange == null`, and `Table.Range == $A$1:$N$2`; the first `ListRows.Add()` produced a populated row followed by an additional blank row.
- `ExcelGanttRowInserter` now reuses the final physical row only when `ListRows.Count == 0` and every cell in that row is blank. Existing non-empty tables retain the `ListRows.Add()` path.
- TypeOptions refusal deletes an appended row and clears a reused blank row, preserving the original table geometry on the initial-state path.
- Office contract tests: `GanttRowInserterTests` 9/9 PASS, including initial-row reuse, append behavior, header mapping, guard refusals, and both TypeOptions rollback paths.
- Live Office regression: `AddRowIntegrationTests` 3/3 PASS. The first insert leaves `ListRows.Count == 1`, `Table.Range.Rows.Count == 2`, and `DataBodyRange.Rows.Count == 1`; the three-command sequence leaves three body rows and no trailing blank row.
- No rendering, Refresh, dialog, edit/delete, selection-relative insertion, Type dropdown, migration, repair, or scene code was added.
- Fix commit `75df937` was created with pre-commit quick gates passing. Full repository gates remain pending.
