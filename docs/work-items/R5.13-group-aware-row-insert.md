# Work item — R5.13

> **Guide status**: Authored (Tier B — binding contract) 2026-10-13 ·
> Depends on: R2.8 (scaffold-row insertion), R5.3 (the parent/child
> model), ADR-0035 D3 (the positional insert), ADR-0036 (the genuine
> worksheet-row shift).

## Outcome

When a new row is inserted directly below an active cell that sits
inside a contiguous outline-group child run, the new row is assigned
that group's parent and the native outline is rebuilt, so the row
joins the group instead of landing top-level and splitting the run.
The native `-`/`+` controls reflect the new row's parent without
waiting for the next Refresh.

## Context

R2.8's insert is positional (ADR-0035 D3) but parent-blind: it places
the row below the active cell and writes the scaffold values, but never
consults the group structure. A row inserted below a group child
therefore landed top-level, splitting the contiguous child run and
leaving the native outline out of step with the table until the next
Refresh rebuilt it. The detection is deliberately read-only over the
same bulk-read body the inserter already materialises, so it cannot
regress the guarded-insert or call-count contracts.

## Explicit exclusions

- No schema change — `ParentId` already exists; the insert writes it,
  it does not add a column.
- No rendering — the native outline is rebuilt, but chart shapes stay
  Refresh-only (the inserter never renders).
- No change to the guarded-insert or call-count contracts — the
  detection reads the body through the same bulk-read seam and the
  regroup is one `Apply`; a refused positional insert still refuses
  before any read, write, or regroup.
- An append (active cell outside the table) stays top-level — there is
  no enclosing group to join.

## Design decisions

- **D1 — Detection reads the post-insert body.** After the row
  lands, the inserter reads the body and inspects the row above
  (the active cell) and the row below the new row. If the row
  above carries a `ParentId`, the new row inherits it (it joins
  that group). If the row above is top-level and the row below
  is its child, the new row becomes that parent's first child.
  Otherwise it stays top-level.
- **D2 — The regroup is one `Apply` of the projected body.** The
  native outline is rebuilt from the post-insert body through the
  shared `ExcelGanttRowProjection`, so the outline and the table
  cannot drift.
- **D3 — Append stays top-level.** An append has no active-cell
  neighbour, so there is no enclosing group to join.
- **D4 — A refused positional insert refuses before any read,
  write, or regroup.** The guarded-insert safety invariant holds
  even when an outline writer is attached: the refusal is raised
  before the body is read back, so no existing row is ever in
  scope for a write and the outline is never rebuilt.
- **D5 — An unparseable `Id` degrades, not fails.** If the
  projection cannot parse a row's `Id`, the insert stands (the
  row already landed) and the next Refresh rebuilds the outline —
  the pre-projection behaviour — rather than failing work that
  already succeeded.

## Acceptance tests

- `An_insert_below_a_group_child_joins_that_group_and_regroups` —
  both neighbours are children of `parent`; the new row inherits
  `parent` and the outline is rebuilt once, with the new row in
  the hierarchy it was handed.
- `An_insert_below_a_top_level_parent_becomes_its_first_child` —
  the active cell is a top-level parent and the row below is its
  child; the new row becomes that parent's first child.
- `An_insert_below_a_top_level_leaf_stays_top_level` — neither
  neighbour groups; the new row stays top-level.
- `An_append_stays_top_level_even_with_an_outline_writer` — an
  append stays top-level even when an outline writer is attached.
- `A_refused_positional_insert_with_an_outline_writer_never_reads_or_regroups`
  — the refused positional insert reads nothing, writes nothing,
  and regroups nothing.
