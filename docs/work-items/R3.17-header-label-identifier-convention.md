## Outcome

Every header-band label names its parent by appending `:label` to the parent's
identifier, so the year and period headers follow one convention and a year
label draws on top of its own band rather than beneath it.

## Context

R3.16's field table had to name a header label's identifier, and doing so
exposed a disagreement in the model itself. `FrameBandsBuilder` emitted the
period label as `$"{id}:label"` (line 245) but the year label as
`$"chart:year-label:{year}"` (line 218), so two header kinds named their parent
by different rules. Because a renderer reconciles on the shape name (R4.3 D2)
and the primitive identifier is the reconciliation key (R4.7), the
disagreement is a real hazard, not a style preference.

The rename also changed **z-order**, which is the more interesting half. Both
primitives are `ZLayer.Frame` with no lane, stack, or sort key, so the scene's
deterministic ordering falls through to an ordinal comparison of the
identifier. `'-'` (0x2D) sorts before `':'` (0x3A), so the old year label
ordered *before* its own background rectangle and would have drawn beneath it.
Under `chart:year:2026:label` the rectangle sorts first and the label draws on
top, which is the correct back-to-front order for a band and its caption.

## Design decisions

- **D1 — Normalise to `:label` on the parent, not a `-label` prefix.** The
  existing convention already has two users (the period header and the row
  description label's `{rowId}:label`), so the year label was the outlier.
  Rejected: renaming the period label to `chart:period-label:{date}`, which
  would have churned three identifiers instead of one and broken the one
  convention that already matched the row-label pattern.
- **D2 — The pin is convention-agnostic.** The test asserts that every `:label`
  text names a rectangle that exists, not that a literal string is used, so a
  future rename cannot silently break the relationship the test is protecting.
- **D3 — The regeneration and the code change ship together.** The golden
  policy asks for a dedicated baseline commit, but splitting them would leave
  the first commit with a failing golden comparison, and `AGENTS.md` requires a
  green commit. Bundling with the reason stated satisfies the intent — the
  baseline change is reviewable on its own in the diff — and keeps every commit
  green. The alternative (a knowingly red commit) was rejected.

## Implementation steps

1. Build the year identifier once in a local helper and append `:label` to it.
2. Pin the convention with a test that also proves the assertion is not
   vacuous by requiring a non-empty label set.
3. Correct the pre-existing header-label count, which had silently covered only
   the period labels because the year label used a different spelling.
4. Regenerate the golden snapshot by writing the real build output, not by hand
   patching, and verify the only difference is the one identifier.
5. Docs.

## Stop conditions (item-specific)

- The rename turns out to change more than the intended identifier and its
  order → stop and report; the baseline is a human-reviewed artefact.
- Any renderer or consumer of the identifier exists → stop; an identifier
  change is a compatibility decision, not a cleanup. None exists today, which
  is why this row is cheap now and expensive later.

## Risk and rollback

Main risk: the ordering change surprises a reviewer who expects a pure rename.
Mitigated by stating it explicitly and by the diff showing the swap. Rollback:
`git revert`, restoring both the identifier and the baseline.
