## Outcome

The delineator carries a **user-authored named style** whose `StandardOutlinePt` sets the line width; the chart-wide `DelineatorLinePt` metric is the fallback. The Delineator becomes a `RequiresStyleKey` type, so its `StyleKey` cell is honoured and a deleted/unknown style falls back to `DefaultDelineator`. The custom-style Width control (already present in the Theme dialog) now affects delineators. The corner label set remains the floor; a custom style may narrow within it but never offer span positions.

Type-dropdown creation, delete via the general Remove command (with its standard confirmation), and the `Start`-only date semantics all already existed. Nothing new is added to the ribbon, no dialog, no new column — the work is the rewiring that makes the delineator's width style-resolved like its dash already is.

## Design decisions (behavioural)

- **D1 — Delineator is a style-key type.** `requiresStyleKey: true` so its `StyleKey` cell is honoured. A blank `StyleKey` is a `StyleKeyRequired` blocking error. A deleted/unknown style falls back to `DefaultDelineator` via `GanttStyleResolver`.
- **D2 — Width from style, metric as fallback.** `StandardOutlinePt` > 0 wins; otherwise `DelineatorLinePt`. Built-in `DefaultDelineator` resolves from the token, so the built-in path is byte-identical.
- **D3 — Corner label set is the floor.** `GetAllowedLabelPositions` intersects the style's set with the type's corner set; span positions (`Left`/`Right`/`Inside`) are refused for a Delineator row.
- **D4 — No new UI.** Custom style dropdown keeps its `RequiresStyleKey` gate (Custom Activity/Milestone only). Delete is the existing `RemoveCommand` with ADR-0008 D3 confirmation.
