## Outcome

A lane-owning row's live lane has exactly its Excel row's Top, Height and Bottom;
managed row heights are normalised to `GanttRowHeightPt`; live lane auto-growth is
gone; Excel outline groups are rebuilt from `ParentId`; a projected child renders
on its parent lane and consumes no lane height.

## Design decisions

- **D1 — Auto-growth is removed outright.** `LaneLayoutBuilder` no longer computes
  a content-driven height, and there is deliberately **no "grow up to a maximum"
  fallback**: a capped lane is still a lane that disagrees with its row.
- **D2 — The worksheet is the source of vertical geometry; Core consumes it.**
  This is the inverse of the landed direction and extends the discipline ADR-0023
  and ADR-0024 already established for the panel upward to lanes.
- **D3 — Normalisation is the add-in's job**, on Initialise, on hierarchy
  mutation and on Refresh. A user who drags a managed row taller has it restored.
- **D4 — `GanttRowHeightPt` is the single authority** for both the Excel row and
  the Core lane. `LaneHeightPt` is gone, so there is no second minimum to
  contradict it.
- **D5 — Outline groups are rebuilt from `ParentId`**, never read as the
  relationship. Collapse/expand state is presentation and is preserved across
  Refresh.
- **D6 — A projected child creates no lane and no height.** Its shape uses the
  parent's measured lane geometry. When children cannot be kept legible, the
  scene **warns or refuses**; it never grows the lane.
- **D7 — `Splitter`/`Spacer` rows match their Excel row geometry** via
  `SplitterHeightPt`/`SpacerHeightPt` applied to both sides, so Core and the
  worksheet cannot disagree.
- **D8 — Measurement happens after outline state is known**, in this order:
  read hierarchy → repair/read outline → normalise heights → measure visible
  lane-owning rows → resolve projections → build scene.

## Acceptance tests

- **Automated** — `dotnet test tests/GanttCreator.Core.Tests`:
  - for every visible lane-owning row, lane `Top`/`Height`/`Bottom` equal the
    measured Excel row's, exactly
  - **the auto-growth test is deleted**; a new test asserts lane height is
    *unchanged* when content exceeds it, and that the documented warning is
    emitted (positive test)
  - a projected child creates no lane and no height
  - several children overlap one parent lane without growth
  - a collapsed parent still renders its children, with the lanes below moving up
  - outline groups are reconstructed from `ParentId` alone
  - **golden regeneration required** — this changes scene geometry. Human review,
    stated reason, and the regeneration ships in this commit per R3.17 D3.
- **Office host (Required)**: expand and collapse a parent with children and
  confirm the lanes stay aligned with the visible rows in **both** states. Record
  the host build.

## Step 0 — verify prerequisites

- **R4.7B must have landed**: a child needs a resolved render lane before lane
  geometry can be derived from the worksheet rather than from content.
- The growth code to remove is `LaneLayoutBuilder.cs:170`:
  `var laneHeight = Math.Max(metrics.LaneHeightPt, contentHeight);`
- `08-TEST-CHECKLIST.md` §B's auto-growth item was replaced in roadmap revision
  10; if this row lands before that edit, the checklist and the code disagree.
- `ExcelPanelGridMeasurement` already returns per-row heights (ADR-0023) and works
  on a protected sheet (ADR-0024). Reuse it rather than building a second
  measurement path.

## Stop conditions

- Exact row/lane equality proves unachievable on the host → stop and report with
  the measured values. A tolerance is a decision, not an implementation detail.
- Normalisation would require editing a row the add-in does not own → stop;
  ADR-0029's ownership boundary applies.

## Risk and rollback

Main risk: this is a **behaviour reversal**, so any test asserting growth fails and
must be deleted rather than relaxed. That deletion is intended and is the reason
this row needs human review. Rollback: `git revert`.
