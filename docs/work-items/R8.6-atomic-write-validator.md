## Design decisions (behavioural)

- **D1 — Temp-then-replace.** The file is written to a temporary path
  in the target directory, fully flushed, validated, then atomically
  replaced onto the target; the temp file is removed in `finally` on
  failure — a partial file never appears at the target path
  (**positive test**: an injected mid-write failure leaves the target
  untouched).
- **D2 — Validate before success.** The R8.5 byte-level facts are
  re-read from the written file (signature, exact dims, pHYs, and a
  non-empty-IDAT/decode check); only then is success reported — the
  never-report-success-without-verification rule, applied to files.
- **D3 — Distinct failures.** Unwritable path (the matrix row),
  locked target, disk-full-class write errors, and validator failures
  are distinct typed outcomes with actionable messages; each gets one
  technical log record (operation ID; no schedule content).
- **D4 — Existing-file policy.** Replacing an existing file at the
  user-chosen path is the explicit consequence of the user choosing
  that path (the dialog's contract); the atomic replace is the
  mechanism — recorded so no confirm-dialog duplication is invented
  here (the R2.7a policy applies to destructive *data* commands, and
  this is a file-save the user initiated).

## Acceptance tests

- **Automated — the failure matrix**: each injected failure
  (mid-write, locked target, invalid path, validator-rejecting bytes)
  → no partial target file + one typed failure + temp cleaned
  (**positive tests**); success path → validator-green + temp gone.
- **Office host (Required)** — live: the unwritable-path case from
  the compatibility matrix (read-only folder/permissions) plus a
  normal save; record host builds.

## Stop conditions (item-specific)

- Atomic replace is not atomic on the target volume/OS combination →
  stop; the fallback (validate-then-delete-on-failure) needs the
  human's nod and its own tests.
- Success could be reported before validation → stop (D2).
