- **PROBED 2026-09-27 against the installed PIA — all six properties are
  now facts, and the "which member carries the status bar" question is
  answered: it is two members, not one.** Reflection over
  `Microsoft.Office.Interop.Excel._Application` (ExcelDna.Interop 16.0.0,
  ADR-0004), every member read/write with a virtual setter:
  - `Application.ScreenUpdating` — `System.Boolean`, read/write.
  - `Application.EnableEvents` — `System.Boolean`, read/write.
  - `Application.DisplayAlerts` — `System.Boolean`, read/write.
  - `Application.Calculation` — `XlCalculation`, read/write, three
    defined values: `xlCalculationSemiautomatic`, `xlCalculationManual`,
    `xlCalculationAutomatic`.
  - **Status bar is two distinct properties, both read/write:**
    `Application.DisplayStatusBar` is `System.Boolean` (the visibility
    toggle) and `Application.StatusBar` is `System.Object` (the text).
    The guide's open question is therefore resolved as **both**: the
    scope captures and restores `DisplayStatusBar`, and separately
    captures and restores `StatusBar` (whose captured value is therefore
    `object?`, not `string`, and may legitimately be null).
  - `Application.Selection` — `System.Object`, **canWrite = false**.
    Selection restore therefore cannot be a property write: it goes
    through `Range.Select()`, which the PIA exposes as
    `Range.Select()` returning `Object` with no parameters. This
    confirms D3's "best-effort and ordered last" as a mechanical
    necessity rather than a defensive flourish, and it is why selection
    restore needs its own seam and its own injected-failure test.
  - `Application.Select` and `Worksheet.Select` do **not** exist on those
    interfaces; `Range.Select` is the only select member in play.
- `AGENTS.md` requires the scope to run on the STA/main thread; the
  scope must not marshal or offload.

## Design decisions (behavioural)

- **D1 — Capture-on-change.** The scope records each property's
  original value only when the command actually changes it; restore
  writes only what was captured. Unchanged properties are never
  touched (conventions list). **Probed 2026-09-27:** "status bar" is
  **two** read/write members — `DisplayStatusBar` (`Boolean`, the
  visibility toggle) and `StatusBar` (`Object`, the text) — so this row
  captures and restores both independently, and the captured
  `StatusBar` value is `object?` rather than `string`.
- **D2 — Dispose/`try/finally` equivalence.** The scope restores in
  `finally` semantics whether used via `using` or explicit
  try/finally; restore failure cannot skip the remaining properties.
- **D3 — Selection restore is best-effort and ordered last.** Selection
  restore can fail on edge hosts; it degrades with a logged technical
  record (operation ID) and never masks earlier restores. **Probed
  2026-09-27:** `Application.Selection` is read-only, so this is a
  mechanical necessity, not defensive polish — the restore path is
  `Range.Select()` on the captured selection range, which is a COM call
  that can be rejected and has no other write path.
- **D4 — Failure injection points.** Every property write is an
  injectable seam; the fake-state tests inject a failure at *each*
  point and assert full restoration of everything captured so far
  (checklist K).
