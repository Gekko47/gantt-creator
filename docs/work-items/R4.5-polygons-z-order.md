## Design decisions (behavioural)

- **D1 — Diamonds via freeform at exact points.** Four scene points →
  one freeform shape; geometry asserted point-for-point within the
  documented tolerance; name/tag per R4.3 D2.
- **D2 — Z-order = scene order, applied in one pass.** The renderer
  creates/updates in the scene's already-deterministic order and
  applies any reordering the host requires in a single deterministic
  pass derived from that order — never per-shape `BringToFront`
  calls, never host-default order.
- **D3 — Same-date and same-stack overlaps are visible and ordered.**
  The live gate inspects same-date milestones and same-stack bars:
  overlap rendering follows the scene's subtype/sort/ID order exactly
  (entity guide: reproducible without pretending overlaps do not
  exist).

## Notes during implementation

### Step-0 probe, 2026-09-28 — the freeform question is ANSWERED, and the obvious call shape is a SILENT trap

The guide's Step-0 obligation was to establish the freeform members and
their point semantics. Three probe rounds against Office `16.0.20326.20158`
x64, using a four-point diamond (100,90) (110,100) (100,110) and a plain
auto-shape rectangle at the same place as a control:

| Round | Call shape | Result |
| --- | --- | --- |
| 1 | three vertices in ONE `AddNodes`, boxed `Double` in the `Object` params | **degenerate**: `L=100 T=90 W≈0 H≈0`, no exception |
| 1 | the same with `Single` values | identical — the `Object` typing is **not** the cause |
| 2 | nodes relative to the builder start | wrong: `L=0 T=0 W=100 H=90` |
| 3 | **one `AddNodes` per vertex, only X1/Y1, `Type.Missing` for the rest** | **correct**: `L=100 T=90 W=10.000079 H=20.000078` |

Three findings, all of which change the implementation:

1. **The multi-vertex `AddNodes` overload fails SILENTLY.** It creates a
   degenerate shape at the right position rather than raising. A test that
   asserted only "a shape is at x,y" would have passed against a zero-size
   diamond, so the gate asserts the **tip-to-tip extent** as well as the
   position. This is the row's real risk, and it is why the guide's stop
   condition ("freeform point semantics differ from assumed") was correct to
   demand a probe.
2. **Coordinates are ABSOLUTE sheet points**, the same convention `AddLine`
   uses, so no offset from the builder origin is applied. One coordinate
   convention now covers every shape family.
3. **`msoEditingCorner` is chosen over `msoEditingAuto`** because it
   guarantees straight segments, so auto-smoothing cannot round a milestone's
   tips. The probe measured identical geometry for both on a straight-edged
   polygon; the corner form makes that equality structural rather than
   incidental.

### Superseded: the freeform path and its "separate tolerance" (2026-09-28)

The probe above is kept because its **finding is what changed the
implementation**, but the conclusion drawn from it was wrong and is
recorded here rather than quietly deleted.

**What was measured, and what it was first read to mean.** The host
reported a freeform's bounding box as `20.000078` for a diamond whose
scene points span exactly 20pt. That was read as "accumulated error in
the freeform builder", and a **1e-3pt** tolerance was introduced for the
freeform path with `GeometryMath.Epsilon` left governing the other
families. Commit `1106b99` records that reading.

**Both halves of that were wrong.** A follow-up probe measured the
error in EMU (1 EMU = 1/12700 pt) at five exact spans, against a plain
`msoShapeDiamond` at the identical box:

| exact span | freeform error | `msoShapeDiamond` error |
| --- | --- | --- |
| 10 | +1.005 EMU | **0.000 EMU** |
| 20 | +0.993 EMU | **0.000 EMU** |
| 37.5 | +1.017 EMU | **0.000 EMU** |
| 100 | +0.969 EMU | **0.000 EMU** |
| 253 | +0.969 EMU | **0.000 EMU** |

1. The error is **not accumulated**. It is a **fixed +1 EMU**, constant
   across a 25x range of sizes: `BuildFreeform` stores each vertex on a
   whole-EMU grid, so any freeform's span is off by at most one grid
   unit regardless of size. The "accumulated" wording in `1106b99` is
   incorrect.
2. **A milestone does not need a freeform.** Excel *derives* a diamond
   auto-shape's vertices from its `Left`/`Top`/`Width`/`Height` box
   rather than storing absolute vertices, so it never touches the EMU
   vertex grid — and it measured **exact at every span**.

**Consequences, which are the current contract:**

- `OfficeShapeKind.Polygon` (freeform) is replaced by
  **`OfficeShapeKind.Diamond`**, placed at the scene polygon's bounding
  box. The `AddFreeform` path is **deleted**, not left as dead code.
- **The second tolerance is deleted.** `GeometryMath.Epsilon` (1e-6)
  governs rectangles, lines, text, **and** milestones. The live gate now
  asserts `W=20 H=20` exactly and passes at 1e-6.
- A polygon that is **not** a symmetric axis-aligned diamond is
  **refused** with `SceneTranslationRefusalReason.NotADiamond`, not
  approximated. A rotated or skewed quadrilateral is not a diamond, and
  drawing it as one would silently change the resolved entity.
- An in-place diamond **update** is now expressible (it is just
  `Left`/`Top`/`Width`/`Height`), where the freeform's read-only vertex
  collection had made it impossible.

**The generalisable lesson.** The "unavoidable" limitation was a
property of the **API chosen**, not of the host. The first probe asked
"does freeform work?" and never asked "is freeform the only way to
place a diamond?" — the same mistake as ADR-0019's `Shape.Tag`, R4.4's
`xlAlign*` constants, and the multi-vertex `AddNodes` overload. A probe
that establishes a limitation should also establish that the limitation
is unavoidable.
