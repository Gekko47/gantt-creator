## D1 — the data panel's WIDTH is the sum of its measured columns

**The gap.** Two mutants survive in `LiveDataPanelBounds` (`src/GanttCreator.Core/Scene/SceneBuilder.cs`,
the method around line 844). It computes `left` from `grid.PanelLeftPt`, computes `right` as
`grid.OriginLeftPt` plus the **sum** of every column's `WidthPt`, and returns a rectangle whose width
is `right - left`.

- The sum mutated to a maximum survives.
- `right - left` mutated to `right + left` survives.

Both are real: `SceneBuilderTests.Grid(int rowCount)` builds **two** columns of 40 pt and 160 pt, so
the sum (200) and the max (160) differ, and a non-zero `OriginLeftPt` makes `right − left` differ
from `right + left`. Nothing asserts the panel rectangle's size, which is why both live.

**The work.** One fact in `tests/GanttCreator.Core.Tests/Scene/SceneBuilderTests.cs`:

1. Build a scene with `Grid(1)` and the existing `Request(...)` helper (one event is enough).
2. Find the data-panel primitive. Read `PanelBuilder` first: the panel is emitted with a style from
   `PanelTheme` and a primitive id owned by the panel, not by a row — grep `PanelBuilder.cs` for the
   id prefix it uses and assert on that prefix rather than hard-coding a literal.
3. Assert its `Bounds.Width` equals **200** (`40 + 160`, the two measured columns). That kills the
   `Max` mutant.
4. Assert its `Bounds.Left` equals the grid's `PanelLeftPt` and its `Bounds.Right` equals
   `OriginLeftPt + 200`. That kills the `right + left` mutant, and pins the gutter relationship the
   R5.18k work established.

State in the remark *why* two columns: a one-column grid makes `Sum` and `Max` identical and the
test would pass for the wrong reason.

**Expected observation.** `dotnet test tests/GanttCreator.Core.Tests/GanttCreator.Core.Tests.csproj -c Release --filter "FullyQualifiedName~SceneBuilderTests"` green, and a targeted Stryker run
over `SceneBuilder.cs` shows both mutants killed instead of survived.

## D2 — the null-versus-empty `Events` guard pair

**The gap.** Two mutants survive at `SceneBuilder.TryBuild`'s entry guard (around line 369), which
refuses a null event list and, unless `AllowEmptyEvents` is set, an empty one. Both logical mutations
of that guard survive, which means no test constructs the two states that tell them apart. There are
three distinct inputs and the batch's tests cover only one:

| `Events` | `AllowEmptyEvents` | Expected |
|---|---|---|
| `null` | either | the typed refusal for a null event list |
| empty | `false` | the typed refusal for an empty list |
| empty | `true` | a scene is built (this is the R5.18j empty-table path) |

**The work.** Read the existing `SceneBuildRequest` record and `SceneBuilderRefusal` enum for the
exact member names (do not invent them), then add three facts: null events refused, empty-and-not-
allowed refused, empty-and-allowed builds. The third may already exist — R5.18j relies on it — in
which case add only the two refusals and note that in the commit message.

**Expected observation.** Same filter as D1 green; the two `Logical mutation` survivors at the guard
line disappear from a targeted Stryker report.

## D3 — the live check that the ribbon paints the glyphs

**The gap.** The batch proved the callback returns an object on which `QueryInterface` for
`IPictureDisp` succeeds (`tests/GanttCreator.AddIn.Tests/LockGlyphImagesTests.cs`). What no
in-process test can reach is the step after that: Excel taking that picture and drawing it on a
toggle button or a dropdown item. Recording it as "closed" would be claiming an unobserved result.

**The work — a recorded manual pass, not code.**

1. `pwsh ./scripts/verify-quick.ps1` to publish the packed XLL, then open Excel, register the add-in
   from `src/GanttCreator.AddIn/bin/Release/net10.0-windows/publish/`, and run **Initialise**.
2. On the Sheet group, with the chart locked (default), confirm the Chart-lock toggle shows the
   **closed** padlock and the label reads "Chart locked"; unlock it and confirm the **open** padlock
   and "Chart unlocked". Do the same for the Cells toggle.
3. On the Columns group, open the dropdown and confirm a tick beside a visible column and a dash
   beside a hidden one, then hide `Description` and confirm the dash appears and the column goes.
4. Repeat at 150 % display scaling — the 32 px source is what keeps it crisp there.
5. Record the result as a `docs/STATUS.md` row: the Excel build (`verify-office.ps1` prints the
   ProductReleaseIds and VersionToReport), the date, what was seen for each of the two glyph
   families, and the phrase "live host, manual" so a later reader does not mistake it for a test.

If any glyph does not paint, the likely causes in order are: a resource name that does not end with
the suffix `RibbonImages` looks for; a callback name in `Ribbon.xml` that does not match a public
method on `GanttRibbon`; or a `getImage` arity that the binding rejects (the signature gate in
`RibbonCallbackSignatureTests` should have caught the last two, so suspect the first).

**Expected observation.** A STATUS row, not a green test. Do not add a test that asserts Excel drew
something — the honest automation ceiling here is what `LockGlyphImagesTests` already covers.

## D4 — retire one leaked COM chain, then lower the ceiling

**The gap.** `verify-office.ps1` passed at **exactly** its ceiling: 38 forced kills against a
ceiling of 38. Its own comment block records what that means — there is no sensitivity left, and the
next test body that leaves a proxy alive fails the gate for a reason unrelated to what it tests.

The per-body attribution printed by the last run is uniform: **35 bodies force exactly one kill
each, one body forces three** (`InitialiseSheetIntegrationTests.Initialise_preserves_a_cell_empty_
sheet_with_live_non_cell_state`), and `OfficeFixtureTests` bodies appear in the list too. A uniform
one-per-body cost is the signature of a *shared* chain released at teardown rather than one test's
local leak — which also means one fix retires ~35 of the 38.

**The work.**

1. Read `OfficeFixture.ComScope` and the teardown path (`OfficeFixture.cs`, and the
   `SuppressLeakSignal` flag while you are there) and find what is still alive at the moment the
   fixture forces a kill. The candidate is the last proxy the fixture itself holds — workbook,
   sheet collection, or the application's `ActiveWorkbook` — rather than anything a test body owns.
2. Fix the one chain: hold each proxy in a local and release it explicitly, per the COM ownership
   rule in `AGENTS.md`, or drop the reference the fixture keeps after teardown.
3. Re-run `pwsh ./scripts/verify-office.ps1` and read the signal. **Lower `LeakCeiling` to the new
   measured value in the same commit** and record the measurement and the date beside it, exactly as
   the existing 26 → 28 → 30 → 35 → 38 history does.
4. If the diagnosis takes more than two evidence-led attempts, stop and record what was measured —
   the bounded-retry rule applies, and a guessed fix here would hide a real leak.

**Expected observation.** `verify-office.ps1` PASS with a signal strictly below the ceiling it is
judged against, i.e. the gate has margin for the first time since 2026-10-11.

## D5 — the deadline rule, restated so it is not re-guessed

`verify-office.ps1` now uses `DeadlineSeconds = 780`, raised from 660 on 2026-11-14 **because the
suite grew past it**: the added round-trip test made the run exceed 660 s, the watchdog stopped it
with no trx produced, and that was the gate failing on its own clock rather than on a defect. The
first run under 780 measured **658 s — 122 s of margin**.

The rule, for whoever reads this next: raise `DeadlineSeconds` only with a fresh measurement, state
the measured duration and the cost (a real hang takes that much longer to surface), and never to turn
a red run green. If a future change pushes the suite past 780 s, add the measurement to the existing
comment block rather than replacing it — the history in that block is what stops the deadline being
inflated by habit.
