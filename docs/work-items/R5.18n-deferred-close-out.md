## D1 — the data panel's WIDTH is the sum of its measured columns

**The gap.** Two mutants survive in `LiveDataPanelBounds` (`src/GanttCreator.Core/Scene/SceneBuilder.cs`,
the method around line 844). It computes `left` from `grid.PanelLeftPt`, computes `right` as
`grid.OriginLeftPt` plus the **sum** of every column's `WidthPt`, and returns a rectangle whose width
is `right - left`.

- The sum mutated to a maximum survives.
- `right - left` mutated to `right + left` survives.

Both are real: `SceneBuilderTests.Grid(int rowCount)` builds **two** columns of 40 pt and 160 pt, so
the sum (200) and the max (160) differ, and a non-zero `OriginLeftPt` makes `right − left` differ
from `right + left`. Nothing asserts the panel rectangle's size, which is why both live.

**The work.** One fact in `tests/GanttCreator.Core.Tests/Scene/SceneBuilderTests.cs`. The rectangle is
not an emitted primitive on the LIVE path: `PanelBuilder`'s `header-cell:` / `panel-cell:` primitives
belong to the export composition, which never calls `LiveDataPanelBounds`. The live rectangle's only
observable consequence is the outer frame's union in `FrameBandsBuilder.AddOuterFrame`, emitted as
`chart:frame:top` / `bottom` / `left` / `right`.

1. Build a live scene with `Request(Event(1))` and a grid whose table is **wider than the plot**, so
   the table's own left and right edges are the ones the union takes. The existing `Grid(1)` helper is
   not enough: its origin is zero, so `right - left` and `right + left` are the same number, and its
   table is narrower than the plot, so a `Sum` → `Max` mutation never reaches the frame. Use columns
   of 200 pt and 400 pt, `originLeftPt: 40`, `leadingGutterPt: 10`, and a plot at 300..600.
2. Assert `chart:frame:left`'s X equals the grid's `PanelLeftPt` (30 = 40 − 10), which pins the
   R5.18k gutter subtraction rather than the raw origin.
3. Assert `chart:frame:right`'s X equals `OriginLeftPt + 200 + 400` (640). That kills the `Max`
   mutant: the max column is 400, so a mutated frame closes at the plot's right edge (600) instead
   of the table's.
4. The non-zero `OriginLeftPt` and gutter make `right − left` differ from `right + left`, so that same
   right-edge assertion kills the second mutant.

State in the remark *why* two unequal columns and why the table must extend past the plot: a
one-column grid makes `Sum` and `Max` identical, and a narrow table leaves the union's right edge on
the plot, so the test would pass for the wrong reason.

**Expected observation.** `dotnet test tests/GanttCreator.Core.Tests/GanttCreator.Core.Tests.csproj -c Release --filter "FullyQualifiedName~SceneBuilderTests"` green, and a targeted Stryker run
over `SceneBuilder.cs` shows both mutants killed instead of survived.

**Expected observation.** Same filter as D1 green; the two `Logical mutation` survivors at the guard
line disappear from a targeted Stryker report.

## D4 — retire one leaked COM chain (still open, judged on the reported signal)

**The gap.** A workbook-operating test body holds a COM chain that survives teardown, so `Quit()`
returns without terminating and [`OfficeFixture`](../../tests/GanttCreator.Office.IntegrationTests/OfficeFixture.cs)
force-kills its own Excel. The counter is binary per fixture — it records that the teardown had to
kill, not how many proxies the body held — so a body only reads 0 once **every** chain it holds is
released.

**Where it stands on 2026-11-18, measured rather than inferred.** The live gate recorded **52
teardown records: 12 at 0 and 40 at 1, none above 1**. The 12 zeroes are bodies that launch Excel but
never operate on a workbook, which is the proof the fixture itself is not the chain. A probe with the
graceful-exit bound widened kept 1 kill at **30,133 ms**, so this is a chain that never releases
rather than a slow host shutdown. Two attempts have been made: the GC-ordering pass was already
implemented before it was proposed, and releasing the `Application.Selection` proxy in
`ExcelApplicationStateScope` retired one real chain (the total read 39 instead of 40 on that run)
without moving any body from 1 to 0. A neutral result is what a *shared* chain predicts: it can only
show when it is the last one a body holds.

**The item's earlier attribution premise was wrong, and it sent one investigation after a phantom.**
It said "one body forces three" (`Initialise_preserves_a_cell_empty_sheet_with_live_non_cell_state`).
That is a `[Theory]` with three `InlineData` rows, summed under its method name by the per-test line;
no teardown has ever forced more than one kill, which the 2026-11-16 record (51 records, 12 at 0, 39
at 1) and the 2026-11-18 record both show.

**It stays open.** Nothing released so far takes a body from leaking to clean, so the leak is still
there and closing this would assert a retirement that was not measured. What changed on 2026-11-18 is
only the gate: the absolute ceiling was retired because it counted suite size, not leaks (L19), so
D4 is now judged on the reported total and escalating fraction falling run over run.

**Attempt 1, 2026-11-18 — the reader's self-acquired proxies: real drops, no counter movement, and
the discriminator it produced.** `ExcelGanttTableReader` now releases every sheet it enumerates
(three enumerations per read), every `ListObjects` collection, and every candidate table that is not
the one it returns, through a `ReleaseAcquired` seam that calls `ReleaseComObject` rather than
`FinalReleaseComObject` — a worksheet and a table are shared-identity objects whose RCW another
component may hold, so cancelling one acquisition is the whole of this adapter's claim. The returned
table and owner are deliberately not released; three contract tests pin which proxies go and which
stay. **The filtered live run then read 4 of the 5 reader bodies still at 1** (10,094-10,114 ms,
exactly the graceful bound), and the one clean body, `Read_refuses_a_1904_workbook`, is the only one
that never calls `ExcelWorkbookInitialiser.Initialise`. **The discriminator is `Initialise`, not
`Read`**, and the reader fix stays because it is a genuine drop that is now tested, not because it
moved the number.

**Attempt 2, 2026-11-18 — a host probe, and the stop the bounded-retry rule requires.** Before
releasing the initialiser's proxies, the mechanism was tested directly rather than assumed:
[`probe-quit-cases.ps1`](../../scripts/probe-quit-cases.ps1) starts a fresh Excel per case, performs
one operation (table, hidden column, quarter-point row height, defined name, validation, shape,
second sheet, protect/release), closes, releases and GCs exactly as the fixture does, then polls for
10 s. **Run 1:** two cases stuck — both of them table cases — and nine exited. **Run 2, identical
script: every case exited**, including both that had stuck, all five table repeats, and both
calculate variants; the timings fell into two bands (about 260 ms and about 2.8 s) with no
correlation to the operation. The flap is therefore **non-deterministic at the COM level and not
attributable to an operation**, so "release the initialiser's proxies" was not evidence-led; it is
withdrawn rather than landed as a guess. The probe stays in `scripts/` because it is the evidence.

**The next hypothesis, tested without touching the fixture — falsified.** The fixture calls `Quit()`
and only then runs `GC.Collect`/`WaitForPendingFinalizers`, so an unreleased but merely
**unfinalised** RCW would still hold a reference when `Quit()` runs. That was tested first:
[`probe-quit-ordering.ps1`](../../scripts/probe-quit-ordering.ps1) builds a deliberately leaking
body (28 columns, whole-column ranges, fonts, hidden columns, a defined name, created in a scope that
dies before teardown, nothing released) and runs **order A = Quit then GC** against **order B = GC
then Quit**, ten repeats each. Result: **10/10 exited in both orders**. The ordering hypothesis is
not supported.

**And the flap does not reproduce outside the test host at all.** One leaking body run alone under
`dotnet test --filter` still read **1 forced kill at 10,098 ms**, so this is not accumulation across
the run; it is deterministic per body inside the xUnit host, while the same workload under PowerShell
COM exits cleanly every time.

**Attempt 3, 2026-11-18 — the harness instrumentation, and two more falsifications.** The fixture now
records what `Quit()` did and how long the body ran, and the gate prints a `Quit()` outcome
histogram; one contract test pins the record shape. The same isolated leaked body then read
**`Quit:"returned"`, `BodyMs:11883`, kill after `GracefulExitMs:10083`** — Excel **accepted** the quit
and did not terminate, so a refused `Quit` is not the defect. Nulling the body's `initialiser` local
(the adapter instance that holds the `Application` RCW) before teardown changed nothing: same record,
`GracefulExitMs:10086`. So "Quit refused" and "adapter instance rooted by a body local" are both
falsified too.

**The full-run dataset (2026-11-18, 69/69 green).** 52 teardown records: **all 52 `Quit:"returned"`**,
40 at one kill and 12 clean. The first cut read the body duration at report time, i.e. after the
graceful poll, so it measured the very wait it was meant to explain (leaking records read 11-14 s,
clean 3 s); it is now captured at teardown ENTRY, and with that correction the two distributions
overlap: leaking bodies' own duration is **797-4,332 ms (median 2,951)** against clean bodies'
**676-3,261 ms (median 767)**. Duration therefore does not separate them. The clean set is the
fixture's own launch/close bodies, the `ApplicationStateScope` calculation body and one two-workbook
AddRow body; `Read_refuses_a_1904_workbook` read 1 on this run after reading 0 on the earlier one, so
attempt 1's "the discriminator is `Initialise`" reading was too strong and is corrected here.

**Eliminated, with the evidence for each:** reader proxies (attempt 1), any single worksheet operation
(run-1/run-2 probe), finaliser ordering (10 + 10 probe repeats), an adapter instance rooted by a body
local (nulling it changed nothing), `Quit` refusal (all 52 returned), duration (distributions overlap),
and the packed add-in auto-loading into the test's Excel (the Excel `Options` key carries **no**
`OPEN*` value, so nothing is auto-opened).

**What the data still supports:** Excel accepts `Quit` and then survives, only for a workbook that
carries the product's own structure — table plus configuration sheet — inside the xUnit host. The
next experiment bisects that structure with this same record: one body that creates only the table,
one that creates only the configuration sheet, and one that creates both.

**The work.**

1. Read `OfficeFixture.DisposeAsync` and `ComScope` (`OfficeFixture.cs`) and confirm what the fixture
   already releases: every created workbook, the `Workbooks` collection, and the `Application` proxy
   are released before `Quit()`, then GC runs. The uniform one-kill-per-body cost is therefore not a
   fixture-held chain. The unreleased acquisitions are in the adapters every body calls —
   `ExcelGanttTableReader.HasConfigurationSheet` / `HasGanttSheet` / `TryFindTable` drop the sheet and
   `ListObjects` proxies obtained from `GetSheetAt`, and `ExcelRowHeightNormaliser.NormaliseLayoutRow`
   drops the `Rows[...]` Range. Confirm that against the per-body attribution, then pick ONE chain.
2. Fix that chain: hold each proxy in a local and release it once, per the COM ownership rule in
   `AGENTS.md`. Do not silently rewrite the reader's documented "takes no ownership of shared roots"
   contract — releasing a proxy the adapter acquired itself is not the same as releasing a root the

3. Re-run `pwsh ./scripts/verify-office.ps1` and read the signal. **Record the new total and the
   escalating fraction in the same commit.** The absolute `$MaxForcedKills` ceiling was retired on

   `scripts/verify-office.Tests.ps1` pins both. **The closure evidence is a body's record falling
   from 1 to 0** (or the fraction falling with the body count held), observed on a live run, plus the

4. If the diagnosis takes more than two evidence-led attempts, stop and record what was measured —

**Expected observation.** `verify-office.ps1` PASS with the **reported total and escalating fraction
falling** run over run. That is the measurement D4 is judged on now: the gate itself is already green

## D5 — the deadline rule, restated so it is not re-guessed

`verify-office.ps1` now uses `DeadlineSeconds = 780`, raised from 660 on 2026-11-14 **because the
suite grew past it**: the added round-trip test made the run exceed 660 s, the watchdog stopped it
with no trx produced, and that was the gate failing on its own clock rather than on a defect. The
first run under 780 measured **658 s — 122 s of margin**.

The rule, for whoever reads this next: raise `DeadlineSeconds` only with a fresh measurement, state
the measured duration and the cost (a real hang takes that much longer to surface), and never to turn
a red run green. If a future change pushes the suite past 780 s, add the measurement to the existing
comment block rather than replacing it — the history in that block is what stops the deadline being
inflated by habit.
