## Step 0 — verify prerequisites (re-verified 2026-09-26 against landed code)

- R4.1–R4.6 landed. The reconciliation key is **verified and unique**:
  `ScenePrimitive.PrimitiveId`, built only by
  `ScenePrimitive.CreateId(SceneOwnerId, role)`
  (`src/GanttCreator.Core/Scene/ScenePrimitive.cs`), and `GanttScene.TryCreate`
  **refuses a duplicate id** (`SceneCreationRefusal.DuplicatePrimitiveId`) and
  an unresolvable or cyclic group child
  (`src/.../Scene/GanttScene.cs`). An unchanged scene therefore yields an
  identical id set by construction, which is what makes D1's empty-operation
  idempotence pin meaningful.
- `SceneOwnerId` has three kinds — `Row`, `Chart`, and the shared
  `Rows` set (ADR-0017). A shared owner is **membership-sensitive**:
  adding or removing a contributing row changes the id, so
  reconciliation must remove-and-recreate rather than mutate an id in
  place. R4.8 owns the unowned-content side of this.
- The scene inputs are landed and have no production consumer yet:
  `SceneBuilder.TryBuild(SceneBuildRequest)` →
  `SceneBuildOutcome`/`SceneBuildResult` with a typed `SceneBuilderRefusal`,
  and `SceneValidator` producing a `SceneValidationReport` (R3.12
  `abd52c9`+). The reader is `IGanttTableReader`/`ExcelGanttTableReader`
  (R2.4) and validation is `GanttRowValidator` (R2.5) with the R2.9
  TypeOptions layer.
- The seven-step order is re-read and D1–D4 implement it literally. The
  `GanttCreator.` tag is written by R4.1 D2 and is the only mutation
  key; the scene-side ownership inputs are `OwnerId` and `PrimitiveId`
  (R3.14 decision, 2026-09-26).
- **What `Update` actually re-applies — verified against landed code
  2026-09-28, and it decides this row's update-vs-recreate choice.**
  `IShapeWritePort.Update` re-applies the **geometry of every kind** and, for
  a text box, its **content**: the string, the resolved font tokens, and the
  resolved alignment. It deliberately does **not** rewrite `Name` or the
  `AlternativeText` ownership tag — those are the reconciliation key and the
  ownership proof, and re-stamping them would silently "repair" a
  user-edited shape, which is R9.4's job to report.
  **Still create-only: the fill, stroke, and pattern members, which R4.6
  owns.** This row must not treat an update as "make the shape match the
  request" until R4.6 closes the style side; before that, a refresh that
  changed only a colour would move the shape and leave the old colour. Two
  cases therefore need delete-and-recreate rather than update: a style-only
  change, and any ADR-0017 membership change (which already changes the
  `PrimitiveId`). Both are pinned by
  `ExcelShapeWriterTests.An_update_never_rewrites_the_name_or_the_ownership_tag`
  and `A_text_box_with_no_bounds_is_refused_before_its_content_is_applied`.
- **The `ApplyZOrder` ownership preflight is discharged (remediation commit D).**
  `ApplyZOrder` resolved shapes **by name** and called `ZOrder` with no ownership
  check, while `Update`, `Delete`, and `ListOwned` all authorise on
  `CarriesOwnershipTagFor`. A user-drawn shape that happened to carry a requested
  primitive ID would therefore be *reordered* by a refresh even though the same shape
  is correctly preserved by every other mutation path — a preservation guarantee that
  held everywhere else and silently did not hold here. The ownership check now sits
  in the **existing** preflight loop (which already refused a missing shape before
  mutating anything), so an unowned shape anywhere in the list refuses with **zero**
  `ZOrder` calls and the same `NotFound` reason `Update`/`Delete` report. The
  approved single reverse-order `msoSendToBack` pass is **untouched** — the change
  is *who* may be reordered, never *how*. Pinned by five tests in
  `ExcelShapeWriterTests`, three mutation-checked: with the ownership test moved
  into the mutation loop, all three fail. The middle-position test is the atomicity
  pin and is deliberately **not** written as "unowned shape last", because the
  approved pass walks the list in reverse and would then have issued no command
  before refusing — that version passes vacuously.

## Design decisions (behavioural)

- **D1 — Reconcile by stable scene ID.** Owned shapes are matched by
  the R4.3 D2 name/tag pair: matched → update in place; scene-missing →
  delete (owned only); scene-new → create. An update re-applies
  geometry for every kind and, for a text box, its content **and its
  style**, because R4.4, R4.6, and R4.11 have all landed and
  `ExcelShapeWriter.Update` now calls `ApplyText` and `ApplyStyle`.
  **Amended 2026-09-28:** the original text read "a matched shape
  must not update its fill, stroke, or pattern in place: those members
  are still create-only because R4.6 owns them", and specified
  delete-and-recreate for a style-only change. That premise expired
  when R4.6 landed in `6520f62`; the sentence was already written as
  conditional ("would be wrong *until* R4.6 closes the style side"),
  so it self-discharged. Update-in-place is now both correct and the
  architecture's stated preference. An ADR-0017 membership change
  still changes the `PrimitiveId` and therefore still deletes and
  recreates — that is a consequence of the key, not of this decision.
- **D5 — The plan is a pure function of (desired, owned), and
  idempotence is proved as a fixed point.** `ShapeReconciler.Plan`
  issues no host call, so the property is provable without Excel:
  reconciling an already-converged chart plans identically again and
  leaves the same owned set. **Amended 2026-09-28:** the original
  "the observed operation set for an unchanged scene is **empty**" is
  not implementable on this port and was replaced by the fixed-point
  property. `ListOwned()` returns identifiers only, so the planner
  cannot know whether a matched shape already matches; and a read-back
  property diff would be **unsound**, because `TextColour = null`
  means "leave the host font alone", so after a write the intent is no
  longer observable and a diff could not distinguish "we wrote black"
  from "the theme supplied black" from "we never wrote". A tolerance
  loose enough to cope would also hide real changes. The fixed-point
  property is strictly stronger evidence than "this refresh happened to
  write nothing", which would hold only by accident. The roadmap row's
  own acceptance wording — "two refreshes produce identical owned
  IDs/counts/bounds" — is satisfied, and is what the live gate asserts.
- **D2 — Update-first; atomic fallback.** Default is update-in-place
  (preserves selection and performance). The complete-replace
  fallback exists behind the state scope and is chosen only with
  recorded benchmark evidence (architecture rule) — not as a
  convenience.
- **D3 — Blocking errors short-circuit before any shape mutation.**
  The step-3 rule: validation errors are surfaced (reusing the R2.6
  note flow) and the owned set is untouched (**positive test**).
- **D4 — Selection and state.** The R4.2 scope wraps the whole
  reconciliation; selection is captured/restored per its D3; the live
  gate explicitly checks selection integrity after double refresh.

## Stop conditions (item-specific)

- Diff reconciliation proves unreliable (flicker, partial states) →
  do not patch opportunistically: take the atomic fallback with
  benchmark evidence per D2, or stop if even that fails.
- An owned shape cannot be matched by ID (host renaming shapes) →
  stop; the ownership model is the invariant.

## L18 — decided by this row (2026-09-28)

L18 assigned R4.7 the decision on how an over-long shared-owner identifier
is reconciled. **Resolved: refuse and surface, with no truncation and no
contributor-set ceiling.**

The alternative options L18 named were a bounded name with the full
identifier retained in the tag, or a documented contributor-set size
ceiling. Both are rejected on evidence already in the tree:

- A bounded name would make the shape's `Name` stop being the
  reconciliation key, and R4.1 D2 established that `Name` carries the
  full `PrimitiveId` precisely so the unbounded ADR-0017 identifier has
  somewhere to live. Re-bounding it would re-open the R4.8 ownership
  question the ADR-0019 tag was raised to close.
- A contributor-set ceiling is a **product** constraint on how many rows
  may share one deduplicated entity, which is a schema/product decision
  and not this row's to invent.

What actually happens is already correct and is now pinned by a test:
`ExcelShapeWriter.Create` refuses an identifier past
`MaxShapeNameLength = 255` *before* any host call, so an over-long
identifier fails as a typed `ShapeWriteRefusal` and the reconciliation
reports it with the identifier attached
(`ShapeReconcileFailure(PrimitiveId, Refusal)`). The failure mode is
therefore "this entity does not render and says why", not "it renders
wrongly" and not "the key is silently ambiguous". No schema change, no
silent truncation, and no new limit. L18 should be closed as decided.
