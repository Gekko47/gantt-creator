# R5.3 WI-E — Add Child and the permitted child-Type selector

**Status:** Delivered (2026-10-21)
**Owner rulings:** 2026-10-21 (Add Child and the permitted child-Type selector are
in scope for R5.3; the bar height is a custom-style property)
**Depends on:** R5.3 (promote/demote/move/remove), R4.7A (the hierarchy model and
the child-Type rules), R4.7D (the outline groups)
**Governing:** `docs/07-GANTT-ENTITY-GUIDE.md` §9, §10, §23, §24;
`docs/02-ARCHITECTURE.md`; ADR-0008 D4 (guard first); ADR-0034 D1 (a lane owns
its row)

---

## 1. Summary

R5.3's roadmap row is *"Add parent/child commands and stable lane
reassignment"*, and the Phase-5 note keeps *"the permitted child-Type selector
and the delete/promote Ribbon surface over them"* in R5.3. R4.7A's work item
defers the same two things to R5.3 explicitly: *"No Ribbon UI. Add Child,
delete/promote and the permitted-Type selector are R5.3's surface over this
row's mechanics."*

The delete and promote halves landed. The **Add Child** half and the
**permitted child-Type selector** did not, and no code path existed for
either: `git grep "AddChild"` over `src/` and `tests/` returned zero hits, and
`EntityHierarchyCatalog.TypesThatMayBeChild()` existed with **no consumer**
outside the tests.

## 2. Cause

- The hierarchy's rules live in `EntityHierarchyCatalog`, but nothing projected
  them to a UI. The catalogue answered "may this type be a child?" and the
  answer went nowhere.
- `IGanttRowInserter.Insert(type, nextId)` always appended a **top-level**
  row. It had no way to insert a row *as a child* of a selected parent, so the
  `ParentId` and `SiblingOrder` cells were never written by an insert.
- The Ribbon's Add buttons each insert one fixed type. There was no
  type-picker whose items depend on the current selection.

## 3. Fix

### 3.1 Core — `AddChildPlanner`

A pure planner: given the validated rows, the selected parent row, and the
requested child type, produce the writes that make the new row a child of
that parent, or a typed refusal.

- The parent must **own children** (`EntityHierarchyCatalog.MayOwnChildren`).
- The requested type must **be a child** (`MayBeChild`).
- The parent must not already own **seven** children
  (`EntityHierarchyCatalog.MaxChildrenPerParent`).
- The parent must not itself be a child: that would make the new row depth 3
  (`EntityHierarchyCatalog.MaxDepth`).
- The new row lands **directly beneath the parent's existing child run**, so
  the outline group stays one contiguous run.
- A `CriticalInterval` parent additionally requires a **span** child
  (the parent's own rule, already in `HierarchyMutations`).

The permitted child types for a given parent are projected by the same
catalogue, so the Ribbon's list and the planner's acceptance can never
disagree.

### 3.2 Office — the as-child insert

`IGanttRowInserter` gains an as-child variant that writes the planned
`ParentId` and `SiblingOrder` cells. Guard-first per ADR-0008 D4.

### 3.3 AddIn — the Ribbon surface

A **split button** on the Add control whose menu lists the permitted child
types for the selected parent, projected from
`EntityHierarchyCatalog.TypesThatMayBeChild()`. The permitted list is never
authored twice: the catalogue is the only source.

## 4. Acceptance

- Adding a child to a parent writes the `ParentId` and `SiblingOrder` cells
  and the new row renders projected onto its parent's lane.
- A parent that may not own children, a type that may not be a child, a
  parent at seven children, and a parent that is itself a child are each
  refused with a **typed** reason and a **positive test**.
- The Ribbon's child-type list contains only types the catalogue permits for
  the selected parent, and the planner accepts every type on that list.

## 5. Exclusions

- No change to the hierarchy rules themselves: `EntityHierarchyCatalog` is
  used as it stands.
- No third-level nesting: a depth-3 row is refused, not supported.
- No change to the outline-group writer: the new row joins the parent's
  existing group through the same writer the other commands use.

### 6.1 Two corrections the tests forced

**A Critical Interval is never a parent.** The first draft of the planner
carried a `ParentNotSpan` rule for a `CriticalInterval` parent, on the
premise that an interval takes only a span child. The R5.3 owner ruling
makes a Critical Interval **child-only and never owning**, so it is refused
as a PARENT (`ParentCannotOwnChildren`) rather than given a narrower list of
child types. The rule and the refusal reason were removed.

**A menu is not bindable in Excel-DNA 1.9.** The plan called for a Ribbon
**menu** whose items the hierarchy catalogue populates. Excel-DNA 1.9
exposes no `IRibbonMenu` type at all (verified by reflection over
`ExcelDna.Integration.dll` and `exceldna.interop` 16.0.0), so a `getMenu`
callback cannot be bound. The surface is a **dropDown** instead, using the
`getItemCount` / `getItemID` / `getItemLabel` pattern the description-label
and date-label dropdowns already use. The projection is unchanged: the
dropdown still offers exactly the catalogue's permitted child types.

### 6.2 Evidence

Core +11 (`AddChildPlannerTests`), Office contract +5
(`ExcelAddChildMutatorTests`), AddIn +11 (`AddChildCommandTests`) and +8
(`AddChildRibbonTests`). The architecture suite's guard-first registry
gained the new adapter and its port.

The positive tests for every refusal, as `AGENTS.md` requires: an unknown
selection, a parent that may not own children, a type that may not be a
child, a parent at seven children, a parent that is itself a child, a
protected sheet, and a refused insert. The Office tests assert that a
refused plan inserts **no row at all** — the refusal happens before the
insert, so a refused add leaves the workbook untouched, not even an empty
row.

**Office host gate: not run.** The live acceptance test — add a child in
Excel, Refresh, and compare the live result — is a human step and is
recorded as outstanding.
