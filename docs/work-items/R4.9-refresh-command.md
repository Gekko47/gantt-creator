## Design decisions (behavioural)

- **D1 — One command, one orchestrator.** **Amended 2026-10-04: this decision was
  superseded by R4.8A D1 before it was implemented.** It originally read "`RefreshSheetCommand`
  runs: read → validate → blocking errors → surface → build scene → render", which
  would have put the whole pipeline in the Ribbon callback. R4.8A moved that order into
  `GanttRefreshOrchestrator` and the landed command is deliberately thin — it checks
  availability, invokes the service **exactly once**, and presents the outcome. That is
  the correct shape and it is what shipped; this entry records the amendment rather
  than re-implementing anything. What R4.9 still owns is the *gate*, not the sequence:
  the seven steps are read (R2.4 refusals → one actionable message each) → validate
  with registry (R2.9) → blocking errors surfaced with **zero mutation** (the R2.6 note
  flow reused verbatim) → else build scene (R3.12 `SceneBuilder`) → render (R4.5–R4.7
  inside the R4.2 scope) → count-only summary on success.
- **D2 — Presenter degradation and the boundary.** Identical to
  R2.6/R2.2: unexpected exceptions cross the one command boundary;
  presenter failure degrades to no dialog; nothing scatters message
  boxes.
- **D3 — Ribbon gating.** The Refresh button gates on workbook
  presence (the existing truth table); callback is thin, routes
  through `CommandBoundary`, and refreshes ribbon state after the run.
- **D4 — Validate re-exercised, not rewritten.** The live gate runs
  both commands on a valid and an invalid workbook; Validate's
  behaviour is R2.6's, unchanged.
