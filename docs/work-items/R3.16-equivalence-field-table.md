## Context

R3.14 proved the scene model for three of the ten equivalence rows. It had to
*assemble* the field lists rather than transcribe them, because the guide's
"Entity-to-renderer equivalence" section states which **representation** each
entity takes in each renderer, not which **fields** it carries. That assembly is
recorded in the R3.14 work item's Notes and is sound, but it is an agent's
reading sitting in a test file, not a contract a renderer author can consult.

Three specific gaps make an amendment worth doing rather than leaving to each
Phase-4 row:

1. **A scene representation is not a host representation.** The critical
   interval is a `SceneRect` one `CriticalLinePt` tall in the scene, but a
   *line* in all three host renderers. The current table says "line shape"
   three times and never records the translation.
2. **Two rows draw no host object on the live worksheet.** The data
   panel/header row is Excel cells, and the validation indicator is
   cells/dialog and excluded from export. A renderer author reading only the
   current table could conclude they must draw panel rectangles on the live
   sheet, which contradicts the invariant that the worksheet data table is
   visible and beside the live Gantt, and R4.8's preservation rules.
3. **Seven of ten rows have no field-level proof.** Procurement hatch, the
   critical interval, delineators, the panel/header primitives, the
   bands/grid/frame, and the validation indicator's exclusion are all
   unguarded by any test.

Three corrections this row makes to the first inventory, each verified
against the committed golden scene:

- **The panel row has no fixture.** `SceneBuilder` emits panel primitives only
  when `request.Panel` (a `PanelTheme`) is supplied
  (`src/GanttCreator.Core/Scene/SceneBuilder.cs` line 603), and the canonical
  `BuildScene()` does not set it. The golden contains **zero** `panel` or
  `header` primitives. A field test for this row therefore needs a
  panel-bearing scene, which is new test scaffolding and a product decision
  about the canonical fixture — not a transcription.
- **The Labels row was two rows.** Description and date labels sit at
  `ZLayer` 70 with lane and stack keys populated; a delineator label sits at
  `ZLayer` **75** with both keys **null**. The first inventory put all four
  roles in one row, which would have failed on the delineator label twice —
  wrong layer, missing order keys.
- **Header labels have their own identities and no order keys.**
  `chart:year-label:{yyyy}` and `chart:period:{yyyy-MM-dd}:label` are
  `ZLayer` 80 text primitives with no lane/stack keys. Note the inconsistent
  convention: the year label uses a `chart:year-label:` prefix while the
  period label appends `:label` to its rectangle's id. The table records both
  spellings rather than normalising them, because the id is the shape name.

**A shared delineator line and its labels are not one entity.** In the
fixture the same-date pair shares one line, `G-…a2|G-…a3:delineator`, while
each row keeps its own `a2:delineator-label` and `a3:delineator-label`. A
reader who expected one label per line would reconcile the wrong set.

**Owner and lifetime are the two columns that change renderer behaviour.**
A chart-owned primitive is chart furniture and is never a row-reconciliation
deletion candidate; a row-owned one dies with its row; a shared `Rows` one is
membership-sensitive, so adding or removing a contributing row changes its
identifier and forces remove-then-recreate (ADR-0017 D4).

**Identifier scope (recorded because it is a real hazard).** The role suffix
and the `{placeholder}` structure are the contract, because the identifier is
the shape name (R4.3 D2) and the reconciliation key (R4.7). The *formatting of
an interpolated value* is an implementation detail and is **not** normative:
`chart:grid:{x}` currently formats a double `"R"` and
`chart:period:{yyyy-MM-dd}` formats a date. Reformatting either changes the
identifier for every affected shape and forces a full owned-set replacement.
D-G14 records this; the table must state it rather than let a reader assume
the current formatting is contractual.

Verified members, R3.2 `e244d3c` onward: `ScenePrimitive` carries
`PrimitiveId`, `OwnerId`, `ZLayer`, `EntityType`, `LaneOrder`, `StackIndex`,
`SortOrder`; `SceneStyle` carries `StyleKey`, `FillColour`, `StrokeColour`,
`OutlineWidthPt`, `HatchPattern`, `FontFamily`, `FontSizePt`, `Bold`,
`Alignment`; the base type exposes **no** `Style` (a `SceneGroup` has none).
`SceneOwnerId` has kinds `Row`, `Chart`, `Rows`. `SceneSnapshot` is version 2.
The R3.14 catalogue at `tests/GanttCreator.Core.Tests/Scene/EquivalenceFields.cs`
covers three rows and hard-codes **row** ownership, so chart-owned primitives
are not yet assertable — the re-transcription must add an owner-kind axis.

**Out of this table's reach:** `SceneGroup` membership and child order, which
R6.4 owns. The editable-composition and PowerPoint renderers need it, and its
absence here must be read as "not yet specified", not "not required".

Four notes the guide must carry beside the table:

- **The panel row is specified but unexercised.** Panel primitives are emitted
  only when a `PanelTheme` is supplied, and the canonical reference scene does
  not supply one, so the committed golden contains none. The table states the
  contract; it does not claim test coverage that does not exist.
- **Identifier scope.** The role suffix and the `{placeholder}` structure are
  contractual, because the identifier is the shape name and the
  reconciliation key. The formatting of an interpolated value is **not**:
  `chart:grid:{x}` formats a double `"R"` and `chart:period:{yyyy-MM-dd}`
  formats a date today, and changing either changes the identifier for every
  affected shape. Reformatting is therefore an owned-set replacement, not a
  cosmetic edit.
- **Ownership inputs.** The scene supplies `OwnerId` and the role-derived
  `PrimitiveId`; the `GanttCreator.`-prefixed ownership tag is written by the
  shape port (R4.1 D2), per the R3.14 decision.
- **Grouping is out of scope here.** `SceneGroup` membership and child order
  belong to R6.4. Their absence from this table means "not yet specified",
  not "not required".

## Design decisions

- **D1 — Restatement, not extension.** The table names only fields the landed
  model already carries. Any cell that would require a new field reads "not
  carried by the model; excluded" instead. This keeps the amendment inside
  "restating the contract" and outside "changing the contract".
- **D2 — A translation column, because representation differs from scene
  shape.** Each row records what the scene carries and what each host
  renderer draws, so a rect-to-line or cells-to-shapes translation is stated
  rather than inferred. This is the gap the amendment most needs to close.
- **D3 — Live-sheet column is explicit.** Every row states whether the live
  renderer draws a host object or defers to the worksheet, so no renderer
  author draws panel rectangles over the visible data table.
- **D4 — Ownership is stated once, not per row.** The nine shared-contract
  bullets already give every entity an id, type, geometry, style key, z-layer,
  and ownership metadata. The table adds the per-row *specifics* and a single
  note that the `GanttCreator.` tag is written by the shape port (R4.1 D2),
  per the R3.14 decision.
- **D5 — The legend is an eleventh row, explicitly empty.** §25 is optional,
  hidden by default, and has no equivalence row today. Recording it as "not
  carried by the model today" closes the table without inventing fields.
- **D6 — A drift guard, because this failure recurs.** A test asserts the
  guide's row set and the catalogue's row set agree. A future guide edit that
  adds, renames, or removes a row then fails the suite instead of drifting
  silently, which is the defect class this row exists to remove.
- **D7 — Approval gate.** Step 2 does not start until the product owner
  approves the field lists. Steps 1, 3, and 4 are test-only and may proceed,
  because the ten row *names* already exist in the guide; if approval changes
  any field list, step 3 is re-transcribed before the guard is trusted.
