# Work item — R5.6a

> **Guide status**: Binding contract, added 2026-09-23 by the R2 findings reconciliation. Upgrade to Tier A at Phase 4 exit.

## Outcome

Create, rename, and delete approved user named-style presets through an offline Ribbon dialog (the **Custom styles** tab of the Theme Settings dialog), including the explicit label/colour capability fields required by ADR-0009. Built-in keys cannot be deleted or overwritten; custom styles preserve portable offline configuration and feed Custom Activity validation. A row of a style-key type (Custom Activity, Custom Milestone — the catalogue's `RequiresStyleKey` authority) is assigned a custom style through the ribbon's **Custom style** dropdown, which writes the row's hidden `StyleKey` cell.

## Owner ruling 2026-10-19 (binding) — object-first property editing

The custom-style editor edits **one style object with all of its properties**, not a bag of option-kind rows. The editor is grouped by concern — **Fill** (colour + pattern), **Outline** (colour + width + line style), **Label** (colour + default position + permitted positions), **Size** (bar height + milestone size) — and the list of user-created styles is the master selection on the left, with the selected style's properties on the right.

The **whole dialog** follows the same rule: the options are separated by the object they change, and each object's properties are shown together rather than split across tabs by option kind. The dialog is three scope tabs:

| Tab | Object | Grouping |
|---|---|---|
| **Entity styles** | A built-in style preset | By entity family: Activities, Milestones, Procurement, Chart elements. Each preset group shows that preset's own Fill / Outline / Label properties, plus its code-owned pattern and line style shown read-only. The two **user-authored** styles (`CustomActivity` and `CustomMilestone`) are **not** listed here: a style-key type takes the style the *user* authored, so its built-in fallback is a placeholder, not a style the user chose. Those styles live on the Custom styles tab. |
| **Chart** | The chart | By the chart object changed: *Rows and lanes*, *Grid*, *Milestones*, *Chart appearance*. Every token appears under a human name with its permitted range. |
| **Custom styles** | A user-created style | Fill / Outline / Label / Size, as above. |

Two consequences of the grouping:

- **A token whose scope is not the chart does not appear on the Chart tab.** The entity defaults (bar height, milestone size, outline width, delineator width) are the *default* every entity of that kind uses; a named style's own sizes belong to the style and live with it.
- **An option the renderer cannot honour is shown, not offered.** The hatch spacing and hatch line width are visible on the Chart tab with the reason stated, because the host's patterned fill is a fixed-pitch set with no member controlling either.

1. **Fill type is exposed.** The fill pattern (`None` / `Forward diagonal` / `Backward diagonal` / `Cross`) is a first-class property of a custom style. The schema already carries it (`tblGanttStyles` column `HatchPattern`); only the editor and the write path were missing it.
2. **Stroke type is exposed.** A custom style carries a dash pattern for its outline. The schema gains a `StrokeDash` column (appended, so every existing column index is unchanged) and the scene/renderer carry the resolved dash to the host's `LineFormat.DashStyle`. The vocabulary is a closed six-member subset of the host's twelve — `Solid`, `SquareDot`, `RoundDot`, `Dash`, `DashDot`, `LongDash` — because the host's `SysDash` family renders against the operating system's UI theme and would not look the same on another machine. ADR-0044 records the decision.
3. **A style's sizes and label vocabulary belong to the style, not to the chart.** The bar height, the milestone size, the outline width, the default label position, and the permitted label positions are edited with the style that owns them, not in the chart-wide metric tabs. The chart-wide tabs keep the chart-wide metrics only.
4. **One style, many rows.** A style is not bound to an entity kind: the same custom style can be assigned to a Custom Activity row and to a Custom Milestone row. The style's bar height and milestone size are independent values, and a zero size means "not applicable to that entity kind" — the same convention the built-in presets use.
5. **A partial edit preserves the rest.** A null optional member on a style edit means *not carried*, and the writer preserves the stored value. An edit that changes one colour must not reset the style's pattern, widths, sizes, or label vocabulary.
6. **Built-in styles keep their code-owned properties.** The pattern and the dash of a built-in preset are read-only in the editor; making them editable would break the reader's exact match on the built-in rows for no user gain.
7. **Hatch spacing and hatch line width are not exposed.** The host's patterned fill is a fixed-pitch pattern set with no member controlling either value, so offering those controls would promise something the renderer does not deliver.
8. **Every chart border is one uniform soft grey.** The plot frame, the year boundary and the minor grid all draw in the same colour; the year boundary keeps its own `MajorBoundaryPt` width, so it reads as a boundary without a second colour. ADR-0046 records the decision and amends the entity guide's token table. A workbook that stored the old black major grid keeps it, because a stored chart-chrome colour is the user's choice — the remedy is the Chart tab's **Reset to default**.

## Dependencies and exclusions

Depends on R2.7b, R2.9, R2.10, R4.6, and R5.6. No Office theme inheritance, arbitrary code, shape mutation, or renderer-specific fallback. Custom styles are user-authored rows in `tblGanttStyles` preserved on catalogue regeneration (ADR-0007 D4); they are not stored on `tblGanttCreatorConfig` metadata rows.

Excluded from this item: the PNG and PowerPoint renderers do not exist yet, so the dash pattern has no export-parity surface to break. The chart chrome colours (the frame and band colours) are **not** a gap: they are persisted as settings and edited on the Chart tab, under ADR-0045.

## Acceptance contract

- Custom style keys must be unique, non-empty, and not collide with built-in preset keys.
- Built-in preset keys cannot be renamed or deleted.
- Creating a custom style writes a user row to `tblGanttStyles`; it survives save/reopen and catalogue regeneration.
- Deleting a custom style removes its user row; it is not recreated on regeneration.
- Custom styles are editable in the Theme Settings dialog's **Custom styles** tab, with their properties grouped as Fill / Outline / Label / Size.
- A custom style exposes its **fill type** (the pattern) and its **stroke type** (the dash), alongside its colours, outline width, bar height, milestone size, default label position, and permitted label positions.
- A custom style's sizes are range-checked against the same catalogue tokens the global metrics use, with zero accepted as "not applicable to that entity kind".
- A style edit that does not carry a property preserves the stored value; changing one colour never resets the style's pattern, widths, sizes, or label vocabulary.
- The ribbon Custom style dropdown offers only user-created keys (built-in presets are never listed), enables only for a single style-key-type row with at least one custom style defined, and writes exactly that row's `StyleKey` cell — refused before any write for a non-style type, a blank/unknown key, a protected sheet, or a non-single-row selection.
- Custom Activity and Custom Milestone both resolve label positions from their row style (the `RequiresStyleKey` catalogue authority); neither reads its placeholder catalogue set.
- Each style-key type carries a code-owned default style key (`CustomActivity`, `CustomMilestone`) and a matching built-in preset whose tokens are the As-Planned ones, so a row whose user-created style was deleted still renders a visible, correctly sized entity rather than refusing the scene.
- Deleting a custom style that a row is using does not leave that row unrenderable: the dangling key is reported as a non-blocking warning and the engine heals the cell to the type's default on the next Refresh. A live user choice is never overwritten, and a blank key is left blank (it already resolves to the type default at render time).
- The code-owned preset fallback is scoped to the two style-key types. For every other type a missing style means the configuration sheet is damaged and the scene is refused, never silently rendered as a preset.
- Command/contract tests cover unique keys, every capability field, cancel-before-write, built-in protection, save/reopen, Custom Activity and Custom Milestone consumption, the dropdown's projection/enable/selection semantics, the deleted-style heal, the fill and stroke type, and the partial-edit preservation.
- Office gate compares the configured style with live Refresh output.
