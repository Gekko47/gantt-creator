## Design decisions (manifest decision D-G1 — human approval of D1–D3
required before the first write)

- **D1 — Storage format: Excel Tables, not JSON.** Each catalogue is a
  `ListObject` on `_GanttCreatorConfig`. Rationale: the architecture
  contract already names them; R2.9's in-cell dropdown requires a
  materialised cell range (`GanttCreator.TypeOptions` cannot refer to a
  JSON string); tables stay inspectable without the add-in. The roadmap
  allows "single JSON or table block"; the ADR records why tables win.
- **D2 — Table set (5 tables).** `tblGanttTypes` (16 rows projected from
  `EntityTypeCatalog.Entries`: DisplayName, DefaultStyleKey, kind, date
  mode, colour capability, requiresStyleKey, allowed label positions),
  `tblGanttStyles` (built-in presets, one per catalogue entry; user customs
  appended only by R5.10), `tblGanttMetrics` (23 rows), `tblGanttConfig`
  (schema version, catalogue hash, workbook ID, add-in version last used —
  matching `GanttSchemaVersion.cs` remarks). This settles the roadmap's
  naming question: `tblGanttConfig` is the metadata table and the split
  catalogues are the other three; both documents are consistent once read
  together.
- **D3 — Settings storage: `tblGanttSettings` (new; ADR-amended).** The
  architecture table list has no settings home, yet the roadmap requires
  the settings catalogue now. Proposal: a sixth key/value table
  `tblGanttSettings` (`SettingKey`, `SettingValue`, one row per setting),
  keeping `tblGanttConfig` purely add-in metadata. The ADR amends
  [`../02-ARCHITECTURE.md`](../02-ARCHITECTURE.md) "Configuration worksheet
  contract" in the same change. **Status: proposal — human approval
  required.** Rejected alternative: settings rows inside `tblGanttConfig`
  (mixes user-mutable values with add-in metadata and complicates the
  R2.10 repair contract).
- **D4 — Regeneration policy.** `tblGanttTypes` and `tblGanttMetrics`
  regenerate only from the code-owned catalogues and are never
  user-editable (entity guide "VeryHidden catalogue and style rules").
  `tblGanttStyles` built-in rows regenerate; user rows are preserved
  (migration is R2.10's contract, but R2.7 must not ship a write path that
  can destroy them). `tblGanttSettings` holds user values written by
  approved dialogs only; R2.7 writes defaults when a key is absent and
  never overwrites a present value.
- **D5 — Schema version stays 1.** v1 never shipped config tables;
  materialising them completes v1's definition. Future catalogue changes
  bump per `GanttSchemaVersion` remarks. Recorded in the ADR.
- **D6 — Catalogue hash.** `tblGanttConfig` stores a stable hash over the
  code-owned catalogue definition so R2.9/R2.10 detect drift.
  Recommendation: SHA-256 over a canonical, culture-invariant
  serialisation owned by Core, never over raw worksheet text; algorithm
  fixed by the ADR.

## Risk and rollback

Main risks: (a) destructive write to a user workbook — mitigated by
write-only-on-initialise (fresh `_GanttCreatorConfig`) and typed refusals
with positive tests; (b) COM proxy leaks — seams + locals, no chained
access, ownership per `ExcelWorkbookInitialiser` remarks; (c) hash
instability across cultures — pinned by Core culture tests. Rollback:
`git revert` of the single commit; no consumer exists until R2.8/R2.9.
