## Outcome

`GanttCatalogues.Settings` carries a `DateDisplayFormat` key whose
approved value renders every event date as `dd/mm/yyyy` invariantly, and
`GanttSchemaVersion.CurrentSchemaVersion` advances from 2 to 3 so a
workbook without the key is refused rather than read with an inferred
format.

## Context and owed deferrals

Roadmap row: *Add the approved `DateDisplayFormat` setting and advance the
workbook schema version — Settings key-set, key-order, default-value,
strict-parser refusal, and `en-GB`/`en-US` culture-invariance tests;
schema-version pin — None.*

Entity guide §3 and §23 said "the approved display format" and "approved
invariant display format" without naming one. R3.11's stop condition

**Owed deferral:** a user-facing format picker is a separate

so this row writes the default and reads it back; it does not add a

## Design decisions

- **D1 — One member, `DdMMyyyy`.** A single-member closed enum with a
  strict ordinal parser, mirroring `GanttPeriodLabelFormat`. The stored
  text is the member name, matching the existing convention.
- **D2 — One formatting helper, in Core.** A single invariant
  `DateOnly` → `dd/mm/yyyy` helper, called by R3.11's `PanelBuilder` and
  `DateLabelBuilder`, so no renderer and no builder can re-derive the
  format or apply a culture.
- **D3 — Version 2 → 3, pins updated with it.** The `GanttSchemaVersion`
  remarks make a settings key-set change a bump; the Core pins move with
  it in the same commit.
- **D4 — Key order is contract.** The new key is appended last, and the
  key-order test pins the whole sequence so a key inserted in the wrong
  position fails.
- **D5 — No reader change.** The existing exact-key-set check refuses a
  workbook lacking the key. A positive test proves the refusal fires.
