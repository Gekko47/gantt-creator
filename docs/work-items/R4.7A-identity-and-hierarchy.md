## Outcome

`ParentId` is the authoritative relationship, `SiblingOrder` is
engine-maintained, identity is assigned when a row first becomes a meaningful
entity, a parent may have at most seven children, deleting a parent promotes its
children, and a cloned managed structure is reseeded atomically — with every
failure reported as a typed blocking validation issue before any render.

## Design decisions

- **D0 — The child-capability matrix is introduced here, not in R4.7B.** The
  product owner chose this on 2026-09-29. `EntityHierarchyCatalog` is a single
  Core authority answering two questions per `GanttEntityType`: *may this type own
  children?* and *may this type be a child?* It names only members of
  `GanttEntityType`, never a parallel type list, and an **exhaustiveness test
  fails if any catalogue member is unclassified**. The seven-child cap (D4) and the
  general `ParentId` widening (D9) both need this matrix, so putting it in R4.7B
  would make R4.7A depend on a later row to express its own rule. R4.7B then
  *consumes* the matrix for its projection modes rather than defining it.
- **D1 — `ParentId` is authoritative; Excel grouping is presentation.** Outline
  groups are reconstructed from metadata, never read as the relationship.
- **D2 — `SiblingOrder` is required, engine-maintained, hidden.** Blank means the
  engine has not assigned one yet, which validation reports; it is never treated
  as ordering. This is what stops a user sort silently redefining the hierarchy.
- **D3 — Identity is assigned on first meaningful entry.** A completely blank row
  is not an entity and holds no ID. **One `IsSemanticallyEmptyRow()` rule** is
  defined once and reused; per-call-site blank tests are the defect this prevents.
- **D4 — `MaxChildrenPerParent = 7`.** The eighth child is refused with a typed
  error carrying the parent ID and the current count.
- **D5 — Nesting depth is explicitly limited to two levels** (top-level parent,
  then children). Deeper nesting is *rejected* with a blocking issue rather than
  silently accepted, per REV5 §4's requirement that it be supported or rejected
  explicitly.
- **D6 — Promote-on-delete, never cascade-delete.** Deleting a top-level parent
  makes its children top-level; deleting a nested parent gives its children the
  deleted parent's own parent. Children retain their IDs and schedule data.
  `ParentId`, `SiblingOrder`, lane ownership and outline grouping are recomputed.
  Confirmation is required, since custom Undo is not implemented (ADR-0008).
- **D7 — Clone reseed is atomic.** `detect duplicate → build old→new Id map →
  rewrite all Ids → rewrite ParentIds → derive metadata → rebuild outline → new
  ownership context`. A partially reseeded hierarchy is refused, never repaired one
  row at a time.
- **D8 — Every refusal is typed and has a positive test** in the same commit
  (`AGENTS.md` validator rule): broken, self-referential, cyclic, ambiguous
  parent, over-deep, and over-seven each have a test that constructs the bad input.
- **D9 — `ParentId` widens from Critical-Interval-only to every child-capable
  type, in this row.** `GanttRowValidator` line 259 currently sets
  `parentRelevant = isCriticalInterval` and scopes every parent check to critical
  intervals. Making `ParentId` authoritative for general hierarchy requires that
  scope to widen to whatever D0's matrix classifies as child-capable. The matrix
  lands first precisely so this widening is driven by one authority rather than by
  a second, ad-hoc type list. **This changes which rows may carry a `ParentId`
  and therefore what validation accepts today**, so it is a deliberate,
  separately-testable behaviour change rather than a refactor. Types the matrix
  does not classify as child-capable still report `NotUsedByType` for a
  `ParentId`, so nothing becomes silently permitted.
- **D10 — The schema bump 3 → 4 is this row's, not R4.7C's.** R4.7A adds
  `SiblingOrder` to `GanttTableSchema.Default`, which is a schema contract change
  and therefore takes the version. **R4.7C's own guide previously claimed the same
  3 → 4 bump; that is corrected to 4 → 5.** Two rows claiming one version number
  would either collide or skip a version, and the integrity checker cannot detect
  it because the version is the signal it compares against. Each row bumps once,
  in the row whose change requires it.

## Acceptance tests

- **Automated** — `dotnet test tests/GanttCreator.Core.Tests`:
  - `ParentId` is authoritative; reordering worksheet rows changes `SiblingOrder`
    but never an ID
  - a blank row is not an entity; the first meaningful entry gets a new ID; one
    blank row remains after insert and after delete
  - seven children accepted, **eighth refused** (positive test)
  - every refusal code above has a positive test
  - promote-on-delete: children keep IDs and dates, become top-level, and are
    re-grouped
  - paste → new ID; clone → new IDs with the relationship preserved; duplicate
    managed structure → one atomic reseed with no partial state
  - IDs are stable across two Refresh-equivalent builds
- **Automated** — `dotnet test tests/GanttCreator.Architecture.Tests`: Core stays
  reference-clean.
- **Office host (Required)** — create a parent and seven children in Excel, observe
  the eighth refused, collapse and expand, delete the parent and observe the
  children promoted. Record the host build.

## Stop conditions

- A design that requires a user to see `ParentId` or `SiblingOrder` → stop; these
  are engine columns (register §2, and REV5 §22 instruction 4).
- A migration path becomes necessary → stop and ask; the owner confirmed none is
  needed.

## Risk and rollback

Main risk: a `GanttRowDto` constructor change ripples into the reader, validator
and their tests. Mitigated by adding the column at a defined position and updating
all call sites in the same commit. Rollback: `git revert`.
