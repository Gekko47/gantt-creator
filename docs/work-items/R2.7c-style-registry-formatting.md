# Work item — R2.7c

> **Guide status**: Authored (Tier A) 2026-09-25 · implemented and verified. Prerequisite reads: [`IMPLEMENTATION-PLAN.md`](IMPLEMENTATION-PLAN.md) implementer contract. Depends on: R2.7 (catalogues), R2.7b (capability schema, ADR-0009). Blocks: R3.14 equivalence field list; R4.6 style-token mapping.

## Outcome

`GanttStyleRegistry` carries each named style's **resolved formatting** and default
label position, so `GanttStyleResolver` resolves built-in *and* user-authored styles
from one source instead of reading only the code-owned built-in presets.

## Context and owed deferrals

Roadmap row: *Carry each named style's resolved formatting and default label
position in the Core style registry so resolution covers user styles, not only
built-in presets.*

The StageInspect audit landed `src/GanttCreator.Core/GanttStyleResolution.cs` as
prerequisite work. `GanttStyleResolver.FindStyle` reads
`GanttCatalogues.StylePresets` — the 15 built-in presets — so a style authored by the
user in `tblGanttStyles` has no resolvable formatting at all. That contradicts two
existing accepted gates:

- R2.7b: *"save/reopen preserves custom style capabilities and hash"* — capabilities
  survive, but the colours and metrics that give a Custom Activity its appearance do
  not reach resolution.
- R5.6a: *"create a custom style, assign it to Custom Activity, Refresh, and compare
  the live result"* — impossible while the style is invisible to the resolver.

`ExcelConfigCatalogueReader.ValidateStyles` already validates every resolved column
(`FillColour` 2, `StrokeColour` 3, `HatchPattern` 4, `HatchPitchPt` 5, `HatchLinePt` 6,
`TextColour` 7, `StandardOutlinePt` 8, `ActivityHeightPt` 9, `MilestoneSizePt` 10,
`DefaultLabelPosition` 11) and then discards them when it builds
`GanttStyleDefinition`. The data is already read and checked; it simply is not
projected.

## Design decisions (behavioural)

- **D1 — Formatting is optional on the record.** `GanttStyleDefinition` keeps its
  three required capability parameters and adds optional formatting parameters, so
  the compatibility path (`GanttStyleRegistry.Empty`, existing callers) keeps
  compiling and a capability-only definition stays legal.
- **D2 — Resolution prefers the registry, then the built-in preset.** A key present
  in the registry resolves from the registry; otherwise the built-in preset is
  consulted, preserving today's behaviour for every existing caller.
- **D3 — A malformed format is a construction-time refusal, not a render-time
  surprise.** Colours must be empty or uppercase `#RRGGBB`; metrics must be finite and
  non-negative; a hatch pattern and a default label position must be defined. Each
  guard has a positive test in the same commit.
- **D4 — Office gate is `None`.** No worksheet bytes change: the reader already
  validates these columns and R2.7b already carries the live save/reopen evidence.
  This row only projects already-validated values into Core.

## Stop conditions (item-specific)

- Extending the definition would require a new table column or a schema bump.
- A colour or metric value is needed that the workbook does not already store.
- The projection would change a refusal reason R2.7b already pins.

## Risk and rollback

Main risk: changing a widely-constructed record. Mitigated by keeping the new
parameters optional (D1) and by the existing registry tests. Rollback: `git revert`;
the change is additive.

## Notes during implementation

Record only observed results.

- **Observed 2026-09-25.** `GanttStyleDefinition` carries optional resolved
  formatting (`DefaultLabelPosition`, three colours, hatch pattern and metrics)
  with `HasFormatting` and `ValidateFormatting`; the registry validates
  formatting at construction. `GanttStyleResolver.TryResolve` gained a
  registry-taking overload that prefers a registered style, then the Type
  default, then the built-in preset (D2), preserving the pre-R2.7c
  compatibility overload. The Office reader projects every validated user-style
  resolved column.
- **Deviation from D2 recorded:** a supplied-but-unresolvable key falls back to
  the Type default preset rather than refusing, which is the pre-R2.7c
  behaviour. A blank key on a Type with no default still refuses
  `NoDefaultStyle`; a supplied key that cannot be produced refuses
  `StyleUnavailable`.
- **Gap found and closed while implementing:** `ValidateUserStyleCapabilities`
  validated only the label/colour-capability columns, so a user row with a
  negative metric, a lowercase colour, or a non-numeric metric was projected as
  `0`/empty and would have rendered as a silent blank style. Those columns are
  now validated with positive refusal tests.
- Gates: Debug solution build 0 errors; Core 606/606 PASS; Office contract
  227/227 PASS; `verify-quick.ps1` PASS in 200.1s (11/11).
- Office gate: `Not run` (D4 — no worksheet bytes change; live R5.6a evidence is
  the gate that consumes this row).
