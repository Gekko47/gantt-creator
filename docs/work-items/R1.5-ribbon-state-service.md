# Work item — R1.5

## Outcome

The add-in has one `RibbonStateService`: dynamic Ribbon getters answer from an
immutable state snapshot (deterministic, side-effect-free, never throwing), and
one invalidate mechanism owns the `IRibbonUI` handle captured in the existing
`onLoad` callback. Two real state facts gate two controls — `btnDiagnostics`
requires an active workbook, the new `btnOpenLog` requires an available log file
— and workbook state changes (`WorkbookActivate`, `WorkbookDeactivate`,
`NewWorkbook`) refresh and invalidate the Ribbon automatically.

### Decisions recorded here

- **D1 — Two real gates.** `btnDiagnostics` requires `HasActiveWorkbook`; the
  new `btnOpenLog` requires `LogAvailable`. No third, invented rule.
- **D2 — Diagnostics gating is an interim Phase-1 rule.** Diagnostics reads
  add-in identifiers and works without a workbook, so gating it is a deliberate
  Phase-1 choice to make the required Office gate ("controls enable/disable
  correctly as workbook state changes") demonstrable. **Replacement trigger:**
  R2.x, when genuinely workbook-dependent commands exist and take over the
  workbook-fact gate; Diagnostics returns to ungated at that point.
- **D3 — Invalidate triggers.** `onLoad` (one initial invalidation),
  `WorkbookActivate`, `WorkbookDeactivate`, `NewWorkbook`, and every command run
  through `GanttRibbon`'s boundary. `WorkbookOpen`/`SheetActivate`/`SheetChange`
  are excluded: the three chosen events already cover first-workbook-open,
  workbook switch, and last-workbook-close.
- **D4 — Adapter placement.** All new Office calls live in
  `GanttCreator.Office` (verified: that project's lock file resolves only
  `ExcelDna.Interop`, so the PIA types are unambiguous there). `ExcelDna.Integration`
  and the PIA both declare a *public* `Microsoft.Office.Interop.Excel.Application`,
  so naming interop types in the AddIn compilation is a real CS0433 hazard; the
  AddIn therefore stays interop-type-free and hands the raw application object
  (from `ExcelDnaUtil.Application`) to the Office adapter as `object?`.
- **No new log records.** `RibbonStateService` writes nothing to the rolling
  log, so `AddInHost`'s tested "exactly one open record / exactly one close
  record" contract is untouched and getters stay free of side effects. Office
  gate evidence is visual (plus the DEBUG force-state hook).
- **Fail-open getters.** An unknown, null, or unprobeable control id stays
  enabled: a permanently grey button is a worse failure than a briefly enabled
  one, and `CommandBoundary` still validates at execution time.
- **Snapshot stickiness.** A failed capture (or a throwing ribbon handle) keeps
  the previous snapshot; the Ribbon must never be driven by a transient COM
  failure.
- **Ownership.** The adapter takes no ownership of the Excel `Application`/
  `Workbook` shared roots, force-releases nothing, and removes exactly the
  delegates it added; `RibbonStateService.Reset()` disposes the subscription
  exactly once so `AutoClose` leaves no COM connection behind (feeds R1.6).

## Exclusions

- No worksheet contract, `_GanttCreatorConfig`, or Type catalogue work (R2.x).
- No broader Excel application/workbook/worksheet/shape adapter interfaces
  (R4.1); the two ports added here are deliberately narrow.
- No rendering, `ScreenUpdating`, selection, or application-state scope work
  (R4.2) — the adapter reads one fact and subscribes three events only.
- No sheet-level or selection-level state facts (`SheetActivate`,
  `SheetChange`, protected-sheet state): R2/R4 territory.
- No `.dna` change, no new production dependency, no Core/Raster change.
- No change to `CommandBoundary` or `DiagnosticsService` behaviour.
- No ADR is created: the decisions above are recorded in this file (R1.3/R1.4
  precedent). The dangling "ADR-0006" reference in those work items is a
  separate docs defect and is not bundled here.

## Risk and rollback

Risk: the service sits on every future dynamic-getter path, so a bug there would
grey the ribbon silently; the app-event sink also touches COM lifetime.
Mitigation: guarded entry points with positive tests, fail-open defaults,
snapshot stickiness, exactly-once unsubscribe, and the required Office gate.
Rollback: revert the single feature commit — no schema, dependency, or `.dna`
change; the RibbonX delta is two attributes plus one button.

## Notes during implementation

- Verified 2026-09-14 against installed metadata: `ExcelDna.Integration` 1.9.0
  declares its own **public** `Microsoft.Office.Interop.Excel.Application`
  (assembly = `ExcelDna.Integration`), while `ExcelDna.Interop` 16.0.0 ships the
  real PIA (present in the published output) — hence D4.
- Verified: `Microsoft.Office.Interop.Excel.Application` is an interface
  (`IsInterface=true`) deriving `_Application` + `AppEvents_Event`, with
  `add_`/`remove_` for `NewWorkbook`, `WorkbookActivate`, `WorkbookDeactivate`
  and handler types `AppEvents_*EventHandler`.
- Verified: outside a live Excel host `ExcelDnaUtil.Application` returns `null`
  (child-process probe), so `AutoOpen` wiring and the unit tests take the
  degrade path instead of needing an Excel host.
- Verified: `ExcelRibbon` 1.9.0 exposes no ribbon handle and no `OnRibbonLoaded`;
  `IRibbonUI` exposes `Invalidate`/`InvalidateControl`/`InvalidateControlMso`/
  `ActivateTab*` only. Excel-DNA's own comment (`RibbonUI.cs`) prescribes keeping
  the `onLoad` object and calling `Invalidate`/`InvalidateControl` later.
- Office gate: **Not run** at implementation time — requires VS F5 against
  desktop Excel. To be recorded here by the human operator.
