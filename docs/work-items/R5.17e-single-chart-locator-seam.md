# Work item — R5.17e Single-chart locator seam

- **Status:** Planned, not started
- **Parent:** [R5.17](R5.17-repair-rebuilds-a-missing-data-table.md), section 12
- **Decision:** R5.17 section 12.1 — more than one Gantt chart sheet is possible
  but is a product-contract and schema change, not a recovery slice

## Outcome

Every adapter that today answers "which table is the Gantt table" or "which
sheet is the Gantt sheet" asks one locator instead. With one chart the behaviour
is identical and nothing new is written to the workbook; the seam exists so a
future multi-chart ADR changes one type instead of every adapter.

## Why it is separate

The recovery family (R5.17a–d) deliberately did not thread a locator through the
adapters. A measured search of `src` finds **28 comparison sites across 20 Office
adapters** that compare a table name or the sheet label: 21 compare the data
table name, four compare the Gantt sheet label, and three compare the plot-anchor
name.

A locator with no second implementation and no consumer beyond the existing
single chart is a dead abstraction. The seam therefore lands as its own change
with its own acceptance test — the fake two-chart locator in the design below —
rather than as speculative plumbing inside recovery.

## Design

Core:

- `GanttChartRef`: `ChartId`, `SheetName`, `TableName`, `PlotAnchorName`,
  `SettingsScopeKey`.
- `GanttChartContract`: pure functions mapping a chart reference to the current
  contract values. Today `TableName = GanttTableSchema.TableName`,
  `PlotAnchorName = GanttWorkbookContract.PlotAnchorDefinedName`, and
  `SettingsScopeKey = "workbook"`.

Office:

- `IGanttChartLocator` with `FindActiveChart()`, `FindAllCharts()`, and
  `FindChartForSheet(string sheetName)`.
- `ExcelSingleChartLocator` returns exactly one `GanttChartRef` with
  `ChartId = "default"` and the current contract values. It resolves the table by
  the same walk [`ExcelGanttTableReader`](../../src/GanttCreator.Office/ExcelGanttTableReader.cs)
  already uses.
- The reader, checker, catalogue writer, repairers, refresh orchestrator, and
  commands take a `GanttChartRef` or the locator instead of comparing against the
  literal table name or sheet label.
- The delta cache and protection arming are keyed by `ChartId`; with one chart
  the behaviour is identical, and the seam is where a future per-chart cache and
  per-sheet ownership attach.
- The Ribbon state capture asks the locator for the active chart; with one chart
  it is the same chart.

## Acceptance tests

- The single-chart locator returns the same table, anchor, and settings the
  current code uses, asserted against the contract constants rather than a
  copied literal.
- A fake two-chart locator drives the reader, checker, refresh, and ribbon without
  changing their code, proving the seam is real.
- An architecture test asserts no adapter outside the locator and the contract
  compares a table or sheet label for lookup. This is the guard that stops the
  single-chart assumption creeping back.
- Every refusal the locator can raise has a positive test in the same commit.

## Explicit exclusions

- No `ChartId` is written to the workbook.
- No table name changes and no table-name migration.
- No second Gantt sheet is created by any path.
- No relaxation of the one-visible-Gantt-sheet invariant; that needs the ADR in
  R5.17 section 12.5.

## Stop conditions

- The architecture guard cannot be satisfied without behaviour change: stop and
  report which adapter needs a contract change.
- Any adapter turns out to depend on the literal name for something other than
  lookup (a defined-name expression, a stored setting): record it before
  changing it.
- The owner wants multi-chart product behaviour in the same change: that is a new
  work item and a new ADR, not this seam.
