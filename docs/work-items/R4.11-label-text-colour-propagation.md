## Step 0 probe result (2026-09-28, against the installed interop assembly)

The obligation was "which interop member carries a text colour, and does the host
honour it". Both halves are now **facts**:

| Question | Answer | Evidence |
| --- | --- | --- |
| Where is a text colour on a `TextRange2`? | `TextRange2.Font` → `Font2.Fill` → `FillFormat.ForeColor` → `ColorFormat.RGB` (Int32, read/write) | reflected `office.dll` 16.0.0 |
| Is there a simpler member? | **No.** `Font2` exposes `UnderlineColor` but has **no** `Color`; the fill is the only colour surface on a `Font2` | reflected `Font2` members |
| Does it need `FillFormat2`? | **No** — `Font2.Fill` is `Microsoft.Office.Core.FillFormat`, the same type as the shape fill | reflected |
| Does the write need `Solid()` first? | **Yes.** A text fill inherited from the theme can silently ignore a `ForeColor` write; `Solid()` before the colour is what makes it land | live round-trip, both tests |
| Is the byte order the same as the shape fill? | **Yes.** A five-token probe (`#123456`, `#FF0000`, `#00FF00`, `#0000FF`, `#010203`) had the font fill report the identical packed value as the shape fill for every one | live probe, Office `16.0.20326.20158` x64 |
| Is a theme colour involved? | **No** — `ObjectThemeColor`/`SchemeColor` are never written (R4.6 D3 still holds) | decision D3 |

**Correction found by the live gate, worth recording:** the first run of the new
live test *failed* — it read back `0x123456` where it expected `0x563412`. A
targeted probe showed the production path was correct and the **test helper** was
wrong: it had already byte-reversed the integer and then let the mapper reverse it
again. The mapper was not changed. This is the R4.6 D4 pattern repeating — the
live test caught an error, and the error was in the test.

## Outcome

A delay event's label is rendered in `DelayText` inside its body and `DefaultText`
outside it, and a configured text colour reaches the live Excel font unchanged on
both create and update.

## Context and owed deferrals

Roadmap row: *Propagate label text colour through style resolution, the scene
model, and the Office adapter, activating §17's inside/outside switch.*

R4.6 recorded the gap and deliberately did not close it: the scene had no
text-colour member, so the row had nothing to map. R4.6's own notes make the
`DefaultText` token authoritative; the open question at the time was whether it
needed a new code-owned definition. **It does not** — `DefaultText` (`#000000`)
already exists in `GanttCatalogues.Colours` and in the guide's token table, so no
token was added, extended, or duplicated.

## Governing contracts

- [`../07-GANTT-ENTITY-GUIDE.md`](../07-GANTT-ENTITY-GUIDE.md) — §17 (the delay
  inside/outside switch and its "Tests: inside/outside text-colour switch" line),
  the shared colour token table (`DelayText` `#FFFFFF`, `DefaultText` `#000000`),
  and §22 label placement.
- [`../02-ARCHITECTURE.md`](../02-ARCHITECTURE.md) — scene-first rendering; a
  renderer never recalculates or substitutes a value the scene resolved.
- [ADR-0015](../adr/0015-label-cascade-and-widest-gap-fallback.md) — the delay cascade that
  excludes `Inside` on the escape, which is what makes the switch reachable.

## Decisions

- **D1 — Null means unresolved, not black.** `TextColour` is nullable throughout
  and a null is preserved to the host as "leave the font alone". Substituting
  `DefaultText` in the adapter would restyle every label whose style simply did not
  name a colour, and would do it in the renderer.
- **D2 — The scene decides, per label.** `SceneBuilder` gives the inside label the
  row's own resolved text colour and the outside label the `DefaultText` token, then
  supplies both to the planner's existing `OutsideTextStyle` parameter. The planner's
  switch was already written and already correct; it was unreachable because both
  call sites omitted the argument. No planner logic changed.
- **D3 — A named copy, not `with`.** Every `SceneStyle` member is get-only and
  validated in the constructor, so `SceneStyle.WithTextColour` rebuilds through the
  constructor rather than adding an `init` accessor that would let a copy bypass
  validation.
- **D4 — One colour path.** The text colour reuses the same `OfficeStyleMapper.Map`
  and `ToOfficeRgb` the fill and stroke use, so the three cannot disagree about
  channel order. The live probe confirms the host agrees.
- **D5 — §23 date labels take the outside style.** A date label is anchored Left or
  Right of the bar and is never inside a body, so passing the inside style would
  put a delay event's `DelayText` beside its bar, where it is unreadable.

## Review finding — the golden snapshot hid a real defect (2026-09-28)

Reviewing the pending golden delta before regenerating it turned up a defect
the snapshot could not catch. `DelineatorBuilder.WithWidth` rebuilds a
`SceneStyle` to substitute §24's `DelineatorLinePt`, and it forwarded the
members **positionally** — nine of `SceneStyle`'s ten. `TextColour` is the tenth
optional parameter, so it was dropped silently: a delineator whose named style
declared a text colour rendered with the host's default font colour.

**Why the golden could not see it:** the reference fixture's delineator style
declares no text colour, so there was nothing to lose. The measured delta was a
clean 58 × one added field precisely *because* the affected path had nothing to
change. A byte-for-byte snapshot proves the fixture did not change; it says
nothing about a member the fixture never exercised.

Confirmed with a failing-then-passing test rather than by reading the diff, and
the fix forwards `style.TextColour` explicitly. This is the same failure mode
R4.11 exists to remove, surviving in the one place a style is copied instead of
resolved.
