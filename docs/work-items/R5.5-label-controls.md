## Outcome

label visibility) values into the selected rows' table cells — every
option validated against the selected Type's allowed positions — and
the scene reflects them only after Refresh, pinned by scene snapshots
and Type-specific allowed-position tests for every option.

## Design decisions (behavioural)

- **D1 — Options come from the catalogue.** The control offers exactly
  the selected Type's allowed positions (+ `None`/blank semantics per
  the entity guide); `Custom Activity` options resolve from its style
  (R2.9 registry). No option list is authored twice.
- **D2 — Table write, never shape edit.** The control writes the
  `LabelPosition` cell (or clears it for default) — it never touches
  a generated shape (the architecture's per-entity rule).
- **D3 — Retained after Refresh.** The live gate confirms the chosen
  position survives Refresh (retained settings) and clipping behaves
  per §22 (fallback + warning when no candidate clears).

## Acceptance tests

- **Automated**: Core — option-set projection pins per Type
  (incl. `Custom Activity` via registry); invalid-for-type write
  refusal (**positive test**). Office — exact-cell mutation set;
  refusals. AddIn — control contract; scene snapshots per option
  (each position renders per §12/§20/§24 rules).
- **Office host (Required)** — live: set positions for a span, a
  milestone, a delineator; Refresh; inspect placement, clipping, and
  retention; record host builds.

## Stop conditions (item-specific)

- A position outside the catalogue's allowed set must be offered →
  stop (single-catalogue invariant).
- The control would need to move a label directly → stop (§22 explicit
  precedence + refresh-only).

projection (D1) and pins. Rollback: `git revert`.
