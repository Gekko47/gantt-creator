## 4. Work items (one green commit each, in this order)

### WI-1 — Core: one family authority, one dash contract, one editable-metric set
1. New `GanttEntityFamily` enum (`Activities`, `Milestones`, `Procurement`, `ChartElements`)
   and a code-owned `GanttStyleFamilies` map from style key to family, in `GanttCreator.Core`.
   The family is a **presentation grouping** of the code-owned presets, transcribed from the
   entity guide's own sections — it is **not** a workbook column, so no schema or hash change.
   - `CustomActivity` → `Activities`; `CustomMilestone` → `Milestones`;
     `DefaultDelineator`, `Splitter`, `Spacer` → `ChartElements`.
2. `ThemeStyleEdit` gains an optional `StrokeDash` member: `null` means "not carried — keep
   the code-owned preset", which is the same rule the custom-style members already follow.
3. `ThemeEditRequest.EditableMetrics` is trimmed to the metrics the dialog actually offers
   and the renderer honours: `GanttRowHeightPt`, `SplitterHeightPt`, `SpacerHeightPt`,
   `GridLinePt`, `MajorBoundaryPt`, `MilestoneSizePt`, `DelineatorLinePt`. `ActivityHeightPt`,
   `StandardOutlinePt`, `HatchPitchPt` and `HatchLinePt` leave the set (F3, F7).
4. Tests: every preset maps to exactly one family and the four families are all present
   (the "no duplicate heading" guarantee is now a property of the data, not of the render
   order); an undefined dash is refused; the editable-metric set equals the expected set.


### WI-3 — Core/Scene: a user-authored style's milestone size overrides the chart metric
1. `SceneBuilder` resolves the milestone size per row: a **user-authored** style's own
   `MilestoneSizePt` wins when it is greater than zero, otherwise the chart-wide
   `request.MilestoneSizePt` applies. Built-in styles always follow the chart metric, so
   the chart knob stays live for them (D2).
2. The custom-style editor's **Milestone size** starts at `0` and is labelled
   "0 = use the chart's milestone size", so the chart-wide metric remains the default and
   the per-style value is a genuine override.
3. Tests: a custom-milestone row with a non-zero style size renders at the style's size; a
   zero style size renders at the chart metric's size; a built-in milestone always renders
   at the chart metric's size.
4. **Defect found while implementing WI-3:** the milestone pass listed only the four
   built-in milestone types, so a **Custom Milestone row rendered no diamond at all** — it
   took a lane, a height, a label priority and a row height, and then no marker was built
   for it. `CustomMilestone` is now in that pass, so a custom milestone reaches the same
   marker builder as every other milestone. The Custom Activity and Custom Milestone
   types were added in R5.6a; this pass was left behind by that change.

### WI-4 — AddIn: the Entity styles tab becomes master–detail
1. A `ListView` (grouped by `GanttStyleFamilies`, one `ListViewGroup` per family) on the
   left; a property panel on the right showing **all** of the selected style's properties:
   Fill, Outline, Label, Fill pattern, Line type, Outline width, Bar height / Milestone
   size, and Default/Permitted label positions.
2. Code-owned properties (the general dash, the outline width, the bar height, the pattern,
   the label vocabulary) are shown **read-only** with a note that they are fixed by the
   built-in style. The **Delineator** is the one built-in whose **line width** and **line
   type** are editable.
3. The swatch beside each colour is driven by a **dictionary** (`_colorSwatches`) rather
   than a control-tree walk, so it shows the current workbook colour (F2). The chart-chrome
   swatches are fixed the same way.
4. Tests: one family heading per family and no duplicates; the swatch shows the workbook's
   colour, not the default; the delineator's line-type combo reaches the emitted edit; a
   code-owned property is not editable.

### WI-5 — AddIn: the Chart tab offers only live knobs, and Reset restores the presets
1. The Chart tab's groups become: **Rows and lanes** (`GanttRowHeightPt`,
   `SplitterHeightPt`, `SpacerHeightPt`), **Grid** (`GridLinePt`, `MajorBoundaryPt`),
   **Milestones** (`MilestoneSizePt`), and **Chart appearance** (the chrome colours).
   The "Hatch spacing" group and its explanatory note are **removed** (F7). The inert
   "Bar height" and "Outline width" rows are removed (F3).
2. `Reset to default` restores the code-owned preset values for the built-in styles — the
   fill, stroke and label colours from `GanttCatalogues.GetPreset` — and the catalogue
   defaults for the chart metrics and the chrome colours (D4).
3. Tests: the Chart tab exposes no hatch-spacing control and no inert metric; Reset
   restores the preset colours rather than blanking them.

### WI-6 — AddIn: the Custom styles tab is rebuilt with layout containers
1. Every absolute `Location`/`Size` in the tab is replaced by layout containers
   (`TableLayoutPanel`, `FlowLayoutPanel`, `SplitContainer`), so the controls cannot
   overlap, cannot be clipped, and the tab never needs a horizontal scroll bar. The
   client area is widened to fit the master–detail view.
2. The master–detail shape matches the Entity styles tab: style list on the left, the
   selected style's properties (Fill / Outline / Label / Size) on the right. The "New
   custom style" row and the Delete button get their own rows, so neither can overlap
   another control.
3. The dialog's chrome follows the Excel theme: the system UI font, system colours, a
   sensible tab order, and the warning label at the default font size.
4. Tests: no control on the Custom styles tab extends past its parent group's bounds; the
   tab reports no horizontal scroll requirement; the New/Delete flow still works.

## 5. Exclusions

- No new workbook column, no schema version bump, and no catalogue-hash change: the family
  is a presentation grouping, the dash column already exists, and the metric table's
  columns are unchanged.
- No new dependency. The dash is written through the already-verified
  `LineFormat.DashStyle` member; the renderer and the scene are untouched.
- No change to entity geometry, label placement, z-order, the validation contract, or the
  per-row override model.
- No change to the custom-style schema: the tab keeps its current property set.
- No PNG or PowerPoint work — those renderers do not exist in this codebase yet.

## 6. Stop conditions

- Stop if the reader cannot project the dash column without weakening the built-in
  catalogue check.
- Stop if the milestone override cannot be scoped to user-authored styles, because that
  would let a built-in style's stale value shadow the live chart-wide metric.
- Stop if the layout work needs a new UI dependency.

### Post-commit visual regression (follow-up commit, WI-4/WI-6)

The modernised dialog shipped green on structure but did not match the approved
screenshots: the Chart tab rendered, and both master-detail tabs did not. All five causes
were **layout-only** — the scene, theme, catalogue and request model were untouched.

| # | Defect | Cause | Fix |
|---|--------|-------|-----|
| V1 | The Entity styles list showed its family headings and **no rows at all**. | `View.Details` with **no `ColumnHeader`**. A Details-view `ListView` paints no items when it has no column, and `HeaderStyle.None` suppresses only the header, not the column. | One column is added, sized from the master column's minimum width. |
| V2 | Every property group (Fill/Outline/Label/Size, on both tabs) collapsed to a **6px** sliver. | An `AutoSize` `GroupBox` resolves its preferred size by measuring its children, and a **docked** child is laid out *from* the parent's size instead — which measures as empty. The group was left with its border alone. | The property tables are undocked (`DockStyle.None`) so they report a real preferred size; the groups keep their `AutoSize` height and gain a `MinimumSize` width, restoring the intended 380px (Entity) and 420px (Custom). |
| V3 | The master column rendered **121px** wide, not the intended 240/250. | `SplitterDistance` was assigned in the object initializer while the split was still at its 150x100 design size, so it clamped to `150 - 4 - 25 = 121`; `FixedPanel.Panel1` then froze that crushed width for the life of the dialog. `Panel1MinSize` does **not** repair it — the control only honours a minimum when the splitter moves, and it never moves on its own. | `PlaceMasterColumn` sets the distance on the first `SizeChanged` at which the split is wide enough, then unsubscribes, so a later user drag still wins. `Panel1MinSize` now only floors that drag. |
| V4 | The Custom tab's **New custom style** button was clipped away entirely — its right edge sat at 249px inside a 113px row. | A `FlowLayoutPanel` laid the autosized button out past the (crushed) column edge; with `WrapContents = false` it clipped rather than reflowed. | The New row is a two-column `TableLayoutPanel`: the key box is the flexible column and the button owns an autosized one, so the button lands inside the column at any width. |
| V5 | The Entity detail panel showed the empty-state hint **twice**, and the hint never left after a style was chosen. | A second, grey `title` label was built *after* `_entityStyleTitleLabel` and was never updated by the selection handler. | The second label is gone. The single title opens on the muted hint and takes the selected style's name and the normal text colour. |

The tests pin **geometry**, which is the class of assertion the 26 structural tests
already green could not express. They need real layout, and a handle-less `TabControl`
sizes nothing — its pages sit at 200x100 and the `SplitContainer` inside at 184x84 — so
`LayOutTab` creates the hidden window handles before laying the page out, and the
assertions compare against measured bounds rather than remembered ones.

Observed after the fix: master column 121 -> 240px; New button right edge 249 -> 232px,
exactly its row's width; groups 6px -> 380/420px. AddIn **503/503**, `verify-quick.ps1`
**PASS** (Release `-warnaserror` build, format, Pester, non-Office suite).
Office host gate and the human visual check of the dialog: **Not run** — the bounds are
proven headlessly, pixels are not.
