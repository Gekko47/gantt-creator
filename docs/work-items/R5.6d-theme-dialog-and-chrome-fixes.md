## 2. WI-A — the label dropdown falls back to the type's default style

### Cause

`EntityTypeCatalog.GetAllowedLabelPositions` resolves a style-key type's label
vocabulary **only** from the row's style in the registry:

(The excerpts below are shown in a `~~~` fence: `scripts/check-status.ps1` reads
every ``` fenced block in a work item as an *evidence command* and resolves the
paths it names, and a C# excerpt is not a command.)

~~~csharp
if (definition.RequiresStyleKey)
{
    if (styleRegistry is null
        || !styleRegistry.TryGet(styleKey, out GanttStyleDefinition? style)
        || style is null
        || style.AllowedLabelPositions is null)
    {
        return [];        // <- empty: the dropdown has no options and is disabled
    }
    allowed = style.AllowedLabelPositions;
}
~~~

A row whose `StyleKey` is blank, or names a style that was deleted, therefore has
**no** label positions, so the ribbon's description-label dropdown is disabled.
`ExcelLabelPositionMutator` refuses the same state with `StyleUnknown`.

The type already has a code-owned default style (`CustomActivity` /
`CustomMilestone`) and the scene already falls back to it, so the row renders —
the ribbon simply does not know that.

### Fix

- `EntityTypeCatalog.GetAllowedLabelPositions` — when the registry does not know
  the row's style, resolve the vocabulary from the type's **code-owned default
  style preset** (`GanttCatalogues.TryGetPreset(definition.DefaultStyleKey)`),
  and only then from the type definition.
- `ExcelLabelPositionMutator` — a style-key type whose row style the registry
  does not know is **not** refused; the position is validated against the same
  fallback vocabulary.
- `RibbonStateService` — the capture resolves through the same call, so the
  dropdown is populated.

### Acceptance

- A Custom Activity row with a blank `StyleKey` offers the default style's label
  positions and the dropdown is enabled.
- A Custom Activity row naming a deleted style behaves identically.
- A Custom Activity row naming a live custom style offers **that style's**
  vocabulary (unchanged).
- A position outside the resolved vocabulary is still refused.

### Delivered

`EntityTypeCatalog.GetAllowedLabelPositions` resolves a style-key type's
vocabulary from the row's style when the registry knows it, and from the type's
**code-owned default style preset** otherwise — the same preset the scene falls
back to when it renders the row. A style the registry *does* know stays the
authority.

`ExcelLabelPositionMutator` validates the position against that same resolved
vocabulary, so a row whose style was deleted still accepts a label.

The `LabelPositionMutationRefusalReason.StyleUnknown` outcome was **removed**:
with the code-owned fallback in place it had no producer left. The registry
rejects a style that permits no position (`GanttStyleRegistry` ctor: "Style
label capabilities must contain defined positions"), every catalogue type
defines at least one, and a style the registry does not know now falls back —
so a position outside the resolved vocabulary is the ordinary
`PositionNotAllowedForType` refusal. `StyleKeyMutationRefusalReason.StyleUnknown`
is a **different** enum (the style-key mutator's) and is unchanged.

Tests: Core +2 (both style-key types fall back to the type default; a known
style still wins), Office contract +1 (an unknown style key writes a fallback
position) with the old refusal test replaced by a not-permitted-position
refusal, AddIn +2 (the dropdown is enabled and offers the fallback set for a
Custom Activity and a Custom Milestone with no style).

## 3. WI-B — the chart-appearance settings pipeline

### Cause (a) — the settings Value column is never formatted as Text

`ExcelConfigCatalogueWriter.WriteOrReplaceTable` formats the settings table's
Value column as Text so that free text (the plot dates) survives Excel's locale
coercion. The guard is stale:

~~~csharp
if (listColumns is not null && listColumns.Count >= 3)   // the table has TWO columns
{
    ListColumn? valueColumn = listColumns[2];             // 1-based: the Value column
~~~

`GanttCatalogues.SettingsHeaders` is `["SettingKey", "SettingValue"]` — two
columns — so `Count >= 3` is never true and the formatting never runs. A value
such as `10/01/2025` is therefore written into a General-format cell, Excel
re-reads it under the host locale and stores a serial, and the next read returns
a number the parser cannot interpret.

### Cause (b) — two different colour rules

`ColourHex.TryParse` accepts a 7- or a 9-character `#RRGGBB`/`#RRGGBBAA` value
and trims whitespace. `GanttColourToken.IsValidHex` accepts exactly 7 uppercase
`#RRGGBB` characters. The dialog's own pre-check uses the lenient rule, the
writer's validation uses the strict one, so a value the dialog accepted is
refused later with a message the user cannot reconcile; and the swatch is
painted with `ColorTranslator.FromHtml`, which reads 8 digits as ARGB and so
shows a different colour from the one typed.

### Fix

- `WriteOrReplaceTable` — guard on `listColumns.Count >= 2` so the Value column
  is formatted as Text.
- `ThemeSettingsForm` — validate every colour text box (style, custom style and
  chart chrome) with `GanttColourToken.IsValidHex`, the same rule the writer and
  the reader use, and paint the swatch from the strict parse.

### Acceptance

- A settings write leaves the Value column in Text format, so a plot date
  round-trips unchanged.
- A colour the writer would refuse is refused **in the dialog**, naming the
  field, and the swatch shows the colour that will be stored.

### Delivered

`WriteOrReplaceTable` guards on `listColumns.Count >= 2` — the settings table
has **two** columns, so the Value column is the second one — and resolves it
through the writer's existing `GetColumnAt` seam. The Text formatting itself
moved into a new `ApplyTextFormat` seam, so a contract test can observe it
without a live Excel.

The chart-appearance editors are the **only** path that rewrites the settings
table (`WriteTheme` writes styles, metrics and settings together), which is
why the missing Text format surfaced there: every chart-colour edit rewrote
the plot-date settings into General-format cells, Excel coerced them by
locale, and the sheet showed the coerced values.

`ThemeSettingsForm` now validates every colour text box — the built-in
styles, the custom styles and the chart chrome — with
`GanttColourToken.IsValidHex`, the same rule the writer and the reader use,
and paints the swatch from that strict parse instead of
`ColorTranslator.FromHtml` (which reads eight digits as ARGB and so showed a
different colour from the one typed). Surrounding whitespace is trimmed
before the check, so a stray space is not a hard error and the trimmed value
is what the workbook stores.

Tests: Office contract +1 (a write formats the settings Value column as Text
and no other column), AddIn +1 (an eight-digit chart colour — the form the
writer refuses — is refused in the dialog, which stays open and produces no
request).

## 4. WI-C — the default label position is limited to the allowed set

### Cause

`_customDefaultLabelCombo` is populated with every label position, while
`_customAllowedLabelList` holds the permitted subset. Nothing keeps the two in
step, so a default can be chosen that the style does not permit — and the
writer's own rule is that the default must be in the allowed set.

### Fix

- The default-position combo is populated from the **checked** items of the
  allowed list.
- Changing the allowed set rebuilds the combo; if the current default is no
  longer permitted it is moved to a permitted position (or to none) so the edit
  never carries an inconsistent pair.

### Acceptance

- The default combo offers exactly the allowed positions.
- Unchecking the current default moves it to a permitted position.
- The emitted edit satisfies "default ∈ allowed".

## 5. WI-D — uniform borders around the title and the table

### Cause

Three owners draw the Gantt's edges and none of them agree:

| Edge | Owner | Appearance |
|---|---|---|
| The chart frame (four sides of the plot area) | `FrameBandsBuilder.AddOuterFrame` — the frame theme's **major-grid** style | the soft grey |
| The data table's cell borders | Excel's own **table style**; the add-in never sets them | a different line |
| The chart title | an owned textbox shape (ADR-0043) | no border at all |

The frame's top edge is also drawn at `chartBounds.Top`, which is the top
padding row — **below** the reserved title row — so the title sits outside the
bordered block.

### Fix

- The live data table's borders are set by the add-in to the same colour and
  width as the chart frame's border, so one token owns every edge.
- The frame's top edge is lifted to the top of the chart title, so the border
  wraps the title as well as the table.

### Acceptance

- Every border the Gantt draws is the same colour and the same width.
- The title sits inside the bordered block.
