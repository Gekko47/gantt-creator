# Work item — R5.15 managed worksheet protection feasibility

> **Guide status**: Proposed proof-first work item, 2026-10-31. Depends on
> R2.7a destructive-command policy, R4.7C column ownership, and R5.11
> refresh/write behavior. This spike does not authorize production adoption.

## Outcome

Determine whether the add-in can protect the single visible Gantt worksheet
so only approved authoring cells and user actions remain editable, while
Excel-DNA safely maintains locked engine columns, derived values, table
structure, filtering/sorting, outlines, validation, shapes, and chart layout.
Return reproducible Excel-host evidence and an ADR decision. If protection
cannot meet those needs, retain the unprotected sheet with preventive ribbon
gating and validation. Do not move activity rows or engine metadata into
`_GanttCreatorConfig`.

## Current constraints

- `AGENTS.md` allows exactly one visible worksheet and one `xlSheetVeryHidden`
  `_GanttCreatorConfig` sheet. The config sheet stores catalogues, styles,
  metrics, options, and metadata, never activity rows or engine row values.
- `GanttTableColumns` classifies engine-managed and user-authoring columns,
  but its current comments say the worksheet is not protected; `Locked`
  classifications have no effect until protection is enabled.
- ADR-0008 D4 and R2.7a currently require guard-first mutation and refuse
  protected target sheets. Any add-in-owned protection needs an explicit
  ownership-aware ADR amendment, not a bypass of that guard.
- Verify `Worksheet.Protect`/`UserInterfaceOnly` behavior against installed
  Excel-DNA/Office metadata and supported Excel hosts. Do not assume UI-only
  protection survives close/reopen; prove any reapplication lifecycle.
- Worksheet protection reduces accidental edits; it is not a security or
  confidentiality boundary.

## Proof plan

1. Inspect installed interop metadata for protection members and parameter
   types; record Excel version/build.
2. In a disposable workbook, test exact editable/locked ranges; add-in writes
   to locked cells; table resize, insert/delete, sort/filter; Type validation;
   outline expand/collapse; shape create/update/delete; and chart-anchor/layout
   reads.
3. Close/reopen and test whether UI-only behavior persists. If it does not,
   test reapplication during workbook activation before enabling edits.
4. Prove the add-in distinguishes its own protection from a user's existing
   protection. User-owned protection remains untouched and receives typed
   no-mutation refusal.
5. Exercise failures and verify application-state restoration, guard-first
   behavior, no partial mutation where preventable, and one actionable
   feedback path.
6. Record an ADR decision: proceed with a narrowly scoped add-in-owned
   protection adapter, or retain current unprotected workflow and preventive
   controls. Do not treat a password as a security control.

## Acceptance criteria

- Live Office evidence records host build, exact ranges, allowed/refused
  operations, reopen behavior, and failure behavior.
- Existing user protection is never removed or replaced.
- Required add-in writes and Excel operations work deterministically under
  any adopted protection; unsupported commands are disabled.
- The visible table remains beside the chart; no event/engine data moves to
  the config sheet; no additional worksheet is created.
- ADR-0008/R2.7a, architecture, and checklist change only after proof and
  owner decision. Until then, this remains feasibility work.

## Stop conditions

- Adoption requires an unapproved schema, extra worksheet, security promise,
  or Office-version support change.
- Excel-DNA cannot safely mutate the protected sheet without bypassing the
  common mutation guard or exposing an unsafe unprotect/reprotect window.
- Reopen/reapplication behavior cannot be made deterministic.
