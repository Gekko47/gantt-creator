## Design decisions

- **D1 — Tool (D-G3, approved 2026-10-05): Stryker.NET** as a
  `dotnet tool` pinned in `scripts/tool-versions.psd1`, installed by
  the gate step (not a csproj PackageReference). Alternatives
  (hand-rolled mutator) rejected: unmaintained, no report format.
  The version was verified against the installed CLI, not assumed:
  `--since`, `--threshold-high/low/break-at`, and `--project`/
  `--test-project` all exist in 5.0.0.
- **D2 — Changed-code scope, 80%.** The gate runs Stryker against
  `GanttCreator.Core` only, through `GanttCreator.Core.Tests`, with
  `--since origin/main` so the score measures *changed* code. The
  `ThresholdHigh = 80` constant lives in `tool-versions.psd1` and is
  read by the gate — never hard-coded in the script.
- **D3 — Gate shape.** `mutation-gate.ps1` wraps install → run →
  threshold judge → report artifact; wired as a `verify.ps1` step (same
  step name in `ci.yml` for parity). The failure exit code is judged
  after capture — **never `-EnableExit`** (the L10 lesson; the
  `pssa-gate` pattern).
- **D4 — Pester guard.** `mutation-gate.Tests.ps1` asserts: the verify
  step exists and runs after the Core test step; the tool version is
  pinned; the threshold constant equals 80; the report path is
  produced by the harness; no `-EnableExit` usage (pattern-matched).
  Every guard ships with a **positive** test in the same file, per
  AGENTS.md. The guard is written with 20 positive tests; **a green
  run has not yet been observed** — the guard's first observed pass is
  recorded in `docs/STATUS.md` when it happens, and no pass is
  claimed here until one is.
- **D5 — Timing.** The threshold applies **from the next Core change
  after this row lands**; this row archives the baseline and does not
  gate itself retroactively.

## Notes — gate review 2026-11-01

The gate was reviewed end to end after a `verify.ps1` run appeared hung. It was
not hung: on this branch `git diff origin/main...HEAD -- src/GanttCreator.Core`
selects **67 files** (the whole project), so `--since` mutated all of Core —
6,687 mutants in **~43 minutes** (report written 15:45:25, run started about
15:02:30) — and the gate buffered Stryker's output until exit, so nothing was
visible for the whole run. Fixes: a changed-set scope guard (`-MaxChangedFiles`,
default 30) that refuses a whole-project scope with the count and the remedy;
streamed Stryker output; a scored-denominator score line; and the duplicate
tool probe removed. All four are pinned by positive Pester tests.

The fresh whole-Core report measures **77.45%** (3,459 killed / 4,466 scored;
786 survived, 8 timeout, 213 no-coverage, 1,193 compile-error), up from the
76.22% baseline. Weakest files by survived + no-coverage: `GanttRowValidator`
(88+29), `HierarchyMutations` (46+28), `SceneSnapshot` (53+14), `RollingLog`
(48+7), `LabelPlanner` (48+7), `DelineatorBuilder` (43+10),
`GanttCatalogueTokens` (40+11).

Known limitations, recorded rather than fixed: the gate has **no deadline**, so
a deliberate full run must be watched; it mutates **Core only**, so a mutant
killed only by an Office/AddIn test counts as survived; and 18% of mutants are
compile-error, which the score excludes by Stryker's definition.

### Widened test-project set — measured, and kept opt-in

Core-only `--test-project` scores a Core mutant SURVIVED when only an Office or
AddIn test kills it, so the score under-reports the suite. Widening to
`GanttCreator.Core.Tests` + `GanttCreator.Office.ContractTests` +
`GanttCreator.AddIn.Tests` was implemented and measured on 2026-11-01:

| Configuration | Mutants | Wall clock | Cost per mutant |
|---|---|---|---|
| Core.Tests only, whole Core | 6,687 | 43 min | about 0.39 s |
| Widened, `GanttRowValidator.cs` only | 403 | unfinished at 49 min | at least 7.3 s |

`--mutate GanttRowValidator.cs` does scope the run — Stryker reported 4,999 of
6,687 mutants removed by the mutate filter — so the 403-mutant figure is real.
The cost is roughly 19x per mutant, which extrapolates to about 13 hours for a
whole-Core baseline. The widened set is therefore reachable through
`-TestProjects` as an explicit opt-in and is **not** the default; the artefact
it would recover has to be recovered with Core tests instead.

Two measurement details worth keeping:

- the glob form matters: `--mutate "**/GanttRowValidator.cs"` did **not** scope
  the run (it emitted whole-project compile-error warnings), while
  `--mutate GanttRowValidator.cs` did;
- the 1,193 compile-error count was identical in both runs, which suggests it
  is counted project-wide regardless of `--mutate`.

Of `GanttRowValidator`'s 117 open mutants, **59 are message-string mutants**
(`""` / `$""`), and `GanttRowValidatorTests` contains exactly one assertion on
`Message` in 1,300 lines. That is a genuine test gap rather than a measurement
artefact, and it is the next target.

**Progress against that target.** `GanttRowValidatorMessageTests` now pins 14
messages in full, including every interpolated offending value: unknown Type,
duplicate Id, the required-date pair, the single-date rule for a point type,
malformed and unresolvable `ParentId`, the unused `Finish`/`LaneId`/
`StackIndex` warnings (each naming its own field), self-reference reported as a
cycle and explicitly **not** as a depth problem, grandchild depth, the child
cap reporting both count and limit, ambiguous parent, non-owning parent, and
unusable parent. Depth and capacity expectations are built from
`EntityHierarchyCatalog` rather than hard-coded, so the assertions test the
interpolation rather than the constants.

**Measured 2026-11-01, with Excel closed.** A scoped run over
`GanttRowValidator.cs` on `GanttCreator.Core.Tests` reduced that file's open
mutants from **117 to 86** — **31 killed** — with message-string mutants
falling from 59 to 36. That is 31 of the 114 killed mutants the branch needs to
reach the pinned 80%: the technique works, and it is not sufficient on its own.

Two cost facts came out of the same run:

- `--mutate GanttRowValidator.cs` cut the *tested* set to 403 of 6,687 mutants
  but did **not** cut wall clock: the run still took about 50 minutes, because
  Stryker generates and compile-checks every mutant in the project before it
  applies the mutate filter. The `SceneBuilder.cs` compile-error warnings and
  the "4999 mutants ... Removed by mutate filter" line are the evidence.
  Scoping by file buys precision, not time.
- That fixed cost is also the honest explanation for the widened test-project
  result: the widened set added per-mutant test time on top of an already
  roughly 40-minute fixed cost, which is why 403 mutants exceeded 49 minutes.

**Corrected later the same day — the 50-minute figure was the working-directory
defect, not generation cost.** These runs were invoked from the repository root,
so Stryker discovered 3,470 tests and ran the live-Excel integration suite for
every mutant. A Core-only run from the Core project directory tests a file in
2-4 minutes (602 mutants in about 4 minutes; 110 in 2 m 41 s), so generation is
a small fraction of the run and scoping by file *does* buy time. The widened
set's 49-minute non-finish is likewise inflated by the same cause and needs
re-measuring before it is used as a cost argument; the default stays Core-only
regardless, because the gate must not depend on a live host.

### Open question: the `NoCoverage` classification is not trustworthy here

The re-measurement leaves **52 `NoCoverage` mutants** (24 in the validator, 28 in
the hierarchy planner) in the score denominator, which drags the score down. At
least one cluster is provably executed by a passing test:

- the report's stored source for `GanttRowValidator.cs` is byte-identical to the
  working file at the reported line numbers (1,258 lines, same text at 342-347),
  so the line numbers are not stale;
- `Delineator_lane_and_stack_are_warned_and_cleared` builds a Delineator row with
  a `LaneId` and a `StackIndex`, passes, and asserts exactly the `NotUsedByType`
  issues that lines 342-347 and 376-381 emit;
- `GanttRowValidatorMessageTests` pins the message text at those same lines.

So Stryker's `NoCoverage` verdict for these multi-line `Add(...)` argument spans
contradicts the test evidence. Both explanations still on the table are
instrument artefacts (sequence points merged or absent for the argument spans
inside a local function) and neither has been proved. **Practical consequence:**
treat the 52 as *unverified* rather than *untested*, and treat the 76.76% score
over the mutated files as a lower bound. Do not spend test effort on them until
the classification is understood.

The glob observation needs the same correction. A literal `--mutate` glob
matches only a file in the **project root**: `--mutate SceneSnapshot.cs` matched
nothing and produced a report with zero SceneSnapshot mutants, while
`--mutate Scene\SceneSnapshot.cs` matched. The whole-project compile-error
warnings seen with `**/GanttRowValidator.cs` are the project-wide 1,193 count,
not evidence that the glob failed.

### HierarchyMutations — 74 open mutants to 52

`HierarchyMutationsBehaviourTests` (17 tests) asserts the returned plan exactly:
window and swap indices, body indices, and the dense sibling-order write
sequence, including that a promotion emits `0` then `1` and never `0` then `-1`,
and that a demotion's existing child keeps order `0` unwritten while the
selection takes the tail slot. Measured effect: **74 → 52 open mutants, 22
killed**.

Of the 52 that remain, **21 are unreachable rather than untested**.
`PlanDemoteToChild` filters candidates with `MayOwnChildren` *before* testing

types for which the private `IsSpan` returns `true`. So `!IsSpan(candidate.Type)`
in the `ParentNotSpan` refusal is always false, and the nine `false` arms of the
`IsSpan` switch plus its default can never be reached. That is 18 boolean
mutants, the two logical/equality mutants on that line, and one negated-
expression mutant.

Recorded as a **dead defensive branch, not a test gap**. Removing it is a
separate decision: the check documents the intended rule even though the
catalogue currently makes that rule impossible to violate, so it is left in
place rather than deleted to improve a score.

Running total against the 114 killed mutants needed for the pinned 80%:
**31 (validator) + 22 (hierarchy) = 53**.

### SceneSnapshot — characterised, not yet worked

`SceneSnapshot` carries **67 open mutants, 51 of them string mutants**. The
class is specific: they are the field-name literals passed to
`Required(value, "field")` / `RequiredFinite(value, "field")` /
`RequiredInt(value, "field")`, the five primitive `Kind` literals
(`"rect"`, `"line"`, `"polygon"`, `"text"`, `"group"`), the three owner-kind
literals (`"row"`, `"chart"`, `"rows"`), and the diagnostic texts such as
`"Invalid z-layer {value}."`.

Consequence for test design: a serialise/deserialise round-trip kills the
`Kind` and owner-kind literals (8 mutants) but **cannot** kill a field-name
literal, because a successful round-trip never reads one. Those need
deliberately corrupted JSON — one fixture per failure path, asserting the exact
message, e.g. `"Missing scene field 'bounds'."`. That is roughly 20 fixtures,
and it is the next batch for this file rather than something a round-trip test
can cover.

Recorded here rather than attempted: hand-building those documents has to match
the document schema exactly (`UnmappedMemberHandling.Disallow` rejects any extra
property), so each fixture is a deliberate, verifiable artefact rather than a
guess.

**Both batches landed** (`SceneSnapshotMessageTests`, 27 tests): the all-kinds
round-trip plus 19 field/value message pins, all via `JsonNode` surgery on the
serializer's own output. Core suite 1823/1823 under `dotnet test`.

### OPEN DEFECT — two tests fail under Stryker but pass under `dotnet test`

The follow-up scoped probe over `SceneSnapshot.cs` produced **no measurement**:

```text
[21:30:35 WRN] 2 tests are failing. Stryker will continue but outcome will be impacted.
[21:41:16 WRN] It looks like all mutants with tests were ignored. Try a re-run with less ignoring!
[21:41:16 WRN] It looks like all mutants resulted in compile errors.
```

The report contains **zero `SceneSnapshot` mutants**, so the run measured
nothing and no kill delta can be claimed for these 27 tests. The suite passes
1823/1823 under `dotnet test` in the same Release configuration, and the
previous hierarchy probe (which ran after `HierarchyMutationsBehaviourTests`
landed) reported no failing tests — so the two failures appeared with the
`SceneSnapshotMessageTests` batch and only under Stryker's runner.

**ROOT CAUSE FOUND** (`--log-to-file`, `logs/log-20261101.txt`):

```text
[21:50:36 INF] Number of tests found: 3470 for project "<the Core project>". Initial test run started.
[22:00:32 DBG] Initial test run output: "<a test in ConfigRepairIntegrationTests>"
[22:00:32 WRN] 2 tests are failing. Stryker will continue but outcome will be impacted.
```

**Stryker discovered 3,470 tests, not the Core suite's 1,823**, and the failing
ones belong to the Office integration test project. When the initial run has
failures, Stryker stops trusting the coverage map and ignores every mutant's
tests, which is exactly the "all mutants with tests were ignored" line and the
empty report.

**Root cause of the discovery, found afterwards: the working directory, not
`--test-project`.** Two runs of the installed dotnet-stryker 5.0.0 with the same
`--project` and the same single `--test-project`, differing only in working
directory:

| Run from | `IsSolutionContext` | `SolutionPath` | Tests found |
|---|---|---|---|
| repository root | `True` | set | 3,470 |
| the Core project directory | `False` | `null` | 1,823 |

1,823 is the Core suite exactly (`dotnet test` on `GanttCreator.Core.Tests`
alone). So `--test-project` does select which projects run per mutant, but
**discovery follows the working directory**: from a directory that holds the
solution file, Stryker enumerates the whole solution's tests. The probes that
produced the 3,470-test runs were ad-hoc invocations from the repository root;
`mutation-gate.ps1` already ran from the Core project directory, so **the gate
itself was never affected by this**.

**CORRECTION — the failures are not "no host".** The first reading of this log
concluded the integration tests could not pass with Excel closed. Running that
project directly disproves it. Observed, in the `ConfigRepairIntegrationTests`
class:

- the test completed in about 15 seconds with a **real** COM workbook and real
  findings — the fixture did start a host;
- the failure is an assertion on the **confirmation-skipped count**: the test
  expects **2**, the repairer returned **1**;
- standard output before the failure read
  `Identity findings before repair: PlotAnchorDisagreement, IdentityDamage`.

**Investigation conclusion: the implementation is right and the expectation is
stale.** Evidence, in three steps:

1. `ConfirmationSkippedCount` is not a cell count. `ExcelConfigRepairer` sets it
   to `plan.ConfirmRequiredFindings.Count` and returns immediately when the
   caller declines — so it counts *confirm-required findings*, not rewritten
   cells.
2. The fixture yields exactly two findings, and the test's own output names
   them: `PlotAnchorDisagreement` and `IdentityDamage`.
3. `ConfigIntegrityPlan.Classify` (ADR-0011 safe-repair boundary) puts
   `PlotAnchorDisagreement` in **AutoRepair** and only `SchemaVersionOlder`,
   `IdentityDamage`, a styles-table catalogue damage, and
   `UserStyleQuarantined` in **ConfirmRequired**.

So the plan has **one** confirm-required finding and `ConfirmationSkippedCount`
is correctly **1**. Expecting 2 would require `PlotAnchorDisagreement` to be
confirm-required, which ADR-0011 explicitly says it is not.

This is corroborated by the rest of the same test: it asserts the first row
keeps its Id and the second is rewritten — exactly **one** cell — and
`GanttRowValidator` reports `DuplicateId` once, against the non-canonical row,
which is what makes the first row canonical.

The assertion was deliberately left alone pending this evidence; the fix is to
expect **1** and to say why in the test, not to weaken the check. Applied: the
test now expects 1, records the ADR-0011 reasoning, and adds `Assert.Single` on
`ConfirmRequiredFindings` so a future classification change fails there instead
of silently shifting the count. That class is 2/2 green.

**Running the whole integration project exposed a second, more important
result:** 69 of 70 pass in 9 m 34 s. The suite does **not** need a
pre-existing host — it starts Excel itself — so the "live host unavailable"
assumption behind several deferred Phase 5 items is wrong. The one failure is
`AutoRefreshTriggerIntegrationTests.Production_scheduler_renders_a_table_edit_and_updates_the_live_shape`,
which is the **R5.11 scheduler-to-render** case.

**Root cause: a harness defect, not a product regression.** `WaitForShapeTextAsync`
caught only `COMException`, but `Shapes.Item(name)` reports a *missing name* as
`ArgumentException` ("The item with the specified name wasn't found"). The loop
therefore aborted on its **first poll** — before the queued refresh could create
the shape — so the test could never observe a working scheduler however correct
the product was. The catch is now filtered to `COMException or ArgumentException`.

**Result after the fix: the test passes in 16 s, and the whole integration project
is 70/70 in 9 m 42 s.** So the production scheduler *does* render a table edit and
*does* update the live shape — R5.11's headline live evidence now exists and is
green, and the earlier "no host available" deferral of that evidence was simply
wrong.

This is a **newly discovered defect that the gates cannot see**: the test is
tagged `OfficeIntegration`, which `verify-quick.ps1` and `verify.ps1` exclude by
policy (ADR-0001), so nothing in the current gate set reports it. It also means
the Phase 5 exit evidence is missing a failing integration case.

So the defect was **never in the new tests**. Two hypotheses were eliminated on
the way (`GanttScene` has no mutable static state; the failure is not
working-directory dependent — 1823/1823 pass from the Core project directory).

**Consequences, corrected:**

1. The voided probe was an **ad-hoc invocation from the repository root**, not a
   gate defect, so no runsettings or trait exclusion is needed. `mutation-gate.ps1`
   now asserts the project-directory context (`Assert-ProjectDirectoryContext`,
   with positive Pester tests) so a future edit cannot move the invocation back to
   the root and silently turn a 1,823-test run into a 3,470-test one that reports
   nothing.
2. The validator and hierarchy probes produced populated reports, but they were
   also run from the repository root, so their discovery set was the whole
   solution rather than the Core suite. Their kill counts therefore include
   kills made by Office or AddIn tests, and the numbers have been re-measured
   (below).
3. The SceneSnapshot batch was **unmeasured**; it has now been measured
   (below).
4. **The 50-minute probe was an artefact of the same defect.** A Core-only run
   from the Core project directory tests a file in **2-4 minutes**: the
   three-file run below tested 602 mutants in about 4 minutes, and the
   SceneSnapshot run tested 110 in 2 m 41 s. The earlier single-file probe that
   ran for ~50 minutes was root-invoked, so every mutant's test run included the
   live-Excel integration suite. The gate's cost was never inherent.

### The gate cannot build while Excel holds the packed XLL

A scoped re-measurement on 2026-11-01 failed before testing a single mutant:

```text
(ExcelDnaPack target) ->
  MSBUILD : PackExcelAddIn error DNA-426010896: ERROR: Existing output .xll file
<the packed AddIn64 xll in the AddIn publish output> could not be deleted.
(Perhaps loaded in Excel?)
```

`EXCEL.EXE` was running (confirmed by `tasklist`). Stryker builds the solution
for its initial build, the AddIn's `ExcelDnaPack` target cannot replace a
loaded `.xll`, and the run aborts. The earlier successful whole-Core run at
15:02 predates Excel being opened, which is why this is intermittent rather
than constant. It is recorded here as an environment prerequisite of the gate:
**close Excel before a mutation run**, exactly as the Office-host gate requires
the opposite. No code change was made for it, because the correct behaviour is
a loud build failure rather than a gate that silently measures nothing.
