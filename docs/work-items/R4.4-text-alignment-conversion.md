## Design decisions (behavioural)

- **D1 — Consume, never re-measure.** The renderer writes the
  scene's text and positions the shape at the scene's resolved
  `TextBounds`; a contract test asserts no call to any measure API and
  no side change vs the scene's chosen side (**positive test**: a
  scene label placed Left stays Left even when Right looks emptier).
- **D2 — Font from the token.** Family/size/bold map from the
  typography token to the Office font properties; nothing is invented
  between token and property (the full matrix test lands in R4.6).
- **D3 — Alignment mapping is closed, and the constants are the probed
  ones.** The source values are the three `GanttTextAlignment` members
  fixed by
  [ADR-0018](../adr/0018-text-alignment-is-not-a-label-position.md), so
  the mapping table has no fourth case: `Left → msoAlignLeft`,
  `Centre → msoAlignCenter`, `Right → msoAlignRight`. **The original
  spelling in this row (`xlAlignLeft` / `xlAlignCenter` /
  `xlAlignRight`) was falsified** — those members do not exist in the
  installed interop assembly. See "Notes during implementation" for the
  probe and for why the `TextFrame2` path is used.
  The scene resolves the side and the alignment; the renderer maps them and
  never re-derives either. The vertical middle-alignment §2 requires for the
  title is a separate axis and is not part of this mapping. The per-position
  alignment a §22 label arrives with is ADR-0018 D4's rule and is already
  resolved in the scene by `LabelPlanner.TextAlignmentFor` — R4.4 consumes
  that result, it does not reimplement the rule.
- **D4 — Overflow text renders as given.** The ellipsis is already in
  the scene text; the renderer applies no truncation of its own
  (assertion: text passed through verbatim, **positive test** with an
  over-long label fixture).

## Notes during implementation

### Step-0 probe, 2026-09-28 — the alignment-constant question is ANSWERED, and this row's own D3 table was wrong

Reflection over the installed `ExcelDna.Interop` 16.0.0 assemblies
(ADR-0004) establishes the members this row needs:

- **The names in this row's D3 do not exist.** There is no
  `xlAlignLeft`, `xlAlignCenter`, or `xlAlignRight` anywhere in the
  Excel or Office.Core interop assemblies. This is the **same class
  of error ADR-0019 was raised for** — a plausible member name assumed
  rather than probed — and this row's own evidence ledger already
  carried the row as *unknown until probed*. D3 is corrected above to
  the real constants; the behaviour it describes is unchanged.
- **Two text APIs exist and they are not equivalent.** Probed:

  | | `Shape.TextFrame` (legacy) | `Shape.TextFrame2` |
  | --- | --- | --- |
  | Alignment | `HorizontalAlignment: XlHAlign` (`xlHAlignLeft` = -4131, `xlHAlignCenter` = -4108, `xlHAlignRight` = -4152) | `TextRange.ParagraphFormat.Alignment: MsoParagraphAlignment` (`msoAlignLeft` / `msoAlignCenter` / `msoAlignRight`) |
  | Font | `Characters(Start, Length)` → `Excel.Characters.Font`, members typed **`Object`** | `TextRange.Font.Font2`, members typed `String` / `Single` / `MsoTriState` |
  | Text | none — set on the shape | `TextRange.Text` |

**Decision: R4.4 uses the `TextFrame2` path.** The `Font2` members are
strongly typed where the legacy `Characters` path returns `Object` for
`Name`, `Size`, and `Bold`, and this repository treats untyped interop
as a live hazard — R4.2's `Application.Calculation` failure
(`DISP_E_TYPEMISMATCH` on a correctly-typed member) and R4.1's
`Shape.Tag` assumption are both consequences of trusting an inferred
member shape. The deviation from the guide's implied `XlHAlign` shape
is recorded here rather than taken silently.

The scene still resolves the side and the alignment; the renderer only
maps them.
