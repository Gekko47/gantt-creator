## Design decisions (behavioural)

- **D1 — Consume, never re-measure.** The renderer writes the
  scene's text and positions the shape at the scene's resolved
  `TextBounds`; a contract test asserts no call to any measure API and
  no side change vs the scene's chosen side (**positive test**: a
  scene label placed Left stays Left even when Right looks emptier).
- **D2 — Font from the token.** Family/size/bold map from the
  typography token to the Office font properties; nothing is invented
  between token and property (the full matrix test lands in R4.6).
- **D3 — Alignment mapping is closed.** The source values are the three
  `GanttTextAlignment` members fixed by
  [ADR-0018](../adr/0018-text-alignment-is-not-a-label-position.md), and
  the mapping table is now **fixed** (the three-member enum leaves no
  fourth case): `Left → xlAlignLeft`, `Centre → xlAlignCenter`,
  `Right → xlAlignRight`. The Office target is the Excel
  horizontal-alignment constant, one per member.
  The scene resolves the side and the alignment; the renderer maps them and
  never re-derives either. The vertical middle-alignment §2 requires for the
  title is a separate axis and is not part of this mapping. The per-position
  alignment a §22 label arrives with is ADR-0018 D4's rule and is already
  resolved in the scene by `LabelPlanner.TextAlignmentFor` — R4.4 consumes
  that result, it does not reimplement the rule.
- **D4 — Overflow text renders as given.** The ellipsis is already in
  the scene text; the renderer applies no truncation of its own
  (assertion: text passed through verbatim, **positive test** with an
  over-long label fixture).
