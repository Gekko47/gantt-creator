# Work item — R1.4

## Outcome

Every Ribbon command runs through one `CommandBoundary`. A thrown command
produces **exactly one** rolling-log record (deterministic operation ID, command
name, stage, Excel version, exception type, HRESULT, redacted detail) and
**exactly one** user-safe dialog (concise message + operation ID; no exception
text, stack, or paths). Excel remains usable. The boundary is failure-proof: a
log-write or dialog failure degrades and never propagates into Excel.

### Decisions recorded here

- **One boundary, AddIn layer.** `CommandBoundary` is a public sealed singleton
  per Excel session (`Instance`, `SetLog`, `Reset`), mirroring the proven
  `DiagnosticsService` pattern. No Core changes: translation is pure logic, but
  the contract is host-level; the Core/Office boundary stays untouched.
- **Operation ID**: `GC-<yyyyMMdd-HHmmss-fff>-<NN>` in UTC, invariant culture,
  from an injected `TimeProvider` (the repo clock-boundary rule, already used by
  `RollingLog`) plus a per-instance monotonic counter. Deterministic under a
  fixed clock; testable via the internal constructor.
- **One log record** per failed command:
  `CommandError: op=<ID> command=<control ID> stage=ribbon-callback
  excel-version=<x|unknown> exception=<type> hresult=0x<hex> detail=<full
  exception text, redacted by RollingLog>`. Excel version is probed with the
  existing "unknown" degradation (docs/02-ARCHITECTURE.md COM-log rule:
  operation ID, HRESULT, Office build, stage).
- **User-safe translation**: category map (COM failure, permission, I/O,
  cancellation, generic) plus the operation ID; the message never contains the
  exception text, stack, or paths.
- **Dialog**: managed WinForms `TaskDialogPage` (Error icon, one OK button) with
  a MessageBox fallback — the ADR-0006 managed TaskDialog pattern; no P/Invoke.
  No access-key escaping needed (no hyperlink).
- **Failure-proofness**: the log write and the dialog show are individually
  guarded inside the failure path; a double failure still never propagates.
- **Force-failure hook**: committed `#if DEBUG` hook. `CommandBoundary.Run`
  calls `DebugForceFailure.ThrowIfRequested(commandName)`; in Release the
  env-var read is compiled out and `IsRequested` returns `false`. Gated by
  `GANTTCREATOR_FORCE_COMMAND_FAILURE=<commandId>` (e.g. `btnDiagnostics`).
  Pinned by `DebugHookGuardTests` (source scan with a positive control) so the
  guard cannot silently disappear; no behaviour in Release builds.
- **Excel-DNA auto-registration**: no `.dna` change; `CommandBoundary` is a
  plain class, not a callback type.

## Exclusions

- No typed-result pipeline for expected user/data validation errors (R2.5/R2.6
  handle all-errors validation).
- No Ribbon state service / `getEnabled` (R1.5); no shutdown semantics (R1.6).
- No Core, `.dna`, Ribbon.xml, resx, or csproj changes.
- No new NuGet packages (TaskDialog/MessageBox come via the existing
  `UseWindowsForms` desktop-SDK import).
- No Excel or PowerPoint COM calls (HRESULT is only read from the caught
  exception object).

## Risk and rollback

Risk: the boundary is on every future command path, so a bug there would mask
real failures. Mitigation: failure-proof guards are individually tested, and
the Office gate demonstrates the end-to-end failure path. Rollback: revert the
single feature commit; no schema, dependency, or product-contract change.
