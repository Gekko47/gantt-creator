## Step 0 — verify prerequisites

- Every Phase-4+ Office evidence row's host records gathered
  (Windows/Office builds, channels, bitness); the observed set becomes
  the matrix's evidence base.
- The ADR set re-read (0001 runner, 0003 VS baseline, 0005 host) —
  the matrix formalises what those ADRs recorded informally.

## Scope

- The matrix artifact (a doc/table — exact home fixed at Tier-A
  upgrade): each row = Windows build + Office build/channel/bitness +
  machine role (dev/reference/CI runner) + evidence links.
- A machine-readable form if useful for CI selection (decided at
  Tier-A upgrade), validated by a schema/consistency test (**positive
  test**: a malformed or evidence-less row fails).
- The explicit unsupported list (x86? Excel Online? Mac? — each with
  the reason and the roadmap's out-of-scope citations).
- `docs/REPO-MAP.md`, `docs/STATUS.md`, status line.

## Exclusions

- No new support promises beyond recorded evidence (a build nobody
  ran cannot be claimed supported); no CI-runner changes; no ADR
  supersession.

## Design decisions (behavioural)

- **D1 — Evidence, not aspiration.** A matrix row requires an actual
  recorded host run (the Phase-4+ discipline); unrecorded
  configurations go to the unsupported/untested list with the reason.
- **D2 — Reference machines are named roles.** Dev, reference, and
  runner machines are listed with their exact builds; their
  relationship to the perf/golden evidence (R4.10/R8.4) is linked.
- **D3 — The unsupported list is explicit and reasoned.** Each entry
  cites the why (roadmap out-of-scope, no evidence, platform
  constraints) — never a silent omission.

## Acceptance tests

- **Automated — the matrix/schema validation test**: every row
  complete (builds, channel, bitness, role, evidence link); the
  malformed-row positive; the unsupported list non-empty where the
  roadmap excludes platforms.
- **Office host (Required)** — the record step: actual Windows/Office
  versions, channels, bitness, and machine roles recorded from live
  machines (the human/runner does this; it feeds R10.5's manifest).

## Stop conditions (item-specific)

- A claimed-supported build lacks evidence → move it to
  unsupported/untested (D1); never claim it.
- The x86 question surfaces without a decision → stop; the roadmap's
  matrix says "x64 primary; x86 only if approved as supported" — the
  human decides, recorded.

## Risk and rollback

Main risk: over-claiming support — D1/D3's evidence rule is the
guard. Rollback: `git revert`.
