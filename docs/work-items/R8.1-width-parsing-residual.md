## Outcome

`ExportSize` is the single converter from the export composition's bounds
in points to pixel dimensions at 300 DPI. The user-entered width grammar
(`cm`/`in`/`px`), `ExportUnit`, `WidthRequest`, and their tests are
withdrawn by the 2026-11-23 owner ruling: the PNG is the chart's own size,
so no width input exists. The safety limits (`MaxPixelDimension`,
`MaxTotalPixels`) and the single-rounding rule are preserved, and the
re-scoped `ExportSizeTests` pin the points conversion and both limits.

## Revision 2026-11-23 (owner ruling) — width grammar withdrawn

The owner ruled that the PNG export uses the chart's pre-existing fonts and
its own page size/width, with no separate special sizes; the width grammar
this row verified therefore has no consumer and is removed rather than kept
as a dead authority (revision plan §3, D7). `ExportSize.ParseWidth`,
`ExportSize.ParseValue`, `ExportUnit`, `WidthRequest`, and the
`ToPixels(WidthRequest, …)` overload go; one points entry remains
(`ToPixelsFromPoints(double sceneWidthPt, double sceneHeightPt)`) computing
`round(pt / 72 * 300)` per axis with the same per-axis and total limits and
the same single rounding boundary. The preview-feed contract below is
**withdrawn** and its consumer (R8.7) is withdrawn with it. The R8.4 golden
dimensions are reproduced exactly through the points entry, so no baseline
regenerates. The schema version does not move for this row.

## Preview-value feed contract (consumed by R8.7) — WITHDRAWN 2026-11-23

**Withdrawn by the revision above; retained as history.** R8.7's preview
and the width grammar it consumed no longer exist.

The exact type/shape `ExportSize` expects from the R8.7 ribbon preview;
documented here by R8.1 and cited by R8.7 D1/D2. The preview is delegated
math — it must never carry a second formula.

- **Producer members**: `ExportSize.ParseWidth(string input)` →
  `WidthRequest`; `ExportSize.ToPixels(WidthRequest request, double
  sceneWidthPt, double sceneHeightPt)` → `PixelDimensions`.
- **Input grammar**: `"<value><unit>"` with unit `cm` | `in` | `px`,
  case-insensitive. Whitespace around the whole input **and between the
  value and the unit** is tolerated (the unit suffix is stripped and the
  value substring is trimmed independently — pinned by the `"  15 cm  "`
  case in `ParseWidth_accepts_valid_formats`). The value is parsed with
  `CultureInfo.InvariantCulture` and `NumberStyles.Float` (decimal point
  and exponent notation accepted). Zero, negative, empty, unknown-unit,
  and non-finite values raise `FormatException`.
- **Scene-dimension inputs**: the export composition's width/height **in
  points** — finite and strictly positive; their source is the export
  aspect the refresh records (R8.7 D4) or R8.8's pipeline. `ExportSize`
  never reads a worksheet.
- **Constants**: `Dpi = 300`, `CmPerInch = 2.54`,
  `MaxPixelDimension = 65_535` (per axis), `MaxTotalPixels =
  100_000_000` (combined allocation budget; square boundary 10,000).
- **Rounding reading (owner ruling 2026-11-22)**: the pixel height is
  computed from the **unrounded** pixel width and each dimension is
  rounded exactly once at the final boundary via `Math.Round`'s default
  (`MidpointRounding.ToEven`). The architecture's two-line formula is a
  summary; the implementation is normative (checklist A's
  single-rounding-boundary rule).
- **Error contracts**: `FormatException` (parse side);
  `ArgumentOutOfRangeException` (conversion side; messages name the
  limit enforced).
- **Consumer obligations (R8.7)**: build the `WidthRequest`, call
  `ToPixels`, display the returned `PixelDimensions`; the equality pin
  in R8.7's AddIn suite asserts preview == parser output over a table
  of inputs; the live Office check's independent calculation must
  replicate `MidpointRounding.ToEven` or avoid exact-midpoint inputs
  (Excel's `ROUND` is half-away-from-zero and would disagree by 1 px
  at midpoints).
