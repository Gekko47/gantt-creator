# Work item — R1.6

## Outcome

The add-in unloads deterministically: `AutoClose` detaches the one owned COM
event connection first, then writes the close record, then drops every
service's log reference, then disposes the log — and after `AutoClose`
returns no owned resource is live (no reachable event handler, no singleton
holding the log, no open log file handle). The five-cycle Office gate runs
the packaged XLL inside real Excel (`Application.RegisterXLL`) and leaves
no orphan process and no add-in error.

### Decisions recorded here

- **D1 — Detach-first teardown order.** `AutoClose` sequence: (1)
  `RibbonStateService.Reset()` — detaches the workbook-state event
  subscription, drops the ribbon handle and adapter; (2) close record; (3)
  `CommandBoundary.Reset()` + `DiagnosticsService.Reset()` — log references
  are dropped *before* the log is disposed, so no singleton can observe a
  disposed log; (4) dispose the log. Each step is guarded separately so one
  failure cannot block the next; the never-throw contract is unchanged.
- **D2 — Reopen contract.** `AutoOpen` after `AutoClose` re-arms the log and
  every session singleton (Excel-DNA can load/unload/reload an XLL in one
  Excel session). Pinned by a contract test.
- **D3 — Office gate composition.** The five-cycle fixture registers the
  packed XLL each cycle via `Application.RegisterXLL` (verified 2026-09-16
  against learn.microsoft.com/office/vba/api/excel.application.registerxll:
  loads an XLL code resource, registers its functions/commands, returns
  Boolean `True` on successful load). The gate asserts registration
  success, one `open` record per cycle in the add-in log, clean process
  exit, and no orphan.
- **D4 — Disposable spike before commit 2.** `RegisterXLL` behaviour under
  COM automation (Trust Center interaction; whether `Quit()` exits while an
  XLL is loaded) is verified with a one-off spike on the real machine
  before the fixture extension is written. If the spike contradicts D3,
  stop and report — no unreviewed fallback.

## Exclusions

- No RibbonX/`.dna`/schema/dependency/signing change.
- No change to `ExcelApplicationAdapter` ownership semantics (its one owned
  resource — the event subscription — already detaches exactly once).
- No L12 `createdump` root-cause work unless the abort reproduces in this
  gate; the first stop is then `scripts/diagnose-l12-createdump.ps1`.
- No refactor of `DiagnosticsService`/`CommandBoundary` beyond the reset
  order and the `GetLog()` test accessor.

## Acceptance tests

- **Automated** (`dotnet test tests/GanttCreator.AddIn.Tests -c Release`):
  - `AutoClose_detaches_the_workbook_state_subscription_before_writing_the_close_record`
    — sequence `open, subscribe, detach, close, dispose`.
  - `AutoClose_leaves_a_dead_subscription_that_delivers_no_events` — after
    `AutoClose` a workbook-state change invokes no handler and writes no
    record.
  - `AutoClose_drops_every_service_log_reference_before_disposing_the_log`
    — `CommandBoundary.Instance.GetLog()` and
    `DiagnosticsService.Instance.LogFilePath` are null after `AutoClose`.
  - `AutoOpen_after_AutoClose_reopens_deterministically` — records
    `open, close, open, close`; services re-armed after the second open.
  - `AutoClose_releases_the_real_log_file_handle` — the active log file of
    a real `RollingLog` can be deleted after `AutoClose`.
  - All existing AddInHost/RibbonStateService/Office contract tests stay
    green.
- **Office host** (roadmap `Required`): five Excel open/close cycles, each

  `pwsh ./scripts/verify-office.ps1 -DeadlineSeconds 600`; evidence recorded

## Risk and rollback

Risk: reordering `AutoClose` could break the existing close-then-dispose
test expectations or drop a reset that today masks a bug; a failing existing
test exposes behaviour that must be re-decided, not adjusted to fit.
Mitigation: the full AddIn test project runs before commit, and every step
is independently guarded. Rollback: revert the single feature commit — no
schema, dependency, or `.dna` change.
