# Work item — R1.6

## Outcome

The add-in unloads deterministically: `AutoClose` detaches the one owned COM
event connection first, then writes the close record, then drops every
service's log reference, then disposes the log — and after `AutoClose`
returns no owned resource is live (no reachable event handler, no singleton
holding the log, no open log file handle). The five-cycle Office gate runs
the packaged XLL inside real Excel (`Application.RegisterXLL`) and leaves
no orphan process. Historical scope (Commit 2, D3): that commit proved only
the narrowed smoke test — registration success, shared packed-XLL open-record
growth, and owned-process exit — with no record attributed to the owned
instance, no `AutoClose` host evidence, and no complete no-add-in-error gate.
Current outcome (D5 session-token commit, Option A): open-record attribution
is closed — the gate seeds the seen-session set before cycle 1 and requires a
new distinct session token per cycle, and five distinct tokens were recorded
(Office gate PASS 2026-09-17). Three items remain open: close-record
attribution (`AutoClose` produces no `close` record on the `RegisterXLL` +
`Quit()` automation path, so process exit is not `AutoClose` proof); human
review of the Office-gate report in Excel; and the branch-final `verify.ps1`,
push, and CI gates, which are human-gated.

### Decisions recorded here

- **D1 — Detach-first teardown order.** `AutoClose` runs five teardown
  operations, each inside its own catch-bearing `try` (verified against
  `src/GanttCreator.AddIn/AddInHost.cs`): (1) `RibbonStateService.Reset()` —
  detaches the workbook-state event subscription, drops the ribbon handle and
  adapter; (2) the close record; (3) `CommandBoundary.Reset()`; (4)
  `DiagnosticsService.Reset()`; (5) dispose the log (that guard keeps the
  `finally` clearing `_log`/`_sessionToken`). Steps 3 and 4 are guarded
  *independently*, so a `CommandBoundary.Reset()` failure cannot skip
  `DiagnosticsService.Reset()`; both drops happen *before* the log is
  disposed, so no singleton can observe a disposed log; one failing step
  cannot block the next, and the never-throw contract is unchanged. The guard
  shape is pinned by
  `tests/GanttCreator.Architecture.Tests/AddInHostTeardownGuardTests.cs`: the
  three `Reset` calls are non-throwing by contract, so no runtime test can
  make one fail, and the contract is asserted on the parsed `AutoClose`
  source instead — each of the four operations the checker lists (the three
  `Reset` calls plus `LogClose`) sits inside exactly one catch-bearing `try`
  and no two share a guard, with positive controls for the pre-fix
  shared-guard shape and for a deleted step. The log dispose is guarded the
  same way but is not one of the four operations the checker lists.
- **D2 — Reopen contract.** `AutoOpen` after `AutoClose` re-arms the log and
  every session singleton (Excel-DNA can load/unload/reload an XLL in one
  Excel session). Pinned by a contract test.
- **D3 — Approved narrowed commit-2 scope:** retain the registration/process-exit smoke test, not a complete lifecycle gate. Each of five cycles asserts RegisterXLL success, growth in a shared packed-XLL open-record count, and owned-process exit. The approved post-disposal poll deadline is 60 seconds. Neither a growing shared count nor a successful Quit attributes AutoOpen/AutoClose to that owned instance. No close record was observed; deferred initialization is an unverified explanation, not an established fact. Test names/comments claiming per-cycle AutoOpen are smoke-test observations, not lifecycle proof. Production logging remains unchanged.
- **D4 — Disposable spike before commit 2.** `RegisterXLL` behaviour under
  COM automation (Trust Center interaction; whether `Quit()` exits while an
  XLL is loaded) is verified with a one-off spike on the real machine
  before the fixture extension is written. If the spike contradicts D3,
  stop and report — no unreviewed fallback.

## Risk and rollback

Risk: reordering `AutoClose` could break the existing close-then-dispose
test expectations or drop a reset that today masks a bug; a failing existing
test exposes behaviour that must be re-decided, not adjusted to fit.
Mitigation: the full AddIn test project runs before commit, and every step
is independently guarded. Rollback: revert the single feature commit — no
schema, dependency, or `.dna` change.

## Pending work item — R1.6 close-callback attribution

Status: **partially resolved by the D5 session-token commit (Option A,

Done (Option A, commit 3):

- **D5 — correlatable session token** (decision recorded 2026-09-17):
  `AddInIdentity` gains `SessionToken`; `open` gains `session=<token>`;
  `close` becomes `close session=<token>`. The token is deliberately NOT a
  GUID or long hex (Core `Redactor` masks both to `[guid]`/`[token]`,
  destroying on-disk correlation) and NOT the Excel PID (reused across
  cycles, and not observable inside `AutoOpen`/`AutoClose` without a new
  COM call). `AddInHost.GenerateSessionToken` emits a timestamp-prefixed
  12-character random token over an alphabet that excludes `a`–`f`, so it
  survives `Redact` unchanged; pinned by
  `GenerateSessionToken_survives_the_log_redactor_unchanged`.
- Attributable five-cycle Office gate
  (`Five_cycles_registering_the_packed_XLL_leave_no_orphan_and_show_session_open_record_growth`):
  seeds the seen-session set from the log **before** cycle 1 (negative
  control — a foreign record that predates the test cannot satisfy any
  cycle), then requires each cycle to produce a **new** distinct session
  token; the owned-PID orphan poll remains the closing assertion.
- Office gate: **PASS 2026-09-17** (9/9, 5 m 35 s, Excel
  16.0.20326.20144 x64): 13 pre-existing sessions rejected; five new
  distinct sessions, one per cycle; no orphan; no L12 abort.
