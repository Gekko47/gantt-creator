## Amendment — 2026-10-11 (pre-implementation rulings)

- **D1-amended — Move = physical content rotation, not a `SortOrder`
  write.** The original D1 offered "`SortOrder` first; physical row
  moves only if the Tier-A upgrade proves them necessary". The
  evidence closes it in favour of row position: the data panel
  restates the table in `RowNumber` order, the live lanes are
  anchored positionally by body-row ordinal (ADR-0034), and no
  production adapter has ever written the `SortOrder` column (blank
  means "engine has not assigned one", `GanttRowValidator`).
  Writing `SortOrder` alone would move the plot but not the visible
  rows, breaking D3's alignment invariant. Move therefore swaps two
  contiguous windows of full row content (the R5.3 promote/demote
  machinery); IDs and every other cell travel with their row (R2.3).
  *Known limitation (pre-existing, inherited by move):* a non-blank
  hand-set `SortOrder` pins plot order ahead of row order for every
  content-moving command; recorded, not guarded here.
- **D4 — Bounds are a silent success.** Move Up at the top of the
  selection's set (previous top-level group / previous sibling) and
  Move Down at the bottom return success with zero cells written and
  present no dialog ("quietly does nothing"). Infrastructure
  refusals (protected sheet, selection outside table, unreadable
  table) keep the R5.3 typed-refusal messages.
- **D5 — Group/sibling windows.** A top-level selection moves the
  contiguous window of its row plus its contiguous child run past
  the adjacent top-level group's contiguous window (a two-block
  swap; gap rows of a malformed table stay put). A child selection
  swaps with the adjacent row carrying the same `ParentId`; any
  other neighbour is the run boundary → silent no-op. The planner
  resequences the affected run's `SiblingOrder` densely (R5.3 D4);
  no type rules apply because hierarchy relations never change.
- **D6 — Remove deletes the selected row only; its children are
  promoted to its parent** (the owner's ruling 2026-10-11): the
  R4.7A promote-on-delete contract, whose Core planner
  (`HierarchyMutations.PlanPromotion`) exists with no production
  consumer. Remove is destructive under ADR-0008: guard-first
  adapter, Core-pinned warned confirmation ("This change cannot be
  undone."), no undo. It performs **no shape operations** — the
  row's shapes leave with the host row or on the next Refresh
  (Refresh-only rendering contract). This lands R4.7A's Required
  live gate ("delete the parent and observe the children
  promoted") and discharges R2.7a D6's confirmed-destructive run,
  cross-referenced in R2.7a/R5.7.
- **D7 — Ribbon layout.** The Ordering group gains a vertical box
  (Promote, Demote, then a horizontal two-button box: **Up** /
  **Down**); the Data group gains one **Remove** button. Both new
  gates reuse workbook + initialised. The owed deferral from R5.3
  is restated on the XML: later work adds cell tracking
  (`SheetSelectionChange`) and selection-gated `getEnabled` for
  these buttons (R5.10-class).
- **D8 — Row-deletion COM behaviour is a probe-before-code
  requirement** (ADR-0036 discipline): how a body-row delete shifts
  cells, shapes, the table range and the reserved padding row is
  measured by `scripts/probe-delete-row.ps1` before the remover
  adapter relies on any of it.

## Amendment — 2026-10-12 (owner rulings: D9 selection-follows-move; D10 delete-mechanism evidence)

- **D9 — The selection follows the moved row (landed).** Move
  Up/Down puts the selection on the moved row's new position
  (its one-based body index), so repeated moves keep acting on
  the same row; a D4 boundary no-op leaves the selection put.
  `ParentChildMutationOutcome` carries `int? MovedToRowNumber`
  (null when nothing moved) and an extended `Ok` factory;
  `ApplyMove` computes it as `SwapStart + 1` — the selected row
  is first in its window and `BlockSwap` exchanges the windows
  in memory, so the moved row lands on the neighbour's former
  span start (contract assertions: group-up 2→1, group-down
  1→3, child-up 3→2; `null` at both bounds). Both commands
  select through the shared `IInsertedRowSelector` seam (the
  AddRow selector — the sole permitted `Activate()` caller,
  read-only classified), so no new activation or mutating file
  exists; a host selection failure degrades to silence (the row
  moved, only the cursor stays), pinned by injected-selector
  tests for both commands.
- **D10 — Remove's delete mechanism: the seam deletes the whole
  worksheet row (landed 2026-10-12).** The owner's
  2026-10-12 direction: the removed row's chart elements must
  follow the delete without a Refresh.
  `scripts/probe-delete-row-shift.ps1` (live host, 2026-10-12)
  measured a TRUE worksheet-row delete (`Rows.Delete` inside
  the ListObject range): **accepted** — the symmetric
  counterpart of the worksheet-row INSERT ADR-0036 Q2
  measured (also accepted inside the ListObject range, every
  shape following; the "refused insert" was ADR-0035's
  claim, withdrawn by ADR-0036 itself); the table shrinks
  A1:C4→A1:C3 and content shifts up; the shape below the
  deleted row moves up exactly one body-row height (Top
  56→38, TopLeftCell D4→D3, delta −18); the shape anchored IN
  the deleted row is **removed by the host** (Shapes.Count
  3→2 — the probe expected survival; flagged for the owner);
  the reserved 6pt padding row survives directly below the
  table; `AddShape` reports Placement=1 (xlMove), yet shapes
  follow. The production seam originally (`DeleteListRow` →
  `ListRow.Delete()`) instead compacted the table in place: no
  worksheet row shifted, shapes kept their anchors, and an 18pt
  former body row sat below the table instead of the padding
  row (`scripts/probe-delete-row.ps1`) — the live symptom the
  owner reported 2026-10-12 ("deleting the table entries").
  **Landed 2026-10-12** on the owner's confirmation ("it
  should just delete the row"): the seam now deletes the row's
  `EntireRow`, so the worksheet row is removed, the rows below
  shift up with their anchored shapes, the in-row shape is
  host-deleted, and the padding row stays adjacent. D6's "the
  command performs no shape operations" text still holds — the
  host moves the anchored shapes as its own row-delete side
  effect. Pinned by the seam contract test
  (`DeleteListRow_deletes_the_row_s_entire_worksheet_row`);
  the live workbook behaviour is the F5 gate (human-run).
- **D12 — Every mutation regroups the native Excel outline immediately
  (owner direction 2026-10-12).** Promote, demote, Move Up, Move Down
  and Remove previously rebuilt the outline only on the next Refresh,
  so the `-`/`+` controls disagreed with the table until then — the
  reported errors. Each successful mutation now rebuilds the outline
  from the post-mutation table through the existing outline writer
  (`ExcelOutlineGroupWriter` over `OutlineGroupPlanner`), inside the
  same command. Boundary no-ops (D4) write nothing and leave the
  outline untouched; an outline refusal after a landed mutation
  degrades to the pre-D12 behaviour (the mutation stands, the next
  Refresh regroups) rather than failing completed work.
- **D11-amended — Move reverts to content rotation and every move or
  delete triggers a Refresh (owner direction 2026-10-12).** The
  D11 worksheet-row insert+delete relocation was withdrawn after the
  owner's F5 observation and a live probe: the mechanism is
  direction-blind (the LOWER window's rows are always the deleted
  source), so Move Up — where the selection is the lower window —
  host-deleted the moved row's shapes while Move Down appeared to
  keep them (it was the neighbour below that paid). The
  probe-measured alternative, `Rows.Cut(destination)`
  (`scripts/probe-move-row.ps1`, live Excel 16.0), is **refused as a
  swap**: the cut is accepted, the table stays valid, all shapes
  survive — but the destination row's content is OVERWRITTEN
  (`A C B D E` → `A C _ D E`; the window case `B A A1 A2 E` →
  `B A1 A2 _ E`), so Cut destroys a row rather than rotating two.
  The insert+delete control section reproduced the D10 finding (the
  moved row's shape host-deleted, count 5→4, `barRow3` riding the
  insert delta=+18). Move therefore returns to the original content
  rotation — `ApplyMove` always writes the union span and deletes
  nothing (`MoveWorksheetRows`, `RestoreInsertedRows`,
  `InsertWorksheetRow` and their insert-seam tests deleted) — and
  the move/remove commands invoke `RefreshSheetCommand` after a
  successful mutation (`Action? onMutated`, null-in tests): moves
  only when cells were written (a D4 no-op skips), Remove on every
  success (a lone-row delete writes zero cells but changed the
  sheet). The selection moves first so the Refresh's ADR-0020 scope
  captures it and restores it onto the moved row. Promote/demote
  are unchanged (owner asked for move/delete only). Pinned by four
  rewritten move contract tests (rotation: no deletes, union
  content, cell counts) plus nine new AddIn tests (refresh invoked
  once on success, skipped on no-op/refusal/declined-confirm).
- **D13 — A move rotates the worksheet rows' `Hidden` flags with the
  content (2026-10-13).** The reported defect: moving a collapsed
  parent up or down put its content on a still-hidden worksheet
  row, so `LaneRowAnchorResolver` refused with `DegenerateRowHeight`
  and the whole Refresh failed. Root cause, read from source: a
  move is a CONTENT rotation (D11-amended) — `BlockSwap` reorders
  the in-memory cell matrix and `WriteRows` writes the union span
  back; the worksheet ROWS never move. `Hidden` is a property of
  the worksheet row, not of the content in it, so a collapsed
  group's parent content rotated past stale hidden flags. The fix
  reads each union-row's `Hidden` flag, runs the same `BlockSwap`
  permutation over the flags as over the content (so the
  permutation provably matches), and writes the rotated flags back
  — skipping any row whose flag already matches (a no-op move
  never touches the host) and refusing with `WriteFailed` on a
  partial application. Unhiding outright was rejected: it would
  expand the user's collapsed group, which `IOutlineGroupPort`
  deliberately never does. **The accessor is load-bearing:** the
  live probe (`scripts/probe-hidden-row-move.ps1`, Excel 16.0)
  measured `Range("A3:C3").Hidden = $true` as REFUSED with
  COMException `0x800A03EC` while the identically shaped
  `Range("A3:C3").EntireRow.Hidden = $true` was ACCEPTED — the
  same accessor asymmetry ADR-0034 recorded for `OutlineLevel`.
  `SetRowHidden` therefore writes through `EntireRow.Hidden`; a
  plain table-sourced `Range.Hidden` write would fail every
  hidden-flag write on a live host while passing every Moq-based
  test. Pinned by
  `Moving_a_collapsed_group_rotates_its_row_hidden_flags_with_the_content`
  (an asymmetric collapse: moving the collapsed group down past a
  visible neighbour — fails on `DoesNotContain(row, HiddenRows)`
  without the rotation, passes with it) and the Graph fake's
  `HiddenRows`/`HiddenWrites`/`WorksheetRowReads` observability.
  Observed: Office contract 805/805 (+1); live probe Q1–Q4 verdict
  confirmed on Excel 16.0. Checklist: B, I.

## Design decisions (behavioural)

- **D1 — Move = order write, not row shuffle.** Move-up/down adjusts
  the deterministic-order key (`SortOrder` first; physical row moves
  only if the Tier-A upgrade proves them necessary); IDs never change.
  R3.4 re-derives effective stack slots from display position; no command
  writes the visible `StackIndex` compatibility cell.
- **D2 — Collapse is scene exclusion.** Collapsed children are
  excluded from the built scene (their rows remain in the table
  untouched); the parent renders as its roll-up per §10. Expanding
  re-includes them. Both act only through Refresh.
- **D3 — Alignment invariant.** After any command + Refresh, the
  visible data-panel rows and the rendered lane shapes align exactly
  (row/data-panel alignment is §9's test obligation); the live gate
  proves it on the real sheet.

## Amendment — 2026-10-21 (owner ruling; the expand/collapse slice lands)

- **D2-amended — the collapse state is the native Excel outline's, not a
  scene exclusion.** The original D2 ("collapsed children are excluded from
  the built scene; the parent renders as its roll-up per §10") is
  **superseded**. The owner ruled on 2026-10-21 that the current visual and
  function of the collapse behaviour are as intended, and that the only
  missing capability was a Ribbon control that collapses or expands **all**
  the relationships. The native per-group `+`/`-` controls already work
  (R4.7D rebuilds the groups from `ParentId`; R5.13's gate records that
  the native controls "reflect it without Refresh"), so the slice adds the
  missing surface rather than a second collapse mechanism.

  The consequence is that the chart's scene is **unchanged** by a collapse:
  a collapsed child still contributes its bar, exactly as it does under the
  native control. The scene, the geometry, the golden snapshot and the
  entity guide are all untouched by this slice. What changes is the
  worksheet's own row visibility, which is the same state the native
  control writes.

- **D13 — the Ribbon surface is two buttons, not a toggle.** The `Outline`
  group (after `Ordering`) carries **Expand all groups** and **Collapse
  all groups**, each with its own verified icon: `OutlineExpand` and
  `OutlineCollapse`, which the Office 2010 Icons Gallery lists and the
  Excel idMso table names as `button`/`Expand` and `button`/`Collapse`.
  A single toggle was considered and rejected: RibbonX's `imageMso` is
  static, so one of the two states would always show the wrong glyph, and
  a toggle labelled "Collapse" that is *pressed* when collapsed is
  ambiguous. Both buttons are gated on workbook + initialised, like every
  other Data-group button; a sheet with no group is a quiet no-op by
  design, and the command refuses with an actionable message when the
  table is missing.

- **D14 — the mechanism is the child rows' hidden flag, and the
  worksheet-level `Outline.ShowLevels` alternative is rejected.** A live
  probe (`scripts/probe-outline-showlevels.ps1`, Excel 16.0) measured
  both candidates:

  | Question | Measured answer |
  | --- | --- |
  | Q1 scope | **FALSE** — a user's own outline group outside the Gantt table is untouched |
  | Q2 refresh | **FALSE/FALSE** — neither the group pass nor the reset pass re-expands a collapsed group, so a Refresh preserves the collapse |
  | Q3 restore | **TRUE** — clearing the flag expands every group again |
  | Q4 accessor | `EntireRow.Hidden` **accepted**; a plain `Range.Hidden` write is **refused** with COMException `0x800A03EC` |
  | Q5 identical | **TRUE/TRUE** — Excel's own collapse leaves the child rows `Hidden = $true` and the parent `Hidden = $false`, and its own expand reverses it, so the add-in's write produces byte-identical state to the native control |
  | Q6 hand-hidden | **FALSE** — Excel's own expand reveals a hand-hidden row, so the add-in writes only the **grouped** child rows and leaves a row belonging to no group alone |

  `Range.Outline` does not exist on IDispatch (the PIA declares it, the
  COM object does not expose it), so the only reachable `Outline` is the
  **worksheet's**, and `Worksheet.Outline.ShowLevels` is **sheet-wide**:
  it would collapse the user's own unrelated outline groups. The child
  rows' hidden flag is row-scoped by construction and cannot.

- **D15 — the command does not refresh the chart.** Collapsing a group
  changes no model: the hierarchy, the dates and the scene are all
  unchanged, and Q2 measured that a Refresh preserves the collapsed
  state. The command therefore leaves the chart alone, exactly as the
  native control does.
