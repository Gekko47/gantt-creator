# Work item — R5.19

## Outcome

Every actionable control on the Gantt Creator tab shows a Lucide glyph that is legible in whatever Office theme the user has selected: the same geometry is rasterised in a near-black and a near-white palette, and one `getImage` callback picks the pair from the current theme.

## Scope

- `src/GanttCreator.AddIn/RibbonResources/Ribbon.xml`
- `src/GanttCreator.AddIn/RibbonImages.cs`, `RibbonGlyphPalette.cs`, `RibbonGlyphAssets.cs`, `GanttRibbon.cs`, `RibbonStateService.cs`, `RibbonGlyphCatalog.g.cs` (generated)

- `tests/GanttCreator.AddIn.Tests/` (glyph and palette tests; migration of the `imageMso` pins)
- `docs/`, `plans/ribbon-icon-theme-plan.md`

Nothing under `src/GanttCreator.Core/`, `src/GanttCreator.Office/` or `src/GanttCreator.Raster/`.

## Exclusions

- Chart style tokens and chart chrome: R5.6 D1 keeps chart presentation independent of Office themes. The ribbon palette is chrome, not a chart token, and must not be projected into the scene.
- Ribbon layout, grouping, keytips, labels and supertips: settled by R5.16a and R5.9.
- Glyphs for inline `labelControl`, `editBox` and `checkBox` controls, and for the Labels dropdowns.
- A per-entity glyph for each of the 18 menu variants: one family glyph per menu.
- The four Size preset *rows*: `item` has no `getImage`, so they carry no glyph; `ddnSize` carries one instead.
- Any new NuGet dependency, any network access, any drawing at run time.

## Step 0 evidence — measured, not assumed

### Office UI theme value mapping

`HKCU\Software\Microsoft\Office\{version}\Common` → `UI Theme`, `REG_DWORD`. Observed 2026-11-16, one theme change per reading:

| Office Theme | `UI Theme` | Palette |
|---|---|---|
| Colorful | `0x7` | light |
| White | `0x5` | light |
| Dark Gray | `0x3` | dark |
| Black | `0x4` | dark |
| Use system setting | `0x6` | defer to `AppsUseLightTheme` |

The dark set `{3, 4}` matches Microsoft's documented predicate that only Black and Dark Gray are the dark pair ([`Office.ThemeId`](https://learn.microsoft.com/javascript/api/office/office.themeid), [`isDarkTheme`](https://learn.microsoft.com/javascript/api/office/office.officetheme)). No official documentation publishes a numeric mapping; this table is the only authority the code may use.

### Supporting facts

| Fact | Evidence |
|---|---|
| The key is version-scoped: `16.0` has it, `15.0` and the unversioned `Office\Common` do not | `reg query` on all three keys |
| `HKCU\...\Themes\Personalize` → `AppsUseLightTheme` = `0` (dark) on this machine | `reg query` |
| `SystemInformation.HighContrast` returns `False`; `System.Drawing.SystemColors.Window` resolves | PowerShell probe against the referenced assemblies |
| `CT_Item` declares `id`, `label`, `image`, `imageMso`, `screentip`, `supertip` — no `getImage` | `.microsoft/[MS-CUSTOMUI]-250218.docx`, `CT_Item` schema fragment |
| `AG_Image` states that `image`, `imageMso` and `getImage` are mutually exclusive, and is referenced by `CT_DropDownRegular` | same document, `AG_Image` schema fragment |

Two earlier probe runs reported one value for all states because the theme was never changed between prompts; those readings were discarded rather than reasoned from.

### What that observation changed

Excel re-requested the images on the theme change by itself, so **the invalidation watcher planned as Step 11 is not required by the observed behaviour**. ## Decisions

- **D1 — Two palettes, two sizes, generated.** A `light` and a `dark` stroke, at 16 px and 32 px, produced by one script from Lucide geometry on its 24 × 24 view box, stroke width 2, round caps and joins.
- **D2 — One callback.** `GanttRibbon.GetGlyph(IRibbonControl)` serves every static control; the generated `RibbonGlyphCatalog` maps control id → glyph slug and size. The RibbonX `tag` channel was rejected because it depends on host behaviour that cannot be tested in-process.
- **D3 — Resolution order.** High contrast first, then the Office value, then the system value, then light. An unrecognised Office value logs once and falls through to the system branch; it is never guessed.
- **D4 — `getImage`, not `loadImage`.** A theme change mid-session must repaint, and `Invalidate()` re-queries `getImage` reliably.
- **D5 — Neutral strokes only.** No accent colour, so a glyph never competes with an Office accent or a chart colour.
- **D6 — Size carries no glyph at all.** `item` cannot be theme-reactive, and the owner ruled the control itself should stay icon-free: it is a text dropdown beside an inline label, so a picture there only crowds the row.

## Acceptance tests

- **Automated** (`dotnet test tests/GanttCreator.AddIn.Tests`): every control-level actionable and every menu row declares `getImage`; the XML and the generated catalogue agree; slugs are unique outside menu rows; each declared glyph resolves to a committed asset in both palettes and its declared size; `RibbonGlyphPalette` returns dark for `3` and `4`, light for `5` and `7`, defers to the system value for `6`, returns light for an unknown value and for an unreadable key, and prefers the high-contrast branch; an unknown control id returns null without throwing.
- **Automated** (`pwsh ./scripts/check-ribbon-glyphs.ps1`): no `imageMso` remains; every declared glyph exists in both palettes; each PNG is 16 or 32 px; the dominant opaque colour is one of the two approved strokes; no orphan asset. The script self-tests that a fabricated glyph, a missing palette variant, a wrong size and a wrong stroke are each rejected.

- **Office host (Required)**: every glyph paints in Colorful, White, Dark Gray and Black; a theme change while Excel is open repaints the tab without a restart; high contrast stays legible; no blank square anywhere; menu row heights are unchanged.
- **Visual**: none — no scene or chart output changes, and the golden scene must stay byte-identical.

## Risk and rollback

The main risk is the undocumented theme value: an Office build that changes it leaves the palette on the system fallback, which is reported rather than silent. Rollback is `git revert` of the asset commit, then of the XML commit; the two are separate so the ribbon is never left without glyphs.
