## Step 0 — verify prerequisites (Tier A, revised 2026-11-21)

- R7.3 lands first (the validated group's bounds are the input). **R6.1's bounds model
  landed:** [`ExportBounds.Bounds`](../../src/GanttCreator.Core/Scene/ExportBounds.cs)
  is the zero-origin rectangle `(0, 0, ChartBounds.Width, ChartBounds.Height)` and
  [`ExportBounds.PlacementDelta`](../../src/GanttCreator.Core/Scene/ExportBounds.cs)
  is `(ChartBounds.X, ChartBounds.Y)`.
- **`PlacementDelta` is already consumed by the staging composition.** The staged group
  is zero-origin; the PowerPoint fit uses `Bounds.Width`/`Bounds.Height` and must
  **never** subtract or add `PlacementDelta` again. Using `ChartBounds` instead of
  `Bounds` would carry the sheet-relative offset into the slide and place the group
  off-slide; that is a defect, not an alternative.
- **`InvalidBounds` is checked against the resolved bounds, not only the request.** The
  resolver currently refuses a non-positive `request.PlotBounds`
  ([`ExportBoundsResolver.TryResolve()`](../../src/GanttCreator.Core/Scene/ExportBoundsResolver.cs)),
  but a clamped/frame-derived `ChartBounds` can still be degenerate. R7.6's shared
  pre-flight must add the post-resolution guard: `Bounds.Width` and `Bounds.Height` must
  be finite and strictly positive before any staging shape is created; otherwise the
  outcome is `ExportBoundsRefusal.InvalidBounds`. R7.4's `SlideFit` repeats the
  finite/positive guard on its own inputs so it cannot produce a degenerate placement.
- **D-R7.4 is recorded (owner ruling 2026-11-22).** The fit frame is a uniform inset
  derived from the chart's own outer padding
  ([`ChartPaddingPt.Uniform()`](../../src/GanttCreator.Core/Scene/ChartPaddingPt.cs),
  4 pt at scene scale) that **scales with the group**, so the pasted chart keeps the
  margin it was composed with; a fixed percentage inset was rejected as the alternative.
  Because the inset is scene-space, it belongs on the group's side of the ratio and the
  closed form is
  `Scale = min(slideWidth / (groupWidth + 2·inset), slideHeight / (groupHeight + 2·inset))`
  with `Left = (slideWidth − groupWidth × Scale) / 2`, which equals `inset × Scale` on the
  binding axis. [`SlideFit`](../../src/GanttCreator.Core/Export/SlideFit.cs) implements that
  form and its doc comment carries the derivation; the placeholder slide-space reading used
  by the first probe (a flat 4 pt margin) is superseded. **The resize route is also
  recorded: route (a)**, the single absolute `Left`/`Top`/`Width`/`Height` write, which is
  what [`PowerPointTransferAdapter.ApplyPlacement()`](../../src/GanttCreator.Office/PowerPointTransferAdapter.cs)
  already implements. M-7 is **read as** the uncapped fill-to-frame of D2 (the ruling's own
  arithmetic depends on the fit being able to upscale); the measured scales for the
  reference chart are 1.43 / 1.91 / 2.39.
- **The resize route is an owed probe.** The returned range contains the group and its
  flattened children, so resizing the range double-scales the children. Probe three
  routes on the reference host with the representative chart: (a) set the group's
  `Width` and `Height` from one computed scale; (b) set `LockAspectRatio = msoTrue` and
  set `Width`; (c) `ScaleWidth`/`ScaleHeight` with the same factor. Record which route
  preserves geometry, text layout and group-child fidelity, then pin one.

### Step 0 route-probe evidence (recorded 2026-11-21; re-measured 2026-11-22 under the recorded policy)

Method: [`PowerPointSlideFitRouteProbeIntegrationTests`](../../tests/GanttCreator.Office.IntegrationTests/PowerPointSlideFitRouteProbeIntegrationTests.cs)
(`Category=OfficeIntegration`) runs the R7.3 staging → copy → `PasteSpecialShape` path, measures
the text children at the **natural paste scale first**, fits the pasted group with `SlideFit.Fit`
using the recorded D-R7.4 inset (`ChartPaddingPt.Uniform` of the `ChartOuterPaddingPt` token,
4 pt at scene scale), then applies each route to the `msoGroup` and reads the box, the aspect and
the text bounds back. Host builds: **PowerPoint 16.0.20527.20196** (2026-11-21) and
**16.0.20625.20108** (2026-11-22); both runs agree on the route behaviour. Pasted form:
**82 shapes = 1 `msoGroup` + 81 flattened children**, natural box **498.36 × 72 pt**
(aspect 6.9216). Run: 1 test, passed, 30–35 s.

| Slide | Fit target (l, t, w, h) | Scale | Applied: route (a) | Applied: routes (b)/(c) | Aspect Δ |
| --- | --- | --- | --- | --- | --- |
| 720 × 540 (4:3) | 5.69, 218.81, 708.62, 102.38 | 1.42191 | identical to the target | 110.82, 234, 708.62, 102.38 | 0 |
| 960 × 540 (16:9) | 7.58, 201.75, 944.83, 136.5 | 1.89588 | identical to the target | 230.82, 234, 944.83, 136.5 | 0 |
| 1200 × 400 (custom) | 9.48, 114.69, 1181.04, 170.63 | 2.36985 | identical to the target | 350.82, 164, 1181.04, 170.63 | 0 |

All three scales are upscales; the margin is `inset × scale` (5.69 = 4 × 1.42191, 7.58 =
4 × 1.89588, 9.48 = 4 × 2.36985), which is the recorded policy measured on the host.

Measured findings:

- **All three routes hit the target size exactly and preserve the aspect exactly**
  (`aspectDelta` 0.00000 everywhere). The group resize does **not** distort, and the host
  does **not** auto-fit over the single application.
- **Only route (a) also sets the position in the same write.** Routes (b) and (c) scale about
  the paste-supplied top-left, so the group keeps PowerPoint's paste position
  (`110.82, 234` / `230.82, 234` / `350.82, 164`) — a caller using them must write
  `Left`/`Top` **after** the size, which is a second mutation of the same shape and must not
  be reported as one application.
- **Route (c) throws when `RelativeToOriginalSize = msoTrue` on an `msoGroup`**:
  `System.ArgumentException` (0x80070057) — *"The RelativeToOriginalSize argument applies
  only to a picture or an OLE object."* `msoFalse` (scale relative to current size) is
  required. The fixture records this measured reason.
- **Route (b) `LockAspectRatio = msoTrue` + `Width` works** and produced the exact aspect, but
  `Height` is then host-derived, so the applied height is not the value the fit computed.

**Label evidence (D5), measured 2026-11-22.** Every measured text child has
`TextFrame2.WordWrap` **off** and `TextFrame2.AutoSize` **msoAutoSizeNone**, and the font sizes
read **8, 9, 10 and 12 pt at the natural paste scale and identically after every route at every
slide size**. The group resize therefore scales the **shape boxes only** and leaves the text at
its composed size — the ambiguity D5 exists for, now measured rather than assumed.

| Slide | Text children fitting, natural paste | After the fit |
| --- | --- | --- |
| 720 × 540 | 77 / 81 (4 over) | 79 / 81 (2 over) |
| 960 × 540 | 77 / 81 (4 over) | 81 / 81 |
| 1200 × 400 | 77 / 81 (4 over) | 81 / 81 |

The four natural overflows are `label` (`shape 41.9 × 16`, `text 42.4 × 9.6`), two
`panel-text:Type` (`shape 45 × 15`, `text 68.4 × 9.6` and `77.3 × 9.6`) and
`chart:header-text:Description` (`shape 45 × 15`, `text 47 × 10.8`). Because the boxes grow with
the fit and the text does not, **the placement never adds an overflow**: it removes two of the
four at 4:3 and all four at the larger sizes. The two residual 4:3 overflows are a
**pre-existing export-composition property** — a 45 pt panel cell carrying 68–77 pt of 8 pt text
with wrap off, staged by R6.2 for the copy path too — not a placement effect. D5's absolute rule
therefore cannot be met at 4:3 until that composition changes. **Owner decision owed:** fix the
header-label composition in a separate item, or record the 4:3 residue as accepted. The Phase-3
gate asserts the placement-side rule (no child that fits at composition stops fitting after
placement) and records the absolute counts beside it.

**Route (a) is recorded (owner ruling 2026-11-22)** — one absolute
`Left`/`Top`/`Width`/`Height` write of the single computed `SlidePlacement` onto the `msoGroup`.
It is the only route that makes the position and the size one application of the fit, it writes

[`PowerPointTransferAdapter.ApplyPlacement()`](../../src/GanttCreator.Office/PowerPointTransferAdapter.cs)

## Design decisions (behavioural)

- **D1 — Pure fit, applied once.** The fit math is Core-pure and unit-tested; the
  adapter applies the single computed placement. A second placement call anywhere fails
  the sequence pin (**positive test**).
- **D2 — Ratio preserved by construction.** One scale drives both axes — with the recorded
  scene-space inset, `Scale = min(slideWidth / (groupWidth + 2·inset), slideHeight /
  (groupHeight + 2·inset))` — and the applied size is `scale × groupSize` on both axes, so
  the ratio cannot drift. The pin asserts the applied aspect equals
  `Bounds.Width / Bounds.Height` within tolerance for every slide class.
- **D3 — The matrix is 4:3, 16:9 and custom.** Custom includes extreme aspect slides.
  Every case pins position (the margin is `inset × scale` on the binding axis, and never
  smaller on the other), scale and ratio. A non-finite or non-positive slide size, group
  size or computed scale is a typed refusal; no degenerate shape is emitted.
- **D4 — Resize the group, never the range.** The `msoGroup` shape is the only target.
  The chosen route is the one measured in Step 0; setting range width/height is
  forbidden because the range also lists the children.
- **D5 — Label fidelity is part of the gate.** PowerPoint does not guarantee that a
  group resize scales text with the geometry. The live gate checks that every label
  remains inside its shape at 4:3, 16:9 and one custom size; a geometry-only pass is not
  sufficient. **Measured refinement (2026-11-22):** the host leaves text at its composed
  size (fonts 8/9/10/12 pt before and after, wrap off, no autosize) and the staged
  composition already overflows 4 of 81 children. The gate therefore asserts the
  placement-side rule — no child that fits at composition stops fitting after placement —
  and records the absolute counts; the composition residue is an owed owner decision
  recorded in the Step-0 evidence above.
- **D6 — The aspect source is `ExportBounds.Bounds`, not `ChartBounds` and not the
  pasted range.** `PlacementDelta` is not applied twice.
