## Step 0 — verify prerequisites (Tier A, revised 2026-11-21)

- R7.3 lands first (the validated group's bounds are the input). **R6.1's bounds model
  landed:** [`ExportBounds.Bounds`](../../src/GanttCreator.Core/Scene/ExportBounds.cs)
  is the zero-origin rectangle `(0, 0, ChartBounds.Width, ChartBounds.Height)` and
  [`ExportBounds.PlacementDelta`](../../src/GanttCreator.Core/Scene/ExportBounds.cs)
  is `(ChartBounds.X, ChartBounds.Y)`.
- **`PlacementDelta` is already consumed by the staging composition.** The staged group
  is zero-origin; the PowerPoint fit uses `Bounds.Width`/`Bounds.Height` and must
  **never** subtract or add `PlacementDelta` again. Using `ChartBounds` instead of
  `Bounds` would carry the sheet-relative offset into the slide and place the group
  off-slide; that is a defect, not an alternative.
- **`InvalidBounds` is checked against the resolved bounds, not only the request.** The
  resolver currently refuses a non-positive `request.PlotBounds`
  ([`ExportBoundsResolver.TryResolve()`](../../src/GanttCreator.Core/Scene/ExportBoundsResolver.cs)),
  but a clamped/frame-derived `ChartBounds` can still be degenerate. R7.6's shared
  pre-flight must add the post-resolution guard: `Bounds.Width` and `Bounds.Height` must
  be finite and strictly positive before any staging shape is created; otherwise the
  outcome is `ExportBoundsRefusal.InvalidBounds`. R7.4's `SlideFit` repeats the
  finite/positive guard on its own inputs so it cannot produce a degenerate placement.
- **The fit frame is an owed recorded decision (D-R7.4), not an invented number.** The
  architecture says "within slide margins" without values. The proposal for the owner:
  a uniform inset derived from the chart's own outer padding
  ([`ChartPaddingPt.Uniform()`](../../src/GanttCreator.Core/Scene/ChartPaddingPt.cs),
  4 pt at scene scale), scaled with the group, so the pasted chart keeps the margin it
  was composed with; a fixed percentage inset is the alternative. The stop-point stands
  until the human records the chosen policy.
- **The resize route is an owed probe.** The returned range contains the group and its
  flattened children, so resizing the range double-scales the children. Probe three
  routes on the reference host with the representative chart: (a) set the group's
  `Width` and `Height` from one computed scale; (b) set `LockAspectRatio = msoTrue` and
  set `Width`; (c) `ScaleWidth`/`ScaleHeight` with the same factor. Record which route
  preserves geometry, text layout and group-child fidelity, then pin one.

Computed scales: 1.42868 (4:3), 1.91026 (16:9), 2.39183 (1200 × 400) — all upscales.

Measured findings:

- **All three routes hit the target size exactly and preserve the aspect exactly**
  (`aspectDelta` 0.00000 everywhere). The group resize does **not** distort, and the host
  does **not** auto-fit over the single application.
- **Only route (a) also sets the position in the same write.** Routes (b) and (c) scale about
  the paste-supplied top-left, so the group keeps PowerPoint's paste position
  (`110.82, 234` / `230.82, 234` / `350.82, 164`) — a caller using them must write
  `Left`/`Top` **after** the size, which is a second mutation of the same shape and must not
  be reported as one application.
- **Route (c) throws when `RelativeToOriginalSize = msoTrue` on an `msoGroup`**:
  `System.ArgumentException` (0x80070057) — *"The RelativeToOriginalSize argument applies
  only to a picture or an OLE object."* `msoFalse` (scale relative to current size) is
  required. The fixture records this measured reason.
- **Route (b) `LockAspectRatio = msoTrue` + `Width` works** and produced the exact aspect, but
  `Height` is then host-derived, so the applied height is not the value the fit computed.
- **Label evidence (D5).** At 4:3 two `panel-text:Type` children report a `TextRange` bound
  wider than the shape box — `shape=64.3 × 21.4, text=77.3 × 9.6` and
  `shape=64.3 × 21.4, text=68.4 × 9.6`. At 16:9 and 1200 × 400 all 18 text children fit.
  The values are **identical under all three routes at the same slide size**, so this is not
  a route artefact. A bound width wider than a wrapping shape is a measurement property, not
  proof of visible clipping; D5 stays in Phase 3 with a wrap-aware measure plus visual
  inspection. This does **not** meet the item stop condition ("labels overflow at every
  route") because the overflow is size-specific and route-invariant.

**Route recommendation: pin route (a) — one absolute `Left`/`Top`/`Width`/`Height` write of
the single computed `SlidePlacement` onto the `msoGroup`.** It is the only route that makes
the position and the size one application of the fit, it writes exactly the values the pure
fit produced instead of a host-derived height (b) or a host-applied factor (c), and it avoids
the `msoGroup`/`RelativeToOriginalSize` trap in (c). The provisional
[`PowerPointTransferAdapter.ApplyPlacement()`](../../src/GanttCreator.Office/PowerPointTransferAdapter.cs)
implementation is already route (a); the read-back comparison in
[`PowerPointPlacementStage`](../../src/GanttCreator.Office/PowerPointPlacementStage.cs)
(0.01 pt tolerance) is the guard that the host accepted the numbers, and it passed in all
nine cells. Still owed to the human: **D-R7.4 margin policy** — the 4 pt inset above is a
probe placeholder, not a decision.

## Design decisions (behavioural)

- **D1 — Pure fit, applied once.** The fit math is Core-pure and unit-tested; the
  adapter applies the single computed placement. A second placement call anywhere fails
  the sequence pin (**positive test**).
- **D2 — Ratio preserved by construction.** `Scale = min(fitWidth / groupWidth,
  fitHeight / groupHeight)`; the applied size is `scale × groupSize` on both axes — the
  ratio cannot drift. The pin asserts the applied aspect equals
  `Bounds.Width / Bounds.Height` within tolerance for every slide class.
- **D3 — The matrix is 4:3, 16:9 and custom.** Custom includes extreme aspect slides.
  Every case pins position (within the recorded inset), scale and ratio. A non-finite or
  non-positive slide size, group size or computed scale is a typed refusal; no
  degenerate shape is emitted.
- **D4 — Resize the group, never the range.** The `msoGroup` shape is the only target.
  The chosen route is the one measured in Step 0; setting range width/height is
  forbidden because the range also lists the children.
- **D5 — Label fidelity is part of the gate.** PowerPoint does not guarantee that a
  group resize scales text with the geometry. The live gate checks that every label
  remains inside its shape at 4:3, 16:9 and one custom size; a geometry-only pass is not
  sufficient.
- **D6 — The aspect source is `ExportBounds.Bounds`, not `ChartBounds` and not the
  pasted range.** `PlacementDelta` is not applied twice.

## Stop conditions (item-specific)

- A slide size distorts the group (host auto-fit interference) → stop with evidence; the
  once-rule may need an ADR amendment, not a quiet second scaling.
- The margin policy needs a product number → stop; record the proposal; the human picks.
- The resize-route probe shows text does not scale and labels overflow at every route →
  stop; the export contract needs a decision, not a workaround.

## Risk and rollback

Main risk: host auto-behaviour after paste (auto-fit) fighting the single application,
and text scaling differing from geometry scaling — the live per-size gate catches both.
Rollback: `git revert`.
