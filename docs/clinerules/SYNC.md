# Two views of the same kit

> The Gantt Creator development kit has two views of the same seven
> documents. Each view has a different audience and a different loading
> rule. This file explains the relationship and the sync discipline.

## The two views

| View | Path | Audience | Loading rule |
| --- | --- | --- | --- |
| Canonical in-repo source | `docs/0N-*.md` | Human reviewers, the source of truth | Read on demand; this is the only view you edit by hand |
| On-demand skill | `.cline/skills/0N-name/SKILL.md` | Cline (on-demand) | Progressive loading: ~100-token metadata always in context; full SKILL.md loaded when the conversation matches the `description:` front-matter |

There is deliberately no third view. Earlier revisions also generated
`.cline/skills/0N-name/references.md` — a full byte-for-byte copy of
the canonical `docs/0N-*.md` body. It was removed (2026-09) because
`SKILL.md`'s own footer already points at the canonical source, so the
copy cost real repo bytes and a whole drift-gate subsystem
(`references.md` existence/parity checks) for zero information the
canonical source didn't already provide at the same token cost. When
`SKILL.md`'s summary is not enough, the next hop is `docs/0N-*.md`
directly — there is nothing else to load.

Always-on rules live in `AGENTS.md` at the repository root. `AGENTS.md`
is loaded by Cline on every turn and is the right home for the critical
invariants that must always be in context. It is hand-maintained and is
NOT regenerated by the sync script. `AGENTS.md` should stay a *pointer*
to each skill's detail, not a second copy of it — every section that
elaborates rather than states a hard invariant should end with a
one-line reference to the matching skill instead of restating its
content.

## Which one do I edit?

**Edit the canonical source** at `docs/0N-*.md`. The skill view is
derived from it. After editing, run `pwsh ./scripts/sync-cline-skills.ps1`
to refresh the on-demand skill.

### The SKILL-SUMMARY block

Each canonical doc carries a hand-authored summary the sync script
extracts verbatim:

```markdown
<!-- SKILL-SUMMARY:START -->
5-15 lines: what this doc is for, and the 2-4 things about it that are
most load-bearing / easiest to get wrong.
<!-- SKILL-SUMMARY:END -->
```

Place it directly after the doc's title (and its `>` context blockquote,
if it has one). This replaced a "first 80 non-empty lines" truncation
heuristic that silently dropped load-bearing content whenever a doc
edit pushed it past line 80 — the failure mode `check-skill-summary.ps1`
existed to patch with hardcoded phrase checks. A hand-authored block
co-located with its source can't drift the way a separate summary file
could, and can't be silently truncated by doc growth. If you edit a
doc's `SKILL-SUMMARY` block, keep it honest: it should still name the
things in the doc most likely to be gotten wrong, not just its topic.

If a canonical doc has no `SKILL-SUMMARY` block, the sync script now
FAILS with a non-zero exit — the migration to hand-authored blocks is
complete (every mapped doc carries one), so the old line-truncation
fallback was removed. A missing block can never again be silently
degraded into a truncated heuristic summary: add the block and re-run.

## What the sync script does

`scripts/sync-cline-skills.ps1`:

1. Reads every `docs/0N-*.md` listed in its `$map`.
2. For each, regenerates `.cline/skills/0N-name/SKILL.md`: front-matter,
   the doc's `SKILL-SUMMARY` block (missing block = hard failure), and a
   footer pointing at the canonical source.
3. Validates that every skill directory has a `SKILL.md` and exits
   non-zero if any is missing.

The script is idempotent. Running it twice in a row produces the same
output.

## The drift gate

`scripts/check-cline-skills.ps1` runs the sync and then fails the gate
if a fresh sync produced any diff. Wire it into `verify-quick.ps1`
and `verify.ps1` so that drift fails the build.

```powershell
# Run the non-destructive drift gate. This checker regenerates the
# .cline/skills/ tree in a temp directory, compares it to the committed
# tree, and exits non-zero if they differ. The on-disk .cline/skills/
# files are not modified by the gate itself, so hand-edited local
# changes are preserved if you abort before committing.
pwsh -NoProfile -File scripts/check-cline-skills.ps1
if ($LASTEXITCODE -ne 0) {
    Write-Error 'Skill tree is out of date. Run scripts/sync-cline-skills.ps1 and commit the result.'
    exit 1
}
```

## Why two views and not one

- **Always-on rules** must be short — they are scanned every turn, and
  a 45 KB entity guide would burn the agent's context window on every
  interaction. `AGENTS.md` is the *contract*, not the *reference*.
- **On-demand skills** carry the summary; the canonical doc is the full
  reference. The `description:` field is what Cline uses to decide
  whether to load the skill, so it must be specific enough to match the
  right skill in a single sentence and not so long that the loader
  wastes context on every turn.
- **The canonical mirror** is the only file you edit by hand. One view
  reads from it; one view is the kit the human reviewer reads.

## Adding a new skill

1. Add `docs/0N-name.md` with the new content, including a
   `SKILL-SUMMARY` block near the top.
2. Add an entry to the `$map` in `scripts/sync-cline-skills.ps1`
   (`Name`, `Description`).
3. Run `pwsh ./scripts/sync-cline-skills.ps1`.
4. Commit `docs/` and `.cline/skills/` together.

A new canonical source without a `$map` entry will be invisible to the
sync script and the gate will not catch it. A `$map` entry pointing at
a non-existent canonical source will fail-fast at sync time. A doc
without a `SKILL-SUMMARY` block will fail the sync with a non-zero
exit until one is added.
